## 逐页

### 3 老人办银行事，难在哪

上屏：

- 用户这头：看不懂菜单、怕点错、怕被骗
- 业务那头：步骤多、安全检查严，一步都不能省

讲稿：银发用户想转个账、查个账单，要翻好几层菜单，还担心被骗。银行这边，一笔转账要核对收款人、金额、风险、验证码，一步都不能少。所以难点有两个：要让老人用起来简单，也要守住银行的严格。

### 4 说一句话，任务一步步办好

上屏：

- 用一句大白话说需求，例如"给妈妈转500元"
- 助手听懂这句话，程序把它排成一步步能核对的任务
- 动钱必须您本人确认，结果只认银行
- 覆盖赛题 01 转账、02 账单、05 订阅/代扣、06 跨场景联动（生日、养老金）

配图：S01 首页、G01 生日一句话直达配送表单。

讲稿：用户不用找菜单，直接说就行。助手听懂要办什么，程序排出几个步骤，每一步做到哪里都看得见。赛题六个场景我们做了四个，其中跨场景联动做了生日和养老金两个例子。

### 5 核心设计：Agent 出主意，程序把关

上屏：freedom-guardrails.png（左栏 Agent 的自由，右栏程序的兜底，底部生日例子）。三条铁律：

- 模型只动嘴不动手
- 动钱必过确认门
- 银行规则只在银行

讲稿：这页是我们最核心的判断。银行的流程是一步一步写死的，Agent 的价值在于灵活。我们的做法是：听懂口语和改口、从能办的业务里选对一项、把"给妈妈过生日"这样的整件事交给联动流程而不是拆成零碎小事、用白话解释，这些交给 Agent；排出哪几步、参数对不对、动钱前要不要确认和验证、结果算不算数，这些交给程序。Agent 只能提出要办什么，执行权在程序手里。所以 Agent 越灵活，程序的门就越要守住。

### 6 系统架构：为什么选 LangChain 生态

上屏：architecture.png，旁注三点：

- Deep Agents：负责理解与提议，模型 GLM-5.3，只能从白名单里选
- LangGraph：状态、检查点、暂停与恢复，多步业务能停下等确认，中断后从原位置继续
- 模拟银行：余额、限额、风控、去重都在银行侧

讲稿：银行业务步骤多、检查多，所以我们选了 LangChain 生态。Deep Agents 负责听懂用户、提出要办什么。LangGraph 负责记住每个任务办到哪一步：转账、生日这些多步业务每到动钱的地方就停下来，等用户确认后再沿原任务继续，中途断了也能接上。银行规则不在 Agent 里写一份，全部以模拟银行返回的结果为准。

### 7 交互：聊天为主，卡片为辅

上屏：

- 聊天是主入口：为老年人设计，说话最自然
- 卡片做快捷操作：确认、修改、取消，查看步骤和回执
- 两种方式改的是同一个任务

配图：T05（聊天说"金额改成600元"，同一任务出新确认单）、R01b（计划卡看步骤）、X03（中断后"接着上次的办理"）。

讲稿：老人最习惯的是说话，所以聊天是主入口。有些事点一下比说一句更快、更准，比如确认、取消、看进度，这些放在卡片上。验证码这类敏感信息只能填在卡片的专用框里。聊天改了金额，卡片马上换成新的确认单，因为两边操作的是同一个任务。

### 8 任务一：转账

上屏流程：一句话 → 追问用哪张卡 → 确认单 → 验证码 + 刷脸 → 回执。

配图：T01、T02、T03a、T04。数字：转出 501 元，余额 60000.00 → 59499.00。

讲稿：说"给妈妈转500元"，助手问用哪张卡，然后出确认单，写清收款人、金额和手续费。这笔属于中风险，还要输验证码、刷脸。成功后回执上的余额来自银行返回。刷脸在演示里由管理员页模拟作答。

### 9 任务二：账单与减支

上屏：

- 账单：本月消费按类别分开，转账另外列出、不算消费
- 减支："帮我省点钱"，列出可以退订的扣费，退订前要确认和验证
- 结果：退掉一项视频会员，每月少扣 25 元；点"先不退了"也可以

配图：B01、R01、R02、R03。

讲稿：账单把消费分类，转账单独列出，老人不会把转给子女的钱当成花掉了。说一句"帮我省点钱"，助手列出可以退订的项目。退订一样要过确认单，也可以随时说先不退了。

### 10 创新一：生日联动

上屏：一句话"11月7日是我妈妈生日，500元以内帮她安排花和蛋糕" → 不再追问预算和日期 → 填配送信息 → 选花和蛋糕 → 采用方案 → 留出 500 元专款 → 花和蛋糕各自下单、付款 → 自动退回没花完的钱。

结果：9 步办完，5 次付钱前确认 + 验证，鲜花 199 + 蛋糕 268 = 467 元，退回 33 元。

配图：G01、G03、G05、G06。

讲稿：这是赛题例子"生日锁定资金加订花订蛋糕"的完整实现。用户说一句话，Agent 听懂这是一件生日安排，预算和日期从原话里读出来，不再重复问。程序排好步骤：先从卡上留出 500 元专款，只能用于这次生日；花和蛋糕的每次下单、付款都要用户确认和验证，一共 5 道门；办完后没花完的 33 元由程序自动退回原卡。Agent 负责听懂，程序负责每一步和每一道门。

### 11 创新二：养老金到账安排

上屏：到账 5000 元 → 留生活费 1500、转本人储蓄 2500、转家人 1000 → 顺手退订一项每月 39 元的网盘。

配图：P01、P02。脚注：养老金演示启用了预设演示数据，首句须使用固定原话。

讲稿：每月养老金到账，老人常常要分几处。说一句话，助手排好方案，两笔转账各自确认、验证，没用的扣费顺手退掉。这个场景用了预设的演示数据，我们在页面和材料里都写明了。

### 12 安全：动钱必过确认门

上屏四格：

- 确认门：确认单 + 验证码 + 刷脸（T03a）
- 信息套取：验证码发进聊天会被拦，提示填到专用框（X02）
- 诱导转账 / 注入：粘贴可疑"安全账户"短信，只分析破绽、不办理（X04）
- 超范围：问挂失，如实说办不了并提醒打客服电话（X01）

底部一行：外部文字当数据、不当指令；银行侧按身份逐次授权；结果不确定时先查原操作，不重做。

讲稿：评分里安全占三成。我们不靠模型自觉，靠程序设门：动钱必须确认和验证；验证码不能进聊天；外面粘进来的文字只当资料看，不能变成命令；办不了的事如实说。银行那边还会按身份再查一次权限，模型说什么都不能代替。

讲稿：我们给每个场景都建了评测集，用例写清输入、期望和结果，都在仓库的 evals 目录里。数字按层次分开写，失败的也照实列出。
