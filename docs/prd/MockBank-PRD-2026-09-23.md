## 一、用户目标与功能范围

### 1.1 它和其他场景有什么不同

我们的系统里**不接真实银行**，而是自己造一家"模拟银行"。

它**不是一个面向用户的场景**——用户永远不会跟它说话，也不会有"打开模拟银行"这个动作。它是**转账、账单、跨场景联动三个场景共用的一家银行**：三个业务模块要查钱、要转钱、要冻钱，都来找它。

所以对它来说，"用户是谁"这个问题要换个问法：**它的"用户"是三个业务模块。**

| | 面向用户的场景（转账/账单/联动） | 模拟银行 |
|---|---|---|
| 谁在用 | 银发用户 | 三个业务模块 |
| 用户说什么 | 一句话需求 | 结构化请求（金额、账号、编号） |
| 输出什么 | 给用户看的回话与确认单 | 给业务模块用的事实和结果 |
| 流程固定吗 | 不固定，AI 编排 | **高度固定**：查条件 → 办事 → 报真实结果 |

### 1.2 一句话目标

**给整个系统提供一家"像真的"银行：有一本账、有真实规则、说一不二。**

三个关键词：
- **有一本账** —— 钱是记在账上的，转出去就真的少了，不是假装。
- **有真实规则** —— 限额、账户状态按真实银行的做法来（有监管依据的用监管数值）。**手续费是例外：本 demo 一律不收（恒为 0），见第 4 章 D03。**
- **说一不二** —— 它返回的结果是唯一事实来源，业务模块和模型都不能自己猜。

### 1.3 谁在用它

| 场景 | 用它做什么 | 本阶段 |
|---|---|---|
| 01 智能转账 | 查收款人（历史收款人 / 常用对手方）、查限额、试算费用、转钱、超时后回查 | 做 |
| 02 账单分析 | 查流水（**消费基线已取消**，账单本地自算，见 X4） | 做 |
| 06 跨场景联动 | 冻结预算、分笔扣款、释放余额、查交易结果 | 做 |
| 03 理财操作 | 账户余额、交易流水（以后还要产品信息、持仓） | 以后 |
| 04 卡片管理 | 账户状态、卡片信息（以后） | 以后 |
| 05 订阅 / 代扣 | 签约授权、周期扣款（以后） | 以后 |

### 1.4 它不做什么

- **不猜用户想干什么。** 用户说"给我妈过个生日"，那是业务模块该理解的事；模拟银行只认"转 500 给某某账户"。
- **不跟用户直接对话。** 所有面向用户的话都由业务模块组织。
- **不替业务做判断。** 比如"这笔消费算不算异常"是账单模块的判断，银行只负责提供事实（近 3 个月月均 800 元）。
- **不做真实银行的生产安全与合规。** 首版是模拟环境，明细与回执都会标注"模拟"。

## 二、功能范围：六个能力域

银行一共能提供这六类服务。**按"能力"分，不按"业务"分**——不说"给转账用的接口"，说"资金划转能力"。这样以后新业务来了，需要的是同一件事就直接复用。

| 能力域 | 一句话 | 现在谁用 | 以后谁用 | 本阶段 |
|---|---|---|---|---|
| **账户** | 谁的钱、多少、什么状态，还剩多少能转 | 01、06 | 03、04 | 做 |
| **交易** | 把钱转出去、付出去 | 01、06 | 05 | 做 |
| **查询** | 查余额、查流水、查一笔交易到底怎么样了 | **01、02、06** | 全部 | 做 |
| **清算** | 钱多久到（**本 demo 一律即时，不收手续费**） | 01 | 06 | 做 |
| **资金管理** | 先把钱冻住，花多少扣多少，剩下的放回来 | 06 | 03 | 做 |
| **签约授权** | 约定"以后每月自动扣" | 还没有人用 | 05 | **预留，不实现** |

### 每个域内部的一条划分原则

**把「查、验、算」和「真的动钱」分开。**

银行不能只有一个"转账"动作。业务模块在动钱之前，必须先能问清楚：

- **验**：这个账号是谁的？户名对不对？（→ 账户域）
- **查**：今天还剩多少额度？钱够不够？（→ 账户域）
- **算**：这笔收多少手续费（**本 demo 恒为 0**）？几点能到（**恒为即时**）？（→ 交易/清算域）

**少了前面这几个，业务模块就没法在动钱之前把方案给用户确认清楚。** 这条原则贯穿第 3—7 章。

#### "故意慢一次"开关（两档）

能让某一次交易不按时返回，用来演"结果未知 → 按原编号回查 → 绝不重发"。**分两档**：
- **约 6 秒返回** → 演"查到了，没有重发"
- **超过 10 秒（如 15 秒）** → 演"10 秒还没确认，转需要关注"

**不开时一切正常。** 管理页按指定演示用户设置下一次对应操作的故障，触发后自动恢复；页面显示是否仍待触发。正式演示使用 6 秒档，长等待档仅用于既定截图 / 说明。管理权限由后端检查，Agent 无权设置，见[公共契约第 7 章](../contracts/公共契约-2026-09-23.md)。

> **配套前提（不写这条，两档都演不出来）**：**业务模块首次提交划转后等 4 秒没答复即视为超时**（D09-b 已拍板：**4 秒**），**必须小于 6 秒**（"故意慢一次"的 6 秒档），否则 6 秒档在第一次调用就正常返回了，永远走不到"回查"那一步。
> 完整时间线（首次超时按 4 秒算）：**6 秒档** → 第 4 秒判定超时 → 第 7 秒回查，查到成功 → 演"查到了，没有重发"。**15 秒档** → 第 4 秒超时 → 第 7、10、13 秒回查仍未确认 → 第 14 秒达到额外等待 10 秒上限，转"需要关注"。
> **演示提示：演超时只用 6 秒档**（4 秒超时 → 回查 1 次成功，总共约 7 秒）；**不要用"超 10 秒档"**，那档最坏要等 14 秒，只在截图 / 说明里用。

#### "时间快进"开关（**定时转账演示启用**；非实时到账仍不启用，09-24 拍板）

把演示环境的**逻辑时钟**拨到指定时刻，演"到点"类行为。**启用范围**：
- **定时转账**（09-24 定）：拨到预约执行时间 → 银行自动扣款、生成流水（种子 P1）；拨过午夜 → 日限额按自然日重置；
- **仍不启用**：非实时到账（普通 / 次日）本轮不做，到账方式仍只有"实时"一种取值（D15）。

> 快进只动逻辑时钟，只能向未来推进；跨期预约执行与自然日限额重置按时间顺序处理。验证码、确认有效期和网络超时均按真实经过时间计时。快进动作留痕；需要回到演示起点时走整体重置。

#### 演示管理与整体重置（09-24 第五批已确认）

简单管理页统一提供故障、模拟人脸结果、快进和重置，并可立即使当前登录会话过期。第六批修订：人脸在演示前端为当前验证直接点「模拟成功 / 模拟失败」，不再预设下一次结果；后端检查管理权限、归属和有效期，模拟银行记录事实。涉诈账户继续由种子数据提供，不修改银行风控规则。登录会话固定 2 小时，刷新不续期；提前过期与自然过期按公共契约 §6.3 处理。

重置经管理页二次确认后，底座停止接受新业务请求并等待在途执行完成，再协调银行恢复种子、应用会话 / 任务 / 确认 / 验证失效、记忆恢复预置、故障恢复默认和逻辑时间回到起点。银行只重置自己的数据，不直接操作应用存储。无法完成等待或重置时明确显示未完成，不能强行清空正在扣款的数据或报告成功。成功后旧任务不得操作新一轮环境；历史审计按演示轮次保留，不随业务数据删除。预置记忆的具体条目另列清单，不能预置验证通过或覆盖银行事实。正式规则以[公共契约 §7](../contracts/公共契约-2026-09-23.md)为准。

## 三、账户域

### 这个域管什么

"谁的钱、有多少、什么状态、能转多少"。

### 业务规则

| 规则 | 说明 |
|---|---|
| **账户分三类** | Ⅰ类（全功能）、Ⅱ类（限额）、Ⅲ类（更小限额）。**本阶段演示只用Ⅰ类户**，但字段保留三类，以后按需启用 |
| **限额按类别判定** | Ⅱ类户：日累计 1 万 / 年累计 20 万；Ⅲ类户：余额 ≤2000 元、出金 日 2000 元 / 年 5 万；Ⅰ类户：单笔 5 万 / 日累计 5 万（**Ⅰ类无数值规定，这是我们的设定**） |
| **不做多层限额** | 只按账户类别判定。**不做**认证方式（U 盾/短信）和渠道（柜面/网银）的分级限额——演示里没有这些介质 |
| **账户状态三种** | **正常 / 冻结 / 销户**。正常能收能付；冻结只收不付；销户不能用 |
| **两个余额要分清** | **账面余额**（一共有多少钱）和**可用余额**（现在能花多少）。**被冻结的钱算在账面里，但不算在可用里** |
| **核验收款人** | 给账号 + 姓名，返回"是否匹配"和**打码后的姓名**（如 `张*三`）。转账确认单上要显示，让用户认人 |
| **限额余量查询** | 可以主动问"今天/今年还剩多少额度"。业务模块排多笔支出前先算够不够，**不能等超限了才报错** |
| **户名打码** | 确认单和流水中，收款人姓名按 `张*三` 形式打码。**具体保留几位、星号几个没有行业规定，是我们的选择** |

## 四、交易域

### 这个域管什么

"把钱真的转出去"。这是**唯一会改变账上数字**的地方，也是安全检查最密的地方。

### 业务规则

| 规则 | 说明 |
|---|---|
| **一次能转多少** | 受账户类别限额约束（见第 3 章）。**到达限额就拒绝，并说清超了哪一项、还剩多少** |
| **行内 / 跨行** | 属性保留，但**不模拟任何速度差异**：行内、跨行**都是即时到账，没有任何人为延迟**（D03）。不模拟大小额支付系统、清算窗口、日终维护 |
| **手续费** | **一律不收手续费（恒为 0）**——不做收费场景、不做收费开关（D03）。答辩口径："手机银行免手续费是行业常态，本 demo 按常态演示。" |
| **动钱前先试算** | 业务模块可以**先问"这笔收多少手续费、预计什么时候到"，拿到结果再去问用户**——这样确认单上的数字才是准的 |
| **陌生账户概念** | 过去 3 个月没打过交道的账户算"陌生"。这个判断供账单场景做异常识别用 |
| **涉诈风控拦截** | 预置一个**涉诈黑名单账号**。往它转账时，银行**直接拦下**，返回"拒绝办理"和原因。**演示只做"拒绝"这一种行为**——《反电信网络诈骗法》第十八条的四种处置（核实交易情况 / 重新核验身份 / 延迟支付结算 / 限制或中止有关业务）**作为拒绝原因的文案素材，不做四个分支**（"延迟支付怎么演"是给自己找麻烦） |
| **重复提交只扣一次** | 同一笔交易（同一个交易编号）重复提交，**只能扣一次钱**，第二次返回第一次的结果 |
| **同编号但参数不一样 → 强制拒绝** | 如果交易编号相同、但**金额或收款人变了**，银行**必须拒绝并报"参数冲突"，绝不放行**。这条防的是"换个参数绕过原编号再提交一次"——只做"重复放行"是不够的 |

## 六、查询域

### 这个域管什么

"查历史"和"查某一笔"——**这是两件不同的事**。

### 业务规则

| 规则 | 说明 |
|---|---|
| **能查多久** | 支持最近 **24 个月**，够出年度报告 |
| **查询完整性（09-24 已定）** | 一次返回指定账户与时间范围内的全部流水，不分页、不静默截断；区间含开始、不含结束。超出最近 24 个月支持范围明确报错；无记录返回空列表，查询失败不得说成无记录；返回数据截至时间。具体规则见公共契约 §2.2 |
| **流水要带分类标签** | 一条流水不能只有金额和时间，必须带三样：**交易性质**（消费 / 转账 / 退款 / 利息）、**商户类别**（餐饮、医疗、购物…）、**方向**（流入 / 流出）。**这是账单场景能不能做分类统计的命脉** |
| **为什么要"方向"** | 四种性质里**只有「转账」两个方向都有**——工资是**流进来**的转账，给妈妈转 500 是**流出去**的转账。少了方向，账单的「转账」那一格会把这两笔加在一起，**直接算错**。其余三种方向固定（消费永远流出，退款和利息永远流入） |
| **冻结 / 释放不算消费流水** | **冻结（占用）和释放（解冻）不计入消费流水，也不计入任何消费统计**；但系统里**留痕、可查询**——作为"资金冻结 / 资金解冻"事件，**不算花钱**。**只有"从冻结里扣款"才生成一条真正的消费流水**（带**商户名 + 用途**、**交易分类**、**方向=流出**）。**释放出来的钱绝不能记成"退款"或"收入"**（见第 13 章 D06） |
| **工资 / 奖金 / 报销怎么认** | 性质是「转账」、方向是「流入」、对方是单位、摘要写"工资 / 奖金 / 报销"。**不为工资单独加一类**——真实银行里代发工资也只是一笔转账 |
| ~~**消费统计基线**~~ **已取消（X4，09-23 预审会）** | 原设计是"按账户和月份跨度查询月均消费、单笔最高"。**现改为：银行不提供这个数**——账单模块本来就要拉全量流水（12 个月），由它**本地自行计算**基线，银行不重复算 |
| **单笔交易回查** | **凭交易编号查某一笔到底怎么样了**。这跟"查流水"是两件事——超时或中断时靠它确认钱扣没扣 |
| **数据时效** | **即时入账**，查到的就是最新的。回执里标注"模拟环境" |

## 七、资金管理域

### 这个域管什么

"先把钱占住，花多少扣多少，剩下的还回来"。**这是跨场景联动能不能跑通的关键。**

### 业务规则

| 规则 | 说明 |
|---|---|
| **可以冻结一笔钱** | 业务模块可以说"我要留出 500 元办事"，这 500 就从可用余额里挪进"冻结" |
| **冻住的钱能分笔扣** | **不是"全冻全解"。** 先冻 500，第一笔花 200 就从冻结里扣 200，第二笔花 150 再扣 150，**还剩 150** |
| **扣款时三个数字怎么变（重要）** | 举例：账面 1000、冻 500 后 → 账面 1000 / 冻结 500 / **可用 500**。这时扣 200：**账面减 200（变 800）、冻结减 200（变 300）、可用余额不变（还是 500）**。**从冻结里扣款不再动可用余额**——否则会重复扣减，凭空少 200 |
| **剩下的可以释放** | 事情办完，把没花完的 150 释放回可用余额。**回执要明确告诉用户**："已消费 350 元，剩余 150 元已解冻" |
| **冻住的钱算不算已花** | 不算"已消费"，但**不能再花第二次**——它已经从可用余额里扣走了 |
| **冻结、扣款、释放要不要进流水** | **冻结（占用）和释放（解冻）不计入消费流水**，也不计入任何消费统计；但系统里要**留痕**——可作为"资金冻结 / 资金解冻"事件，**可查询，不算花钱**。**只有"从冻结里扣款"才生成一条真正的消费流水**：带**商户名 + 用途**、**交易分类**、**方向=流出**（见第 13 章 D06） |
| **能不能撤销 / 退款** | **银行不提供撤销与退款能力。** 没提交的请求银行根本没见过；**钱已经付给商户的，不退**（真实银行到账后本来就不能单方面撤销）。**但钱还没花出去、只是被冻结占着的，必须能释放**——那是用户自己的钱。统一口径（建议写进回执）：**"没花的不扣，花了的不退。"** |
| **资金预留机制** | **冻结 + 分笔核销 + 差额释放**：先冻结一笔预算（如 500），按实际花费**分笔核销**（如 350），办完把**差额释放**回可用余额（150）。**不用预授权**——预授权要多一层对账，demo 没必要。06 直接按冻结能力调用（见第 13 章 D10）。**"冻结能释放"不等于"已付款能退款"**（见 D11） |

| 试算费用与到账时间 | 金额、行内还是跨行、哪种到账速度 | **手续费恒为 0；到账时间恒为即时**（不按行内 / 跨行区分，D03） | 动钱之前拿给用户看。**本轮主线固定实时到账（R3）** |
| **检查本笔交易条件（预检查）**（09-24 补） | 转出账户、收款方、金额等本笔交易要素 | 银行检查交易格式、余额、限额、账户状态及银行侧风控，返回能否办理、原因、关键数字和费用 | 确认前准备交易事实；提交时银行重新检查，预检查不代替确认或身份验证 |
| 划转资金 | 金额、付谁收谁、调用方操作编号 | **成功 / 失败 / 处理中**及对应银行回执；涉风控时返回"拒绝办理"及原因；**同操作编号但参数不符时返回"参数冲突"并拒绝** | 决定下一步能不能继续。⚠ **"涉风控"的范围见第 11 章的 X8 对齐提示** |
| 冻结金额 | 金额、冻结原因 | 冻住多少、冻结编号 | 下单前先占住钱 |
| 从冻结里扣款 | 冻结编号、本次扣多少、**商户名与用途**、**交易分类** | 扣掉后还剩多少冻着 | 多笔支付一笔一笔核销；**这是唯一生成消费流水的动作（方向=流出）**，带上商户和分类，这笔才会在账单里有名有姓 |
| 释放冻结金额 | 冻结编号、释放多少 | 解冻成功，钱回到可用余额 | 办完事后把没花完的预算退回来。**释放出来的钱不能记成"退款"或"收入"**——否则账单会凭空冒出一笔收入（只留痕，不进消费流水） |
| **查冻结余额** | 冻结编号 | **现在还剩多少还冻着** | 中断恢复后核对进度 |
| 查询流水 | 哪段时间、哪个账户 | 流水明细（带**交易性质 + 商户类别 + 方向**三个标签）；没有就说没有 | 做分类统计、找异常。**方向（流入 / 流出）必须有**，否则账单会把工资和转出算进同一格 |
| ~~查询消费基线~~ **已取消（X4）** | — | **银行不再提供月均消费 / 单笔最高** | 09-23 预审会：账单本来就要拉全量流水（12 个月），**改为本地自行计算基线**，银行不多算这个数 |
| 查原操作结果（含交易回查） | 调用方操作编号、服务端可信身份 | 查到时返回与提交共用的操作结果及回执；未查到记录与本次查询失败分别表达，不当成交易失败 | 未收到银行交易编号也可回查；覆盖上述业务写操作，避免重复扣款、冻结或下单 |
| **预约转账（创建 / 查看 / 取消 + 到点执行）**（09-24 补） | 预约信息（收款方、金额、转出账户、执行时间、周期与结束条件） | 预约编号、未来期次、操作结果；**到点由银行自动执行**——扣款、生成流水、不向用户二次确认；余额不足直接失败不补扣 | 01 定时转账：应用侧只管创建 / 查看 / 取消，已创建预约不可修改；改需求须先确认取消并核实成功，再确认新建，取消未知不得先建替代预约。**执行触发在银行侧**（真实银行预约转账语义）；演示推进用时间快进开关 |
| **外部生活服务 Mock（商品查询 / 下单 / 订单状态）**（09-24 补，K1） | 商品查询：商户或用途；下单：商品 + 数量 + 地址 + 时间；订单状态：订单编号 | 商品列表（**取自价目表种子 ⑧**：商品、价格、可送达时间）；下单**只返回成功 / 失败**；订单状态与失败原因 | 06 任务 A 的花与蛋糕；取消 / 退款不做（D11"没花的不扣，花了的不退"） |
| **环境重置**（09-24 补） | 重置指令（演示 / 测试入口） | **清除全部动态信息**（流水、预约单、冻结、订单），回到种子态 | 演示环境提供**多个虚拟账户**配合演示；彩排 / 联调污染后一键还原，第二场演示不砸 |

**这张表是业务模块找银行要能力的唯一入口。** 前面正文提到的每一项能力，这里都要有一行——**正文有、表里没有，业务同事就不知道该管银行要什么。**

**09-24 范围与结果补充**：预约只支持单次 / 每月，每月必须指定结束日期或执行次数，不接受每日、每周或无限期预约；应用先补齐条件再提交。订单下单结果仅说明创建成功 / 失败，付款状态另记为未付款 / 已付款，只有扣款成功才为已付款。从冻结为订单付款时必须带订单编号，银行核对归属、商户与金额，记录付款交易，并保证同订单最多成功付款一次（换操作编号也不能重复支付）。账本与订单付款关联在银行自身边界内保持一致。扣款明确失败保留未付款订单，明确未花掉的冻结可释放；下单或扣款结果未知先核对，不释放可能仍用于在途付款的冻结。具体语义引用[公共契约 §3.3 / §3.4](../contracts/公共契约-2026-09-23.md)。

### 本章的两条核心

**09-24 核验交接补充**：验证码通过前端专用输入框交后端，再经接入层由银行核验，不进入模型、日志或检查点；演示专用提示区标明「模拟验证码」，不接真实短信。验证码有效期 5 分钟，重发旧码失效；低风险连续错 3 次终止本次任务，重发不清零计数。中风险任一核验失败或超时直接终止，成功记录只绑定当前动作。银行保存真实验证记录供安全底座按归属与范围核对，不接受业务自填「已通过」；接口字段见公共契约配套草稿。

> **一、银行说的才算数。**
>
> 业务系统不能自己猜"应该成功了吧"，模型更不能替银行宣布成功。**只有银行返回的结果是事实。**

> **二、"结果未知"不是银行说的话。**
>
> 银行的交易状态只有**成功 / 失败 / 处理中**。所谓"结果未知"，是**业务模块没在预期时间内等到答复**（调用超时），于是**拿调用方原操作编号回来查**。查不到记录或本次查询失败是回查情况，不是新增的交易状态。
>
> 这个区分现在不写清，定字段时一定会纠结"未知"到底由谁给。

### 超时后怎么查（已定）

首次提交划转等待 **4 秒**超时后，每 **3 秒**回查一次，自动回查阶段**最多再等 10 秒**。未查到记录、查到处理中或查询临时失败，在剩余时间内继续查原操作；单次查询耗时计入总时限，失败不重置计时。登录过期或无权限时停止查询，恢复合法访问条件后方可再查，原操作仍待核实。

到达截止时间仍无法核实，任务进入「需要关注」，停止自动查询并保留原操作编号；用户可主动点击「查询结果」，服务端再次核验身份与任务归属后只查询原操作。查到明确结果后更新原任务，一直查不到则继续待核实，**绝不因未查到或查询失败而重发交易，也不能换编号绕过核对**。银行失败结果提供原因码及关键数字，用户话术由业务模块组织。

时间定得短是为了不拖累演示体验；现场用第 2 章的 **6 秒慢档**演示结果未知后回查成功（D09-b）。超出回查截止时间的分支在验收用例中验证。

## 十、主要异常、修改与取消

| 类别 | 银行该告诉业务/用户什么 |
|---|---|
| **条件不满足** | 钱不够，差多少；超了哪一项限额，还剩多少；账户是什么状态 |
| **交易失败** | **返回"原因类别 + 关键数字"**（余额不足差 30 元 / 超日限额剩 2000 元可用）。**"人话"由业务模块组织**——银行给的是事实，不是文案 |
| **风控拦截** | 明确说"这笔被拦下了"，给出原因。**处置动作作为原因文案的素材**，不演多个分支 |
| **结果不明** | 银行给的是**"处理中"**；业务模块等不到答复（超时）时，**拿原编号回查**。**不能说成失败，更不能说成成功** |
| **用户取消** | **银行不提供撤销与退款能力**（D11）：没提交的请求银行没见过；已经到账的要查了才知道，**不退**。**没花完的冻结必须能释放**。统一口径：**"没花的不扣，花了的不退。"** |
| **重复请求** | 同一笔交易重复提交，只扣一次钱；**同编号但金额或收款人变了 → 强制拒绝，报"参数冲突"** |
| **释放与核销** | 花了多少、剩多少、释放回来多少，三项都要能说清 |
| **账户余额变化** | 扣款后**账面、冻结、可用三个数字各是多少**，要能返回——否则业务模块没法向用户解释 |

## 十一、安全与确认考虑

### 银行侧要做哪些检查

- 是不是本人的账户
- 账户能不能用（状态是否正常）
- 钱够不够（**按可用余额算，不是账面余额**）
- 超没超限额
- 收款方是否为涉诈账户

**以上检查全在银行侧执行，业务模块不复刻、不缓存判定结果。**

> **✅ X8 已收口（2026-09-23 Erwin 定案）：涉诈拦截留在银行。**
>
> 预审会上曾讨论"银行只查格式与账户条件、剩余安全判断全归公共安全入口"，**最终定案是银行保留涉诈拦截**——理由是这样与 D12（做模拟风控拦截）、种子数据里的 A7 涉诈黑名单账户、验收例子第 7 条一致。
>
> **最终分工**：**模拟银行查"转账格式是否正确 + 账户条件能否转出 + 收款方是否在涉诈名单上"（怀疑账户与交易）**；**公共安全入口查"越权与诱导"（怀疑人）**。两侧范围不重叠，任一拦下即拦下。上面这一行"收款方是否为涉诈账户"**保留不动**。

### 09-26 结束释放与核验时限补充（Erwin 已确认）

首次冻结时由应用取得“结束时仅释放未消费余额”的限定授权，冻结成功后绑定原冻结编号。完成、取消或安全终止时，确定性收尾先核实在途付款，再释放银行当前未消费余额回原账户；银行继续检查权限、归属、金额与防重复。不得借此付款、退款或继续购买。收尾失败／未知保留待处理；见公共契约 §3.5 和安全与审计字段附件 §3.1。

中风险验证码重发沿用本动作本轮原 code_expires_at，到期前重发也不延长；人脸期限独立且首次启动后固定。任一未通过方法超时即终止，不因重发或迟到成功复活。

### 哪些动作必须用户确认

**动钱之前必须确认。** 而且确认是业务模块的事，不是银行的——银行只负责在收到请求时再检查一遍关键条件。

### 欺诈防范

- 转账前有防骗提示
- 发现可疑交易时，银行可以采取《反电信网络诈骗法》第十八条的四类动作：**核实交易情况、重新核验身份、延迟支付结算、限制或中止有关业务**
- 对老年用户，防骗提示要更直白、默认更谨慎

### 别人来查别人的账

**一律拒绝。** 而且**不告诉对方"这个账户存不存在"**——否则等于泄露了信息。

> **和第 9 章"核验收款人"怎么区分**（两句话容易打架）：核验是**用户为本人发起的转账**服务的，**只返回"户名是否匹配 + 打码姓名"，不返回任何其他账户信息**；"查别人账户"则是**用户想查与本人无关的账户**——那种一律拒绝，连存在与否都不说。

### 适老化

- 提示用日常语言，不用银行术语
- 金额、收款人、账户尾号、时间要看得清
- 防骗话术更直白

## 十二、简单业务流程图

```
业务模块（转账 / 账单 / 联动）
        |
        | ① 先查、先验、先算
        |   · 核验收款人（户名对不对）
        |   · 查限额余量（今天还能转多少）
        |   · 试算费用与到账时间
        v
   银行检查 ──不通过──> 说清原因
        |                （钱不够差多少 / 超了哪项限额 / 账户什么状态
        |                 / 收款方涉诈被拦下）
        | 通过
        v
 ② 业务模块拿完整方案找用户确认
        ↑ 这一步在业务模块里，不在银行
        |
        v
 ③ 提交交易（带调用方操作编号）
        |
        v
   银行执行 ──> 成功 / 失败 / 处理中
                    |
                    |  没等到答复（首次提交超时 4 秒）
                    v
        业务侧进入"结果未知"
                    |
                    v
        每 3 秒拿原编号回查，最多 10 秒
                    |
          ┌─────────┴─────────┐
       查到了               10 秒仍未确认
          |                      |
    按真实结果回报         转"需要关注"，
                       如实告知，绝不重发
```

**图里要能一眼看出两件事**：
1. 银行只管"查条件、办事、给真实结果"；**中间"找用户确认"那一步是业务模块干的**。
2. **"结果未知"不是银行给的**——银行只说成功/失败/处理中；**是业务模块没等到答复才进入"结果未知"，再拿原编号回查**。

### 13.1 验收例子

|---|---|---|---|---|
| **D03** | 跨行收不收手续费、收多少、**从哪扣**（另扣还是从转账金额里扣）；行内/跨行与到账方式怎么搭；跨行实时延迟几秒 | **梁爽（转账）** | 转账确认单、余额校验（够不够"金额+手续费"）、回执 | **一律不收手续费（恒为 0）**，不做收费场景、不做收费开关（答辩口径："手机银行免手续费是行业常态，本 demo 按常态演示"）；**不模拟行内与跨行差异**：行内、跨行**都是即时到账，没有任何人为延迟** |
| **D06** | **流水口径**：冻结/扣款/释放各算不算一条流水、各带什么标签；退款怎么冲减；**06 扣款的分类落在七类字典的哪一类** | **六水（账单）+ 梁爽（转账）+ 周恩宇（06）** | 账单的消费统计、两边口径一致 | **冻结（占用）和释放（解冻）不计入消费流水**，也不计入任何消费统计，但系统里要**留痕可查**（"资金冻结 / 资金解冻"事件，**不算花钱**）；**只有"从冻结里扣款"才生成一条真正的消费流水**——带**商户名 + 用途**、**交易分类**、**方向=流出**。**释放出来的钱绝不能记成"退款"或"收入"**（否则账单凭空多一笔收入）。**退款口径与 02 账单 PRD 一致，直接转正**：退款是**带"退款"性质的正向入账单列**，**类别继承原消费**，账单汇总时自行抵扣（七类字典里没有"退款"，靠"交易性质"字段区分）。**06 扣款分类必须从七类里选：买花 → 购物，买蛋糕 → 餐饮** |
| **D10** | 资金预留用冻结还是别的机制 | **周恩宇（06）** | 06 全部资金步骤 | **冻结 + 分笔核销 + 差额释放**：06 先冻结一笔预算（如 500），按实际花费**分笔核销**（如 350），办完把**差额释放**回可用余额（150）。**06 直接按冻结能力调用**。**"冻结能释放"不等于"已付款能退款"**（见 D11），两个回执不许写得互相矛盾 |
| **D11** | 给不给取消 / 退款能力 | **周恩宇（06）+ Ringo（安全）** | **定了 06 的回执文案要跟着改** | 银行**不提供撤销与退款能力**：钱已经付给商户的**不退**（真实银行到账后本来就不能单方面撤销，这是正确答法）；但**钱还没花出去、只是被冻结占着的必须能释放**——那是用户自己的钱。统一口径（**建议写进回执**）：**"没花的不扣，花了的不退。"** **06 的回执严禁承诺退款** |
| **D15** | 非实时到账在演示里怎么推进 | **梁爽（转账）** | 转账回执状态机、06 回执文案 | **本轮不做非实时到账**（不提供"次日到账 / 普通到账"）：主线和确认单里**到账方式只有"实时"一种取值**。服务于非实时演示的**"时间快进"开关保留能力——09-24 起为定时转账演示启用**（推进预约到点与自然日限额重置，见"初始化与演示支撑"）；**非实时到账仍不启用**（若后续恢复非实时再用于次日到账推进） |
| **D09-b** | **首次提交划转后，业务模块等多久算超时** | **梁爽（转账）** | 决定两档慢开关能不能演出效果；和 D09（回查 3 秒 / 上限 10 秒）合起来才是完整的超时语义 | **4 秒**：业务模块**首次提交划转后等 4 秒**没答复即视为超时，进入"结果未知"→ 按原编号回查（回查规则见 D09：每 3 秒一次、最多 10 秒）。**必须小于 6 秒**（"故意慢一次"的 6 秒档），否则走不到"回查"。**演示超时只用 6 秒档**（4 秒超时 → 回查 1 次成功，总共约 7 秒）；**不要用"超 10 秒档"**，那档最坏要等 14 秒，只在截图 / 说明里用 |

#### 查不到权威出处、属于我们的设计选择

| 项 | 说明 |
|---|---|
| 户名打码的格式（保留几位、几个星号） | 监管只要求"应当脱敏"，未规定格式 |
| 超时后回查的间隔与最长等待（3 秒 / 10 秒） | 行业无公开标准 |
| Ⅰ类户的具体限额（单笔 5 万 / 日 5 万） | 监管未设统一上限，各行自定 |
| 柜面渠道限额 | 公开渠道查不到，且演示用不到 |
| 日限额按自然日重置；Ⅰ类户没有年限额，"查今年还剩多少"对它返回"不适用" | 行业口径不一，我们自行约定 |

#### 刻意不做（范围纪律）

真实银行有、但演示走不到：**跨行退票、清算时间窗口与日终维护、认证方式分级限额、睡眠户等扩展账户状态、卡片自主锁卡、理财持仓展示、代扣协议细则。**

这些是**范围选择，不是能力缺失**。答辩口径：本项目是端到端实时演示，为保障链路稳定性与聚焦核心交互，上述非关键路径做**环境假设豁免**（默认清算全天候、默认无介质差异、默认无退票）。以后真扩到卡片/理财/订阅场景时再回来补。
