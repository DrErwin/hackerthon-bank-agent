## 二、开场口径（会上讲的框架，非决议，记录备查）

| 讲了什么 | 会上原话要点 |
|---|---|
| **管理方式** | 不做"两三个人开发、其他人打杂"的分工；每个人有自己的活，PM 建系统化的流程管控（"有点大厂味儿在"）。 |
| **技术框架** | 后端服务入口 → Agent 平台（AI + harness）→ 业务模块。选 **LangGraph**，理由是"业务跟随能力强"，银行流程需要按预先定义的图走，不能像编程型 agent 那样自由发挥。 |
| **06 的特殊性** | 跨场景没有固定业务流程，**子节点（确认 / 转账 / 购买 / 取消）由 AI 从可选项里编排**；框架的核心 trade-off = **AI 的自由度 vs 安全合规**。 |
| **安全底座怎么落地** | 安全先等业务回填表；业务把流程与异常给 Ringo → Ringo 出功能清单。**以后业务改了涉及安全的流程，必须主动把最新文档给 Ringo**；PM 建变更通知机制。 |
| **前端形态** | 最简单的一套界面：chat history + 聊天框 + 语音键；AI 用**卡片 / 表格 / 带图选项**跟老人交互，关键动作让用户**再点一次确认**。负责人后续由 Erwin 派活并出需求整理。 |
| **模块间协作** | 每个模块**自己维护一份"我能提供什么 / 我需要什么"的清单**（即 API 文档），别人直接来拿。这就是 01 §3.2 / 02 §3.1 那两张表的意义。 |
| **飞书** | 本地 `docs/` 同步到飞书知识库；梁爽本次尚未进群，会后再拉。 |

> 会上确认的一条通用规则：**业务模块只暴露能力边界，流程内的异常由各业务自己定**——"银行给你什么、别的模块能给你什么，中间怎么走你自己确定"，目的是"没有歧义、没有粘连"。
