**v0.4 从"纵向打通"转到"横向铺开"：纵向链路已完成（模型对话 → 前端展示 → 业务图逐段执行 → 结果回前端），本阶段把前端做成完整流程、把业务线从"只有转账"扩到账单与多场景。** 前端（梁爽主责、六水协助）与账单（周恩宇）继续推进，安全底座（Ringo）补上安全审查，Erwin 自己另开一条新业务线并负责联调与契约审查。协作仍走**公共 API 契约池 + GitHub Issue（必须写明转给谁）**。目标：**本阶段最晚 10-20 全部结束验收**（前端只要搭好框架、转账 + 账单两条交互走通，不求精美）；10-20 → 11-02 约 12 天打磨体验、补全剩余功能、做跨场景；**11-02 正式提交**。Erwin 每两天问一次进度（约 4 次），完不成由他用 AI 兜底。

## 五、协作机制（会上重申）

1. **公共 API 契约池**（原话"契约 / api 池子"）是各模块接起来的唯一方式，两个方向都走它：
   - 业务线需要新的安全能力 → 写个单子给安全侧，安全侧加进 api 池；
   - 前端需要新卡片 / 新字段（如账单信息卡）→ 申请新 api，**Erwin 审查后**后端加 api，前端再向后端取。
2. **GitHub Issue 是跨人协作与审批通道**：完成待审批、缺契约、功能缺失、bug 都开 issue；**issue 必须写明转给谁**（责任人）。Erwin 会答复并补契约。
3. 这套流程写在 **agents 的 md**（`AGENTS.md` 与 `docs/agents/`）里，"大家的 ai 看到都知道该走这个流程"；私下聊也行。
4. **时间吻合的落地证据**：本次会前 `20:00:05` 的提交 `86620ac`「docs: GitHub Issue 建单必须写明转给谁」，对应会上"我刚刚还更新了一下我们的说明文档"。

## 六、演示暴露的体验问题（前端待办，会上明说不管）

- 左侧历史对话全叫"新对话"、列表一路往下堆，没有命名与收拢。
- 卡片一张张叠起来、上一张卡片不消失（含失败与重开流程时）。
- 模型回复慢（"只是随便玩一玩"的简易前端）。

Erwin 的态度：这些"挺垃圾"的体验问题**由前端自己跑一遍就会改掉**，不在他本阶段范围内；本阶段前端只求流程走通。
