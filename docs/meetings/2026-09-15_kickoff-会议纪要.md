## 二、评分规则（满分 100，决定精力投放）

| 权重 | 维度 | 考察内容 |
|---|---|---|
| 40% | 任务完成率 | 场景完成情况、多步骤任务规划合理性、工具调用正确性 |
| 30% | 安全合规性 | 诱导转账、信息套取、越权、Prompt 注入的防御；敏感操作确认与风险提示 |
| 30% | 创新性及交互体验 | 场景新颖性、真实问题解决度、对话轮次效率、追问、错误恢复、口语化输入、超范围兜底 |

**划重点**：
- 评审看的不只是"任务成没成"，更看**每一步规划是否合理、工具调得对不对**。
- 任务 + 安全 = **70%**，创新只占 30%。别把力气都堆在花哨体验上。
- 安全里 **prompt 注入**是重点盯的对象；创新里"追问、错误恢复、超范围兜底"这些对话质量项同样占分。

## 三、已定决策

1. 场景只做 **1 / 2 / 6** 三个（先做完，时间充裕再扩到 6）。
2. 用户群体走**适老化（银发经济）**——但只改前端交互，后端业务流程不变。
3. **不接真实银行 API**，自己 mock 一套模拟银行。
4. **用数据验证产品**：预先造测试数据集（input + expectation）。

## 五、技术架构

```
用户 ↔ AI agent ↔ harness（运行环境）↔ 工具 ↔ 模拟银行（mock bank）
                     ↕
          独立 Security 关闸（校验每个操作合法性 + 转账合规性）
```

- 不接真实银行 API，自己造一套银行对外接口。
- Security 是独立体系，管 AI 每步操作合法性，敏感操作（转账等）银行也要与它对一次。

## 七、PRD 要覆盖什么（三重点）

1. **业务流程**：主办方没给文档，全靠自己查 + 跟 AI 聊，把正常流程走通。
2. **边界/异常情况**：永远假设用户不按流程走，提前想好 AI 怎么兜底（如余额不足）。**最容易被漏。**
3. **本场景安全合规**：自己场景特有的合规点（整体合规由 ringo 另做）。

## 八、开发路线

PRD → UX PRD + 技术架构 + schema（API 接口定义）→ 开发 + test case → 正式测试

> 造测试数据集是验证关键：先定义 input（用户怎么说）+ expectation（系统该回什么），再验证结果对不对、步骤合不合理；还要造异常数据测 Security 是否拦截（刷单、恶意欺骗、余额不足）。
