# 全系统模块清单

本清单配合 [全系统模块总览图](system-overview.html)，用于确认整套产品的模块边界和团队接口。这里的“模块”是职责划分，不要求独立部署。所有模块均为规划或设计，本文不宣称已实现。

范围依据：9 月 15 日启动会议与现有 Roadmap 提供产品范围；v0.5 提供最新技术机制；场景 PRD 交付规范提供模块间交接要求。旧文档中的 AgentKernel、自建编排和 Zod 等实现口径不沿用，按 v0.5 的 Deep Agents、LangGraph、Pydantic 处理。

## 模块与子模块

| 系统模块 | 包含哪些子模块 / 能力 | 负责什么、交给谁 | 范围状态 |
|---|---|---|---|
| 用户交互前端 | 对话输入、信息补充、计划与进度、敏感确认、结果展示、任务续办、适老化交互 | 展示后端允许公开的信息；用户的补充和决定提交应用后端 | 核心；语音输入仍待确认 |
| 应用后端 | 登录身份上下文、会话管理、任务归属、开始/补充/查询/取消/恢复入口、HTTP 与 SSE | 核对身份和任务归属，接入安全策略，连接前端与 Agent | 核心；不预设具体登录供应商 |
| Agent 底座 | 统一 Harness、流程运行、模型适配、上下文与记忆管理、暂停恢复、预算约束 | 理解需求并选择能力；公共运行机制由底座复用 | 核心；细节见 Agent 内部图 |
| 能力与工具接入 | 公开能力目录、模块私有工具目录、模块清单、公共数据契约、调用适配、接入检查 | 把业务模块接入底座；明确输入、输出、事件、错误和权限声明 | 核心；使用显式注册，不做动态插件安装 |
| 智能转账模块 | 转账任务的信息收集、业务步骤、确认请求、结果解释和异常分支 | 组织“用户要转账”的任务；查询及实际转账由受控工具调用模拟银行 | 核心；具体任务、额度、预约等由场景 PRD 定义 |
| 账单分析模块 | 账单数据获取、整理分析、结果说明与交互 | 从受控接口取得流水等事实，给用户可解释的分析 | 核心；具体报表与分析口径待 PRD |
| 跨场景联动模块 | 复合意图拆解、调用其他公开能力、组合进度及结果 | 串联已接入业务模块；不直接访问其他模块的私有工具或数据库表 | 核心；具体联动剧本待 PRD |
| 理财操作模块 | 理财场景的业务能力包 | 沿用同一契约、安全入口和模拟依赖接入 | 后续范围；未冻结细节 |
| 卡片管理模块 | 卡片场景的业务能力包 | 同上 | 后续范围；未冻结细节 |
| 订阅 / 代扣模块 | 订阅与代扣场景的业务能力包 | 同上；周期授权与触发条件不能自行默认 | 后续范围；未冻结细节 |
| 安全底座 | 身份与数据范围授权、模块准入、工具逐次鉴权、参数与状态校验、敏感确认、注入内容隔离、隐私脱敏、受控记忆策略 | 给 API、Agent、工具和银行服务提供共同规则；程序决定放行或拒绝，模型不能改规则 | 核心；独立职责，不要求独立网络服务 |
| 模拟银行 Mock Bank | 模拟账户与业务数据、收款人查询、模拟交易执行、流水与结果查询、业务条件校验、操作去重与事务 | 提供可核实的银行事实与实际模拟操作结果；与安全底座核对敏感动作 | 已决定自建、不接真实银行 API；具体接口和业务规则待 Mock Bank PRD |
| 审计与证据回放 | 全链路事件采集、父子调用关联、历史时间线、证据访问、脱敏导出、缺口标注 | 开发者与获授权第三方检查已发生的过程；第三方默认拿授权证据包 | 核心；与任务恢复分别授权 |
| 数据与运行持久化 | 应用业务数据、会话任务索引、确认和操作记录、运行检查点、用户记忆、审计事件与受控证据 | 为各模块提供持久化支撑；数据职责与访问范围独立 | 核心；SQLite/SQLModel 起步，具体记忆后端待验证 |
| 评测与演示支撑 | 业务用例、安全攻击用例、契约检查、端到端验收、中断恢复测试、模拟数据与演示剧本 | 在隔离模拟环境中验证整个系统，检查 Mock Bank 实际状态和审计证据 | 核心工程支撑；不是用户生产请求中的一个步骤 |

外部模型供应商是系统依赖，不是自建业务模块。模型调用都经底座统一入口；具体供应商与版本由配置和兼容验证确定。

模拟银行的上述拆分是现有转账、账单及框架恢复要求下的职责整理，不等于已冻结全部业务接口。卡片、理财、订阅所需的模拟能力随对应业务 PRD 补充，不宣称模拟银行已覆盖真实银行全部能力。

## 最关键的四条交接

1. **前端 → 应用后端**：提交用户需求、补充信息和明确确认，接收进度与真实结果。确认、登录身份验证和安全放行是三件不同的事。
2. **Agent → 业务模块**：通过登记的公开能力与统一契约交接；主 Agent 不需要掌握每个场景的全部私有工具。
3. **业务模块 → 安全底座 → 模拟银行**：业务模块组织流程，安全底座决定允许哪些动作，模拟银行执行并保存业务事实。模拟银行入口再次检查关键授权和业务条件。
4. **运行模块 → 数据与审计支撑**：各层保存各自状态并上报事件；恢复核对检查点和操作记录，审计只读历史、不发起业务执行。

图中把安全底座放在银行操作主线上，突出不可绕过的执行检查；它还横向服务 API、数据隔离、模型输入输出与记忆写入。存储与审计同样是全系统共用能力，为保持清晰，部分横向依赖写在说明卡而非画满连线。

- [启动会议纪要](../../meetings/2026-09-15_kickoff-会议纪要.md)：第三节确定自建 Mock Bank、不接真实银行；第五节明确独立 Security 关闸；第四节给出六个业务场景。
- [Roadmap](../../ROADMAP.md)：三个核心场景、后续扩展、契约与工具注册、统一安全执行器、模拟银行、业务与安全评测的建设安排。技术实现冲突以 v0.5 为准。
- [系统框架 v0.5](../system-framework-v0.5.md)：模块化后端、公共契约、安全边界、记忆状态、恢复和审计机制。
- [场景 PRD 完整参考清单](../../场景PRD完整参考清单.md)：场景、模拟银行、安全及公共底座之间的交接内容与负责人角色；本轮初稿按 [初步 PRD 交付要求](../../初步PRD交付要求.md) 填写。

评审时先确认模块职责与交接，再由各 PRD 补齐业务细则；不要把这张总览当作数据库表设计或生产部署拓扑。
