本图依据 [系统框架 v0.5](../system-framework-v0.5.md) 第一部分绘制，供团队技术评审使用。图中的主链路是：用户前端 → 后端服务入口 → Agent 平台 → 业务能力模块 → 银行系统接入层 → 银行系统（首版为团队自建模拟银行）。

第七部分「数据与运行记录」按归属画成两个框：应用侧记录任务、记忆、检查点、工具调用与审计；银行侧记录账户、账本与银行操作结果。银行通过接入层返回实际状态和结果，应用侧不能直接读写银行的数据表。

双向箭头表示用户确认回环：业务处理需要澄清或敏感确认时，原任务暂停，进度与确认请求经服务入口返回前端；用户回答后继续原任务。红色虚线框表示安全与权限约束贯穿模块化后端，不代表额外部署一个服务。身份、工具执行、银行账户操作和数据访问分别在所属边界检查。

这是一张职责与调用关系图，不表示各框都要独立部署。首版是一个模块化 Python 后端；图中的模拟银行有独立的逻辑与数据边界。模型供应商配置、Agent 内部工具和审计查询界面不在本总览展开。设计尚未完成代码实现与运行验证。

旧的 [v0.4 五模块图](../review-v0.4/system-overview.html) 保留为历史评审材料。其 Agent 内部图与转账交互时序图也仍在 [v0.4 图包](../review-v0.4/README.md)，不能代替本图的 v0.5 系统总览。

模拟转账交互图以一个已选收款人、金额 100 元的例子展示时间顺序。用户在前端发起，业务模块申请确认后原任务暂停；用户确认由后端校验，随后沿原任务继续。敏感工具经统一安全执行入口检查，再由银行接入层把可信身份和原操作编号交给模拟银行。银行返回的实际状态沿原调用链展示给用户。图中省略机械性的逐层回包，但不省略银行接入层或银行侧授权边界；金额只是说明用例，不定义额度规则。此图同样是设计稿，未运行验证。
