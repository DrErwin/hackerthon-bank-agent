# 跨团队纵向交付与版本进度原则

适用于同时涉及两个以上归属目录的纵向场景、公共框架能力和阶段性里程碑。

## 1. 四个事实源

| 内容 | 唯一位置 | 回答的问题 |
|---|---|---|
| 里程碑范围与完成证据 | `docs/versions/vX.Y.Z/` | 这个阶段要做什么，实际完成了什么 |
| 正式负责人、排期与状态 | `docs/01-项目跟踪.md` 与飞书进度表 | 谁在什么时候开始，现在处于什么状态 |
| 当前工程规格、交付包和任务票 | `.scratch/` | 这次具体怎样拆、验收什么 |
| 实际实现与验证 | 代码、测试和评测结果 | 功能是否真的完成 |

任务文件本身不会通知负责人，也不代表已经开工。场景负责人先登记正式分派与开始条件；队员明确接受后，AI 必须在同一任务把接受人、日期和工作线写入交付包及项目跟踪。完整开工流程与 Skill 清单见[队员开工规范](../agents/delivery-workflow.md)。

## 2. 两级拆分

跨团队场景采用两级拆分：

1. **场景负责人拆交付包**：确定业务目标、参与工作线、输入输出、开始条件和联合验收，不替其他负责人决定其内部代码任务。
2. **目录负责人拆实施票**：接受交付包后，在 `.scratch/` 为自己负责的目录创建详细规格和任务票；一张票只修改一个目录。

交付包与各负责人工作组的标识、组内编号、跨组引用和依赖统一按[票据标识规范](../agents/issue-tracker.md)。项目跟踪登记完整交付包标识及工作组 spec 链接；实施票关联原包，对外使用完整票号、标题和链接，负责人变更保持标识稳定。

场景负责人维护纵向结果，目录负责人维护本目录实现。纵向结果失败时回到归属目录修复，不由集成人员长期接管他人代码后再“交还”。

同一个人在某个里程碑内可以临时承担多个目录，但必须在版本文档和项目跟踪中写明期限、审查人及交还点；实施票、分支和 PR 仍按单一目录拆分。临时执行人不自动成为长期目录负责人。

## 3. 标准流程

### 第一步：确定版本

在 `docs/versions/vX.Y.Z/requirements.md` 写清当前里程碑的目标、范围、验收和不做什么；同时创建 `completion.md`，如实标记尚未开始、进行中或已完成。

完成条件：版本索引能说明当前里程碑和上一阶段留下的启动条件。

### 第二步：确认场景规格

在 `.scratch/<scenario>/spec.md` 写当前场景的业务结果和联合验收。规格引用 PRD、架构与公共契约，不复制公共字段。

拆票前先明确核心验收场景和完整测试的覆盖框架，作为各工作线共同的验收依据：

- 核心场景使用稳定编号，写清用户目标、前置条件、自然表达或操作步骤、预期结果，以及不能发生的行为；一条业务主线可以有多个核心场景。
- 核心场景至少覆盖适用的正常完成、缺信息后补齐、取消、验证或权限拒绝、中断或结果不明确后的恢复。动钱场景必须明确确认要求与不得重复提交的底线；不适用的类别说明原因。
- 完整测试先列覆盖类别，例如不同表达、字段边界、修改、异常、恢复及安全专项；具体用例随开发逐步补齐，不等阶段结束才设计。
- 核心场景及覆盖框架放在场景 spec；具体评测用例与证据放在 `evals/<业务线>/`，程序内部测试留在对应代码目录。版本 `completion.md` 记录验收状态与证据链接，不复制另一套用例。

完成条件：核心场景可检查、覆盖框架明确，不存在需要实现人员自行猜测的业务选择。核心场景与完整测试只覆盖当前里程碑，未来需求留在版本范围文档。

### 第三步：划分交付包

在 `.scratch/<scenario>/packages/` 按工作线建立交付包。每个交付包至少写明：

- Owner 与正式激活方式；
- Start when；
- 业务目标与交付范围；
- 向其他工作线提供什么；
- 可检查的验收标准；
- 负责人接受后怎样拆自己的票。
- 接受记录字段：`Accepted by`、`Accepted at`、`Work spec`；多人包按人和工作线分别记录。未有本人接受证据时写“未记录”，不以 Owner 或 Activation 代替接受记录。

完成条件：每个跨目录依赖都有提供方和开始信号，没有把实现细节强塞给其他负责人。

### 第四步：正式激活

场景负责人在 `docs/01-项目跟踪.md` 登记负责人、时间与开始条件，并把规格与交付包链接发给对应负责人；飞书按人决定的时间同步。负责人明确接受后，AI 自动记录领取。开始条件满足的包可以拆票，尚有依赖的包保留 `blocked` 并写明提供方。队员仅报身份或咨询下一步时，AI 应定位可接包并引导确认领取，不能代替本人接受。

完成条件：负责人知道自己何时开始、交付什么、依赖谁，不依赖自行发现 `.scratch/` 文件。

### 第五步：负责人拆票并实现

领取记录写好后，AI 先检查通用 `to-spec`、`to-tickets`、`implement`、`code-review` Skill，按[开工规范](../agents/delivery-workflow.md)安装本轮需要但缺失的项。目录负责人按 `to-spec → to-tickets → 按票执行` 推进：规格和票保存在本人的 `.scratch/`，开发票使用 `implement`，非代码票按交付物验收。已有规格和票直接续做，不重复生成。

拆票、分支和 PR 遵守单目录边界，公共依赖未就绪时可以在自己的目录使用符合冻结契约的 stub 验证，不复制公共实现。每票完成后补票据链接、实际开始日期、证据与项目跟踪状态。

每张实施票引用其支撑的核心场景编号，写清本票验证要求；局部功能票按自身验收完成，不要求尚未具备的整条路径通过。拆票时明确安排联调验收票及阶段全面评测票，引用场景 spec 并列出完整依赖；已有对应票时直接补充，不重复建票。

一条核心路径所需的能力就绪后，立即从真实页面联调，不等所有功能完成。正常路径先贯通，取消、拒绝和恢复等路径具备条件后再逐步验收。联调票负责验证与记录，发现的缺陷回到归属目录修复，不能借联调票跨目录改代码。

每次实现或修复先验证本票，再检查受影响的核心路径；真实缺陷修复后保留能复现该问题的回归用例。临时替代验证与真实模型、HTTP、页面联调分别记录，不能互相替代。

完成条件：每张票有单一目录、关联核心场景、验收标准和必要依赖，联调责任明确，完成状态由实际测试决定。

### 第六步：联合验收与版本收口

场景负责人按场景规格进行端到端验收。阶段完成后先更新该版本的 `completion.md`，记录实际完成、验证证据、差异、遗留和下一步；再把下一版本改为进行中并激活对应交付包。

阶段验收先检查核心路径；未通过时先修复并复验相关路径，再进入完整覆盖。核心通过后执行当前范围的完整业务用例、真实体验走查及所需专项检查。体验走查使用自然表达与真实页面，核对聊天、操作卡片和实际结果是否一致。

完成条件：完成情况有证据，不把文档、占位接口或单模块测试当作端到端完成。核心通过只表示核心路径可用；完整业务验收、真实体验和专业安全审查分别记录，不能以其中一项替代阶段验收。无法执行的检查明确记为阻塞，并说明缺少的条件。

## 4. 状态与开始信号

版本状态只使用：已完成、进行中、计划中、暂缓、已取消。

交付包至少区分：

- `planned`：已确定范围，尚未正式通知或未到开始时间；
- `blocked`：负责人已知晓，但明确依赖未满足；
- `ready`：开始条件满足，负责人确认领取后可以拆票；
- `in_progress`：已记录本人接受，开始写规格、拆票或执行；
- `accepted`：联合验收已接受，不能用来表示刚领取。

状态变化必须同步到正式项目跟踪入口；`.scratch` 中的状态用于工程上下文，不能替代团队任务表。

## 5. 版本文档边界

- `docs/versions/` 的版本号是需求里程碑号，不是软件包发布版本。
- PRD、架构、契约等长期事实文档继续使用当前日期命名，不复制进版本目录。
- `requirements.md` 只写该阶段的目标与范围，并链接长期事实文档。
- `completion.md` 只写实际结果和证据；未验证时明确写未验证。
- 当前阶段的详细规格和任务留在 `.scratch/`，未来需求留在后续版本文档，不提前拆成实施票。

## 6. v0.3 转账纵向场景（已收口）

v0.3 场景采用五个交付包：v0.3 纵向后端主链路、v0.3 最小前端、v0.3 评测与专业审查、后续业务评测准备、纵向集成验收。各包的详细范围见 `.scratch/transfer-agent-framework/packages/`。该场景已于 2026-10-11 收口（含明示例外）；v0.3 期间由 Erwin 临时实现底座、最小安全门和普通转账参考路径并承担转账评测及审查（2026-09-28 全员会定），Ringo 负责安全评测及审查，长期目录归属不变，收口后维护回到长期负责人。当前版本的交付包与领取状态以[项目跟踪](../01-项目跟踪.md)为正式入口（v0.4：`v04-bills/`、`v04-security/`、`frontend-complete/`）。
