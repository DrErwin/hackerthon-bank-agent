# 安全底座开发原则

适用对象：ringo（安全合规负责人），以及任何改动 `security/`、统一工具执行器、权限、确认、审计、记忆隔离的人。
安全不是一个业务模块，而是贯穿前端之外整条链路的公共约束。

> 技术背景：安全落点在 Python 后端 `backend/app/security/` 与 `backend/app/memory/`。前端只展示和收集，不做权限判定。

## 1. 安全的职责范围

安全底座负责：

- 统一工具执行器：每次工具调用校验身份范围、权限、参数、确认状态。
- 模块与工具准入：未声明权限或副作用的工具拒绝注册。
- 确认门：敏感操作与具体调用、参数绑定。
- 用户 / 会话 / 任务隔离，记忆与数据不得串用户。
- 审计事件：调用链、判定、确认、拒绝、恢复；只追加、只读查询。
- 与银行侧对账的安全配合：操作编号、重复执行防护、结果以银行返回为准。

安全底座不负责：

- 编写具体业务 SOP（转账步骤、账单分析逻辑、跨场景编排）。
- 在业务模块里复刻银行限额、余额、风控规则。
- 替代模拟银行做交易是否成功的最终判定。

## 2. 四条不可破的落点

1. 后端入口：核验登录身份、会话归属、任务归属、恢复请求。
2. 统一执行器：外层模块获准 ≠ 内部每次工具放行。
3. 数据层：用户与任务隔离；恢复重放不得重复产生副作用。
4. 前端只展示和收集，不做权限判定。

任何 PR 若让模型、业务模块或前端直接改授权规则，一律拒绝。

## 3. 分支与改动策略

- 分支命名：`feat/security/<topic>` 或 `fix/security/<topic>`。
- 安全 PR 必须小：一次只改一类策略（确认、权限枚举、审计字段、执行器拦截点）。
- 安全变更窗口优先于业务合入。策略合进 `main` 后，业务分支必须 rebase 再合。
- 禁止在安全 PR 中夹带业务功能；禁止在业务 PR 中悄悄放宽拦截。
- 破坏性策略（新增必确认动作、收紧权限）必须提前在群里通知，并说明受影响模块。

## 4. 设计原则

- 默认拒绝：未声明、未登记、越权、参数与批准不一致，一律拦截。
- 确认绑定参数：金额、账户、工具名任一变化即失效，需重新确认。
- Prompt 注入防御是评分重点：工具结果、用户输入、外部文本不得写成系统规则或长期记忆指令。
- 模型只能提出候选动作；是否执行由代码与记录决定。
- 局部 Agent、子流程、私有工具必须走同一执行器，不允许模块自行 new 一个不受管的 Agent。
- 审计与任务恢复分离：审计入口只读，不得调用模型或业务工具。
- 写操作先记「开始 / 授权」，记录失败则停止动作。
- 同一动作的重试与恢复使用同一操作编号；业务参数变了就是新动作。

## 5. 对业务模块的审查口径

ringo 在业务 PR 中至少检查：

- 私有工具是否登记权限、副作用、确认策略。
- 转账等动钱路径是否经过确认回环，而不是对话里口头同意。
- 是否试图用换工具、换模块、换 Agent 绕过拒绝。
- 是否把银行规则写进 Agent 侧。
- 异常与超范围输入是否停止或澄清，而不是继续猜。
- 测试是否覆盖权限拒绝、诱导转账 / 套取信息类输入（可用脱敏样例）。

业务缺声明时打回，不在安全仓库里替他们补业务流程。

## 6. PR 最低交付

- 策略变更说明：谁被拦截、谁被放行、是否破坏兼容。
- 对应测试：放行用例、拒绝用例、确认后参数被改用例、越权调用用例。
- 审计是否能看到本次判定（允许 / 拒绝 / 确认）。
- 若影响公共契约字段，必须与 Erwin 的契约 PR 拆开或明确联立，且契约先合。

## 7. 与评分的关系

官方评审三维度（见 `官方资料/参赛规则与提交要求.md` §四）：

| 权重 | 维度 | 安全底座的对应 |
|---|---|---|
| 40% | 任务完成率 | 安全执行器不拦正常流程，多步骤任务可合理完成 |
| 30% | 安全合规性 | 本文件核心：诱导转账、信息套取、越权、Prompt 注入可拦截或降级 |
| 30% | 创新性及交互体验 | 与前端 / 适老化交互相关，**前端 owner 待定**，安全只约束其不做权限判定 |

安全合规占总分 30%，与任务完成率合计 70%。优先保证：

- 诱导转账、信息套取、越权、Prompt 注入可拦截或降级。
- 敏感操作有确认与风险提示。
- 拒绝原因可审计，不靠事后用模型编造解释。
