# 代码 Review 与合并原则

适用对象：Erwin（架构、底座、最终合入），以及所有提交 PR 的人。

**当前状态：私有 GitHub 远端已建立，自动检查已启用。** 团队约定只通过 PR 合入 `main`；当前 GitHub 账号方案不支持对这个私有仓库强制启用分支保护，故直推与检查门槛暂时只能靠协作约定。限制与待办见 [Git 与提交约定](../agents/git-workflow.md)。

> 目录基线见 [系统框架（2026-09-19）](../architecture/system-framework-2026-09-19.md) §9 的 `backend/app/` 建议结构。
> 各目录负责人见 `AGENTS.md`；前端由梁爽负责、六水协助。公共契约 v1 已冻结，变更按[契约第 8 章](../contracts/公共契约-2026-09-23.md#8-变更管理防拉通机制④)处理。

## 先读：一次功能从提出到合入

1. 负责人把功能拆成一个可演示、可测试的小项，写清目录、依赖、验收用例；AI 开工前读取 `AGENTS.md`、本文件及所属目录的原则。
2. 从最新 `main` 开分支，仅改自己负责的目录；需要公共能力时先走[公共改动流程](#公共底座与-api-改动)，由公共目录负责人处理。
3. 在自有目录完成实现、文档和测试，提交一个 PR；PR 未合时按[业务并行原则 §2](01-business-parallel.md#2-分支与并行)决定下一项能走多远。
4. 作者处理审查意见并同步最新 `main`；目录负责人和必要的安全负责人审查，Erwin 按 §2 的依赖顺序合入。
5. 合入后作者清理分支，受影响的负责人同步 `main` 并验证自己的调用。完成标准：主线测试通过，PR 依赖已闭合，文档与实际接口一致。

## 1. 仓库与分支总则

- 全员同一个私有 GitHub 仓库，`main` 始终可运行已合入模块的测试。
- 合入方式团队统一为 squash merge（主线每个 PR 一条记录）。
- 独立 PR 的作者在合入前保持 `rebase origin/main`；依赖未合 PR 的后继 Draft PR 先以其前序分支为目标，前序合入后再由 Erwin 协助更新到 `main`。冲突在功能分支解决，不在 `main` 上手工拼接。
- 推送已 rebase 的功能分支使用 `git push --force-with-lease`，禁止无 lease 强推。
- 合入后删除远程功能分支；本地 worktree 重置到最新 `main` 或移除。
- 新手 / 非代码成员 git 卡住时由 Erwin 代操作，不要求独自完成 rebase / force。

> 注意：squash merge 会重写前序分支的提交历史。前序合入后，后继分支须由 Erwin 协助只保留自己的改动，再以最新 `main` 为目标；不能直接把含有前序提交的差异交给合并人。

## 2. 合入顺序（按依赖，不按提交先后）

1. 公共契约 `contracts/`
2. Agent 底座、银行接入层、模拟银行接缝
3. 安全执行器与策略
4. 单业务模块的公开入口与测试
5. 模块内部流程与私有工具
6. 跨场景联动
7. 前端展示与适老化

底座与安全 PR 和业务 PR 同时出现时，先合底座 / 安全。联动 PR 不得早于其依赖的公开能力。

**第一条纵向路径**：v0.3 临时由 Erwin 把底座、最小安全门、转账参考路径和模拟银行接通；梁爽负责最小前端，转账评测与业务审查由 Erwin 承担（2026-09-28 全员会定），Ringo 负责安全评测与安全审查。每张票、分支和 PR 仍只改一个目录。这个可运行样例进入 `main` 后，安全与转账维护回到长期负责人，其他业务线再按注册方式接入完整功能。样例建设期间，各负责人可按冻结契约在自有目录做用例、评测和前端设计，不必等着停工；跨模块联调和依赖样例的 PR 等样例合入后再收口。

## 公共底座与 API 改动

业务 AI 发现现有底座、公共契约或平台 API 不够用时，先核对是**自身实现没有按现行契约做**，还是**契约确实缺能力**。前者在自有目录修复；后者先开问题记录（GitHub 远端建立后用 Issue，建立前用 `.scratch/`），写清：所需场景、现行接口的缺口、拟调整的输入输出、受影响模块、是否改变旧调用，以及能否用现有注册点解决。

- 问题确认后由公共目录负责人修改底座、公共模型和公共 API 文档，单独提 PR；业务作者在自己的 PR 中引用该问题和依赖 PR。业务专属能力放在业务模块注册，不为它改平台内部流程。
- 变更按[公共契约 §8](../contracts/公共契约-2026-09-23.md#8-变更管理防拉通机制④)分档确认；涉及安全规则须 Ringo 审查，涉及银行边界须 Erwin 确认。公共 PR 先合，受影响业务再同步、验证和合入。
- 模块自有的公开能力或工具文档由模块作者随 PR 更新；只改本模块的实现并保持现行 API 语义时，不另开公共变更 Issue。

## 3. Erwin 写代码时的原则

- 先交团队能用的基础设施：契约、模块模板、假银行接入、最小执行器、CI。
- 自己的改动同样走小 PR，不攒「架构大补丁」卡住所有业务线。
- 不替业务写场景 SOP，除非对方明确卡死且已沟通由你顶上。
- 契约是唯一公共来源。变更按[公共契约第 8 章](../contracts/公共契约-2026-09-23.md#8-变更管理防拉通机制④)分档：内部修复走普通审查，兼容扩展由契约负责人轻量确认，不兼容修改由契约负责人和受影响模块负责人协同确认。新增字段或枚举也须判断兼容性；仅通知受影响使用者。开发期可统一切换当前 v1，确需支持旧使用方时再定迁移窗口与新版本。
- 银行规则只存在模拟银行内；接入层只做协议隔离，不塞业务 if-else。
- 公共文件与业务文件不要混在同一个 PR。

## 4. Review 必看清单

通用：

- 目录有没有越界。
- PR 是否只做一件事，测试是否与声明一致。
- 是否从过期分支开出，是否需要先 rebase。
- 有前置 PR 是否标明 `Depends on PR #n`。
- 正文是否按[票据标识规范](../agents/issue-tracker.md)引用完整实施票号、标题及链接；来源问题写 `Issue #n`，依赖交付写 `Depends on PR #n`，编号类别明确。

业务 PR 额外看：

- 是否引用公共契约而非复制。
- 是否直连银行或复制银行规则。
- 敏感操作是否有确认回环。
- 联动是否只调用公开能力。

安全 / 底座 PR 额外看：

- 默认拒绝是否被放宽。
- 执行器是否仍覆盖私有工具与局部 Agent。
- 审计是否可回放本次变更，查看入口是否只读。
- CI 与模块注册门槛是否仍能拦住未声明工具。

## 前端设计与后端接入

梁爽主导前端，六水协助。按以下顺序交付，每步的结果经梁爽确认后进入下一步：

1. **用户调查**：围绕银发用户的对话、确认、看结果等核心任务，记录实际困难和优先级，形成简短需求清单。
2. **体验与视觉规范**：依据调查结果写一页适老化规则，包括文字与按钮、对比度、信息层级、操作反馈、错误提示和敏感确认的展示方式；形成关键页面的视觉方向。
3. **原型**：画出聊天、任务等待、确认 / 验证、结果 / 报告的关键路径，拿原型走查；把发现的问题改进原型。
4. **前端实现**：按确认的原型在 `frontend/` 实现，先用符合冻结契约的假数据跑通交互；前端只展示和收集，不自行决定交易是否可执行。
5. **联调**：Erwin 的纵向样例和相应后端 API 就绪后，按契约接入真实后端，验证正常、等待确认、失败和恢复路径；接口缺口按[公共改动流程](#公共底座与-api-改动)提出。

设计和原型可与后端纵向样例并行，真实后端联调依赖样例和 API 就绪。前端 PR 由梁爽负责范围与体验，涉及确认或验证的交互须 Ringo 审查，Erwin 负责最终集成验收。

## 6. 合并窗口与沟通

- 每天固定 1～2 次合入窗口，窗口外只 review、不合破坏性变更。
- 兼容契约扩展合入后通知相关使用者；不兼容契约或安全策略变化合入前向受影响使用者预告并确认切换时间，合入后通知其同步代码。仅在全员受影响时通知全员，无关模块继续开发。
- 打回时写明原因和下一步：越界 / 缺测试 / 缺声明 / 需拆 PR / 需等依赖。
- 不把「谁先提交谁不用 rebase」当成奖励。后到的人 rebase，先到的人也不许在 main 上抢写。

## 7. 冲突处理

- 只碰业务自有目录：作者自行解决。
- 公共文件冲突：停合，由该文件 owner 决定保留哪边，必要时抽成扩展点后再合。
- 两个业务同时改底座同一处：退回双方，先合接口设计，再各自实现插件。
- 禁止为赶进度在 main 上直接编辑冲突文件后推送。

## 8. 合入后的责任

- 合并人确认 CI 绿、依赖 PR 已合；CODEOWNERS 启用后还须确认对应负责人已批准。
- 合入后冒烟失败：先回滚或立即热修，不继续往 main 堆新功能。
- 每个合入的能力应能在模块测试中独立复现；没有测试的回归不算修完。
