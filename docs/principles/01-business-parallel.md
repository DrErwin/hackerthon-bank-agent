# 业务流线并行开发原则

适用对象：梁爽（转账）、周恩宇（账单、跨场景联动）及后续业务模块负责人。账单自 2026-09-28 全员会起由六水移交周恩宇，六水专注前端协作。
仓库：全员同一个[私有 GitHub 仓库](https://github.com/DrErwin/hackerthon-bank-agent)。每人在自己的分支 / worktree 开发，经 PR 合入 `main`；当前 GitHub 方案暂不能强制保护 `main`，状态见[Git 与提交约定](../agents/git-workflow.md)。
提交信息格式见 [Git 与提交约定](../agents/git-workflow.md)。

> 技术背景：后端为 Python（`backend/app/`，FastAPI + Pydantic），前端 React。业务模块只改
> `backend/app/modules/<module_name>/`。前端目录为 `frontend/`，梁爽负责、六水协助（09-25 确认）；前端改动单独明确目录范围，不在业务模块改动中夹带。

## 1. 你拥有什么，不拥有什么

- 只改自己的模块目录：`backend/app/modules/<module_name>/`。
- 可以新增本模块的公开能力、内部流程、私有工具、模块测试、模块专属输入与内部状态。
- 禁止直接修改：`contracts/`、`agent_platform/`、`security/`、`api/`、银行接入层、模拟银行、其他业务模块。
- 跨场景联动只调用其他模块的公开入口，禁止引用他人私有工具、内部状态或数据表。
- 缺底座能力、公共字段或平台 API 时，按[公共改动流程](03-review-and-merge.md#公共底座与-api-改动)提出问题，由对应目录负责人修改；本模块可以先用符合现行契约的假实现继续验证。

**AI 协作规则**：先判断是实现不符合契约，还是契约需要调整。前者在本模块修复，走普通审查，不另提契约审批；后者列出修改前后、使用方和影响，交契约负责人按[公共契约第 8 章](../contracts/公共契约-2026-09-23.md#8-变更管理防拉通机制④)分档处理。不得为让自己的模块跑通而擅自改公共字段、复制一套契约或放宽安全规则。涉及安全的修复仍须 Ringo 审查。

## 2. 分支与并行

- 从最新 `origin/main` 开短分支，命名：`feat/<module>/<capability>`，例如 `feat/transfer/confirm-intent`。
- 一个分支只做一件可验收的事：一个公开能力，或一组紧密相关的私有工具，或补齐该能力的测试。
- **前一 PR 未合并时**，先判断下一项是否依赖它：
  - 无依赖：从最新 `main` 另开分支或 worktree，继续开发；原 PR 的审查修改留在原分支。
  - 有依赖、但公共契约不变：从前序分支再开一个后继分支，Draft PR 的目标分支设为前序分支并标明 `Depends on #编号`，让前后两项分别可审查；前一 PR 合入前，不再叠第三层功能。
  - 依赖未获确认的公共底座 / API 改动：先提交问题记录；只做本模块内的用例、假实现和原型，不把假设当成已定接口提交可合并 PR。
- 同一人同时未合并 PR 最多 2 个；到上限时先处理审查意见或等前序合入。后继 PR 在前序合入后由作者在 Erwin 协助下更新到最新 `main`，重新跑测试再转为可合并状态。
- **git 卡住时优先找 Erwin 代操作**（rebase / 冲突 / force-with-lease），不要自己硬试，更不要动 `main`。

## 3. 开发顺序

各负责人先按[队员开工与通用 Skill](../agents/delivery-workflow.md)确认领取自己的交付包。AI 自动把真实接受人、日期和状态记录到包与项目跟踪，检查本机通用 Skill，再走 `to-spec → to-tickets → implement`；评测、设计和文档任务也须先写规格和拆票，按对应交付物执行。有现成 spec 和票时接着执行，不重复生成。具体 Skill 名称、来源和安装检查以该规范为准。

Erwin 负责先把转账的一条最小纵向路径接通并验收，形成模块注册、确认、模拟银行和前端接入的可运行样例。v0.3 临时由 Erwin 实现转账参考路径，并承担转账评测与业务审查（2026-09-28 全员会定，原为梁爽）；梁爽负责最小前端；阶段收口后转账模块维护回到梁爽。样例进入 `main` 后，各业务线按同一接缝扩展能力。样例未就绪时，业务线可在自有目录按冻结契约开发和测试，不自行改写公共接缝。

1. 先写用例：用户输入、期望状态、应调用的工具、期望结果、至少一条异常路径。
2. 用假工具 / stub 把流程、分支、等待确认跑通。
3. 再接本模块真实工具与银行接入层，不直连银行内部实现。
4. 最后才接主 Agent 做端到端对话。
5. 适老化只允许改前端交互，不改后端业务流程与 API 语义（前端由梁爽负责、六水协助，09-25 确认）。

## 4. 必须遵守的业务边界

- 不直连银行数据库，不复制余额、限额、风控等银行规则；规则以银行返回为准。
- 不缓存银行判定结果当成本地真理。
- 敏感操作必须走确认回环：暂停 → 前端确认 → 沿原任务继续。口头「用户说过可以」不算授权。
- 参数变化后必须重新确认，不得复用旧批准。
- 模块之间禁止循环调用；只走公开能力或已标明的共享基础服务。
- 不在模块内自建另一套权限系统、压缩引擎或 Agent 调度。

## 5. PR 最低交付

每个业务 PR 必须包含：

- 模块清单更新（更新本模块 `manifest`：名称、用途、负责人、实现类型）。
- 公开入口的输入输出（引用公共契约 `backend/app/contracts/`，不复制一份）。
- 私有工具声明：权限、副作用、确认策略、超时与重试。
- 测试：正常、关键分支、等待用户 / 暂停恢复、权限拒绝、异常兜底。
- PR 说明：场景编号、改动类型、依赖、是否触及安全或契约、用例列表。
- 本模块公开能力或工具的用法文档随实现更新；公共 API 文档按[公共改动流程](03-review-and-merge.md#公共底座与-api-改动)处理。

> 骨架由 Erwin 提供（模块清单模板、工具声明模板、PR 模板、测试骨架），业务同学填空并让测试变绿，不从零造格式。

缺声明的工具不能合入。没有用例的实现不能合入。

## 6. 同步与冲突

- 每天至少 `git fetch` 一次；独立分支同步 `origin/main`，后继分支先跟前序分支同步，前序 PR 合入后再由 Erwin 协助把后继改到最新 `main`。
- 冲突在自己的分支解决，禁止直接推 `main`。
- 锁文件、生成物冲突以重新生成解决，不手改纠缠内容。
- 需要改公共文件时停手，找 Erwin；需要改安全策略时找 ringo。
