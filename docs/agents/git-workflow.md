# Git 与提交约定

任何提交、分支、推送操作前读这份。分支策略、PR 门槛和 CODEOWNERS 规则在
[Review 与合并原则](../principles/03-review-and-merge.md)，本文件只管仓库当前状态与提交格式。

## 1. 仓库当前状态

**本地仓库已建立，`main` 分支，尚无远端。** GitHub 远端是下一步，不是现状。

- 远端建立后，`main` 转为受保护分支：禁止直推，唯一合入路径是 PR（见 03）。
- 团队分工按 `AGENTS.md` 的目录边界表；每个目录只有一个 owner。
- 首次提交已完成，这是仓库的基线。

远端建立前后都成立的两条底线：

- 合入 `main` 之前先 `rebase origin/main`。
- 推送已 rebase 的功能分支用 `git push --force-with-lease`。

## 2. 提交信息格式

首行写类型前缀加一句话，说清**做了什么**；正文说清**为什么**。

```
<类型>: <做了什么>

<为什么这么做>
```

| 类型 | 用于 |
|---|---|
| `feat` | 新增能力、模块、工具 |
| `fix` | 修缺陷 |
| `refactor` | 不改行为的结构调整 |
| `test` | 补测试或用例 |
| `docs` | 文档 |
| `chore` | 构建、依赖、配置、仓库维护 |

一个提交只做一件事。意见修复与新功能分成两个提交，方便 review 与回滚。

例：

```
feat(transfer): 增加按备注匹配收款人

备注匹配需要先查账户别名，再回落到姓名匹配；
直接模糊匹配会把「房租」这类备注错认成人名。
```

## 3. 远端建立后的动作

远端建立后按顺序补齐，每一步完成前不要开始下一步：

1. 收集五人 GitHub 用户名，替换
   [03 的 CODEOWNERS 占位账号](../principles/03-review-and-merge.md#5-谁必须批准codeowners-规则)。
2. `git remote add origin <url>` 并推送 `main`。
3. 在 GitHub 把 `main` 设为 protected branch：要求 PR、要求 CODEOWNERS 批准。
4. 通知全员从远端重新 clone 或重设 upstream。

## 4. 飞书同步边界

项目文档会同步到飞书供团队阅读，本地仓库始终是唯一事实源。

- `tools/` 下的飞书同步脚本入库；同步用的授权产物与状态文件不入库（见 `.gitignore`）。
- 同步方向是本地 → 飞书。飞书上被改过的内容不回流，改动在本地提交后重新同步。
- 图包的校验截图不入库，可由图源 `.json` 重新生成。
