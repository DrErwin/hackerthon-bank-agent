# 公共契约附件：确认与验证字段

> 最后更新：2026-10-20（文件名沿用创建日期）

状态：**v1 已冻结（2026-09-27，Erwin 确认）**；业务口径与必要安全补充已收口，可按此并行开发。未实现、未通过测试；不代 Ringo 签核实现安全。

依据：[公共契约 §4.1—4.4](公共契约-2026-09-23.md)、[安全底座 PRD §10](../prd/安全底座父级-PRD-2026-09-23.md)。本文为公共契约第 4 章的字段附件；正式语义以 docs 为准。实现仍须 Ringo 审查。

## 1. 可信记录与前端输入分开

模型可以提出业务参数，不能填写身份、风险最终裁决、确认通过或验证通过。服务端当前登录上下文提供 `user_id` 与 `session_id`；前端选择的任务 / 确认 / 验证记录编号必须逐次检查归属。API 先校验身份，银行经接入层接收可信上下文，不接受模型声明的用户身份。

### ConfirmationRecord（后端保存）

| 字段 | 类型 | 用途 |
|---|---|---|
| confirmation_id | ID | 后端生成的确认记录编号 |
| confirmation_version | 正整数 | 展示 / 作答的版本；旧版本不能通过 |
| user_id / session_id / task_id | ID | 身份与任务归属，由服务端保存 |
| operation_id / action_name | UUID / string | 具体动作及类型；提交时沿用同一操作编号 |
| action_revision | 正整数 | 关键业务内容版本；不因纯展示或原样重确认而改变 |
| parameters_ref | ID | 后端受控的关键参数快照引用；不能指向可由模型修改的文本 |
| display_fields | 结构化展示项列表 | 用户必须看到的对象、金额、账户、时间、用途等；冻结确认还必须展示结束时仅释放未消费余额的限定授权，见主契约 §3.5；按动作类型确定必需项并脱敏 |
| created_at / expires_at | Timestamp | 创建及到期时间，确认有效期 1 小时 |
| decision | pending / approved / cancelled / expired / superseded | 仅由服务端处理当前版本用户动作后更新 |
| decided_at | Timestamp 或 null | 用户选择时间 |

`ConfirmationAnswer`（前端输入）：`confirmation_id`、`confirmation_version`、`choice:approve|cancel`。不接受前端携带替换金额、用户身份或服务端批准时间。每条动作单独作答；可以同屏展示，但不以一个全局 approved 标记代替逐条决定。重复提交相同答案返回原决定，不再次推动副作用；旧版本、已取消或矛盾答案明确拒绝并要求读取当前状态。

关键参数改变形成新的内容版本与动作，旧确认失效。仅到期重确认且内容不变时更新确认记录 / 版本，但保留原动作内容关联，避免把「只重确认」误实现成必须重验身份。若已提交或结果未知，先查原操作，不能借生成新确认重做交易。

确认展示项与实际执行参数来自同一份后端受控快照；F14 读取和 F15 作答时均核验用户、会话、轮次、任务、当前版本及记录状态。执行前再次核对实际关键内容，变化则重新确认；余额、限额等银行条件变化仍由银行判断，不一概增加用户确认。冻结确认继续包含主契约 §3.5 的限定释放授权。

F19 模拟验证码与 F27 模拟人脸仅用于演示验证流程及权限约束，不代表真实身份认证强度；沿用现有模拟能力，不新增真实短信或人脸服务。

### VerificationChallenge（银行保存）

| 字段 | 类型 | 用途 |
|---|---|---|
| challenge_id | ID | 本次验证码及核验请求编号 |
| user_id / session_id / task_id | ID | 服务端可信归属 |
| purpose | basic_identity / action_step_up | 低风险基础身份验证，或中风险当前动作双因子 |
| operation_id / action_revision | UUID / 正整数，基础验证可空 | 中风险必填，绑定当前确认动作；不能指向下一笔 |
| summary | VerificationSummary 或 null | 中风险必有，基础验证为 null；由应用从当前确认参数生成，银行保存并原样返回脱敏快照 |
| required_methods | 方法列表 | 基础为 code；中风险为 code、mock_face |
| created_at / code_expires_at | Timestamp | 当前挑战创建时间与验证码截止时间；中风险截止固定为本动作本轮首次创建后 5 分钟，替代挑战继承原截止时间，不能用新的 created_at 重算 |
| face_started_at / face_expires_at | Timestamp 或 null | 人脸验证创建起单独 5 分钟；未发起时为空，不设合计 5 分钟期限 |
| challenge_status | pending / passed / failed / expired / superseded / cancelled | 银行侧核验事实 |
| code_result / face_result | pending / passed / failed / expired / cancelled，face 可为 not_required | 方法结果，只由银行记录 |
| consecutive_code_failures | 非负整数 | 本任务低风险连续错误数，重发不归零；同一次请求的重复传输不重复计数 |

验证码原文不属于上述可持久化记录。仅受控模拟验证端处理，不写模型消息、日志、检查点；具体临时保存方式随实现确定。演示提示区通过专用受控响应取得模拟码，不经过普通聊天 / SSE 内容。重发生成新 challenge，旧码和旧 challenge 不再可用，连续错误计数按任务延续。中风险到期前重发也沿用原 code_expires_at；同动作另建挑战不能延期。低风险仍允许重新获取后有 5 分钟作答时间。

### VerificationSummary（验证页面的受控摘要）

字段：`operation_id:UUID`、`action_revision:正整数`、`source_confirmation_id:ID`、`source_confirmation_version:正整数`、`action_name:string`、`amount_fen:Money|null`、`payee:PayeeDisplay|null`、`display_fields:DisplayField[]`。付款、冻结、预约等金额动作必须有 amount_fen；转账／预约必须有银行已核验的 payee（含开户行）；导出等无金额动作使用 null，并在 display_fields 展示实际报告／范围／用途。字段只能来自该动作受控参数和确认展示快照，不接受模型、前端自由提交摘要，也不让银行反查应用表。

应用在创建挑战前核对确认归属、内容版本、当前有效性和摘要一致性，通过可信接入层将 summary 连同动作引用交给银行；银行校验摘要中 operation_id / action_revision 与请求一致。创建、查询、重发与核验响应均携带相同的脱敏 summary，前端 VerificationView 直接展示，不能只展示验证码框而丢失本次业务对象。重发保留摘要和原期限；纯确认到期后原样重确认，可保留同 action_revision 的原摘要来源，执行时仍须取得当前有效确认；金额或对象改变则原挑战不能授权新版本，必须重建对应动作的确认和验证。

### VerificationRecord（成功后的可信引用）

`verification_id`、`user_id`、`session_id`、`scope:session|action`、`operation_id:null|UUID`、`action_revision:null|int`、`methods`、`verified_at`、`source_challenge_id`。

基础验证 scope=session，当前有效登录会话可复用；中风险 scope=action，必须匹配当前动作和内容版本且两种方法均通过。验证码到期时间不等于成功后验证记录的有效期；会话有效性和当前风险仍需每次由服务端检查。关键参数改变使旧 action 记录不再适用；纯确认到期、内容未变时，仍有效的 action 记录不因确认单换号自动作废。

**2026-10-19 场景 05 订阅代扣解约（`bank.cancel_subscription`）补充**（**2026-10-20 修订：按 PM 1A 裁定升为三级敏感**）：解约为三级敏感（`OperationLevel.SENSITIVE`）、有副作用、逐动作确认（`confirmation_policy=per_action`）；提交银行前须持久化脱敏 `AuthorizationSnapshot`（由 `authorization_snapshot_ref` 引用），快照或开始日志写入失败立即暂停、不得提交银行。确认单 `display_fields` 展示商户与服务名、扣款金额与周期、扣款账户（打码）、下期扣款日期及生效口径「从下一期（YYYY-MM-DD）起不再自动扣费，之前已经扣掉的钱不退」（不承诺商户侧会员权益何时截止）。身份验证固定采用低风险基础身份验证（`purpose=basic_identity`、`required_methods=["code"]`、`scope=session`），同一有效登录会话内可由服务端核验复用；连续 3 次验证码错误终止本次任务；**不启用中风险模拟人脸（`mock_face`）**。命中高风险外部胁迫或越权信号直接 `BLOCK` 终止。

## 2. 接口候选

接口名称为逻辑能力名，HTTP 路径与状态码已整理在[公共契约 §6.4—6.8](公共契约-2026-09-23.md)，仍待统一审阅；银行方法经接入层调用，前端不直连银行。确认 / 验证对应 F14—F20，人脸作答 F27，会话提前过期 F28；各引用由服务端检查归属及有效性。

| 能力 | 输入 | 输出 / 行为 |
|---|---|---|
| security.create_confirmation | 后端可信动作及参数快照 | ConfirmationRecord 的可展示视图，不暴露内部身份或敏感原参数 |
| api.get_confirmation | confirmation_id | 当前展示内容、版本、有效期及状态，校验任务归属 |
| api.answer_confirmation | ConfirmationAnswer | 当前决定与允许的下一步；调用平台沿原任务继续，不直接从 API 扣款 |
| bank.create_verification | 后端确定的 purpose、任务及必要动作引用 | challenge_id、required_methods、code_expires_at、打码验证摘要；中风险摘要回显本笔金额和收款人 |
| api.resend_verification_code | challenge_id | 由服务端检查任务未终止、允许重发后创建替代 challenge；中风险即使未到期也继承原截止时间，已失败 / 超时拒绝重发续办 |
| bank.verify_code | challenge_id、submission_id、code（专用输入） | 核验结果；基础连续 3 次错误终止，本任务重发不绕过计数；中风险一次失败即终止 |
| api.submit_demo_face_result → bank.verify_face | challenge_id、submission_id、result:passed\|failed | 演示前端当前验证的成功 / 失败按钮；后端校验管理权限、演示轮次、归属和 5 分钟期限后，由银行记录。不是普通业务或模型自填通过标记；过期 / 已终止任务不得复活 |
| api.expire_demo_session | session_id | 管理页立即使目标登录会话过期；后端检查管理权限，行为同自然过期 |
| api.get_verification_state | challenge_id | 返回当前核验事实及任务可继续与否，不返回验证码；技术超时时可查询已保存事实 |
| api.get_demo_code | challenge_id | 仅演示专用提示区获取当前模拟码，校验用户、会话、任务归属；不注册为模型工具，不记录响应原文 |
| security.check_action | 后端注入的 ExecutionSecurityContext + ActionDescriptor | 六种既定安全裁决之一，及必要原因 / 交互请求引用；不能只凭记录编号直接放行 |

`submission_id` 表示一次验证码或人脸提交，用于区分真实重试与网络重复发送；同号不同内容拒绝，同一输入重传不重复增加错误次数。该编号不是业务扣款的 operation_id。

## 3. 核验结论与技术故障

核验响应分为 `kind=verified`（通过）、`kind=rejected`（已取得未通过事实，含原因及低风险剩余次数）、`kind=error`（技术故障，没有可靠核验结论）。中风险只有两种方法均 passed 才产生验证记录，不能因为验证码已通过就提前放行。

技术故障不能被当成验证通过，也不能伪造为用户输错。中风险核验超时仍按已定策略终止，不因稍后的成功回包复活任务；新的任务需要重新走其规定流程。低风险技术故障只暂停执行，不增加「输错」计数。验证码和人脸各自 5 分钟；客户端断线本身不算失败，真实计时继续，重连查询后端原状态。实现与字段仍需审阅，不声称现有框架自动保证。

错误码：`CONFIRMATION_EXPIRED`、`CONFIRMATION_STALE`、`CONFIRMATION_CONFLICT`、`CHALLENGE_EXPIRED`、`CHALLENGE_SUPERSEDED`、`CODE_MISMATCH`、`VERIFICATION_LIMIT_REACHED`、`VERIFICATION_SCOPE_MISMATCH`、`TASK_TERMINATED`、`AUTH_REQUIRED`、`ACCESS_DENIED`、`DEPENDENCY_UNAVAILABLE`。只给允许展示的原因，不回显验证码或他人的记录详情；HTTP 映射见安全与审计字段附件 §6，实际输错通过 VerificationResponse 表达。

## 4. 跨模块安全上下文

`ExecutionSecurityContext` 统一引用安全与审计字段附件 §1，包含 demo_round_id 与 run_id；由公共适配器建立，不作为主 Agent 的可填工具参数。

06→01 若使用子任务，公共平台核验父子任务关联及委派范围；不能机械要求任务编号完全相同，也不能只匹配同一用户就通过。实际动作、关键参数、确认范围、验证范围、权限与当前风险都要符合。传入失效记录按现有规则重新交互，传入无权引用记录则拒绝，不转成另一种工具绕行。

同一低风险会话身份验证可服务两笔分别确认的转账；中风险的第一笔双因子不服务第二笔。银行规则仍在提交时执行，接入层不把历史安全通过当作当前账户授权。

## 5. 验收要求与未完成项

- 原确认 500 元，参数改成 600 元后旧按钮失效；原样确认过期只重确认，不错误清掉仍有效的验证。
- 验证码仅走专用路径；重发后旧码无效、连续错误数保留；低风险第 3 次实际错误终止，重传同一提交不重复计数。
- 中风险一次失败 / 超时终止；在第 4 分 50 秒重发仍只剩 10 秒，旧码立即失效；只完成一种方法不可执行，迟到通过回包不可复活已终止任务。
- 低风险同会话可复用；中风险跨动作或改关键参数后不可复用；跨用户、无父子关系或参数不匹配的引用拒绝。
- 中风险创建、查询、重发均返回绑定同动作版本的金额／收款人／开户行或相应非资金摘要；改金额、对象后旧摘要不得继续核验新动作；基础验证不伪造业务摘要。
- 演示模拟码不能被 Agent 工具读取，确认 / 验证接口返回及审计不包含验证码。

第六批已定：会话真实时间固定 2 小时，刷新不续期，支持管理页提前过期；验证码和模拟人脸各自 5 分钟，模拟人脸由前端按钮作答，无实际识别服务。完整对话与可观测执行日志持久化，权限与写入失败处理见公共契约 §4.5；第七批已定脱敏细则、预置与禁止记忆清单。安全裁决、审计分类、完整 ExecutionSecurityContext 与错误映射见[安全与审计字段](安全与审计字段-2026-09-24.md)；HTTP 协议见主契约 §6。文档已补齐，必要安全回件已吸收；后续实现按现行契约并行推进，整体冻结仍由 Erwin 决定。


补充：ConfirmationRecord、VerificationChallenge、VerificationRecord 均带 demo_round_id:ID；record_ref 的 DisplayField、各项验证时间与重发继承规则统一引用安全与审计字段附件 §3。权限过期与轮次变化均不能靠已持有记录编号继续执行。

## 6. 后端核验能力完整签名

上述 api.* 仅为逻辑名称，实际 HTTP 方法见主契约 F14—F20 / F27 / F28；以下为底座与模拟银行的受控内部签名，不对模型开放：

- `bank.create_verification(context, purpose, operation_id:null|UUID, action_revision:null|int, summary:VerificationSummary|null)`：context 包含 user_id / session_id / task_id / demo_round_id；purpose 为 basic_identity 或 action_step_up。后者必须绑定动作及当前确认并传入匹配的 summary；基础验证 summary 为 null。同动作已有待完成挑战时找回原挑战，不另起五分钟；required_methods 由服务端策略确定；返回 VerificationChallenge 的无秘密视图，模拟码另走 F19。
- `bank.start_face(context, challenge_id:ID, submission_id:UUID)`：仅 required_methods 包含 mock_face 且挑战 / 任务仍可继续时创建人脸时限；重复调用返回原始期限。F20 的 request_id 映射同一 submission_id，不新起计时。
- `bank.verify_code(context, challenge_id:ID, submission_id:UUID, code:string)`、`bank.verify_face(admin_context, challenge_id:ID, submission_id:UUID, result:passed|failed)`：返回 `{kind:verified|rejected|error, challenge:VerificationChallenge, verification_id:ID|null, reason_code:string|null}`；只有必需方法全部通过才产生 verification_id。face 必须核对管理员身份和挑战目标归属，不能使用管理员的用户编号替代被验证用户。
- `bank.get_verification(context, challenge_id:ID)`：返回无秘密的 VerificationChallenge。`bank.resend_verification_code(context, challenge_id:ID, submission_id:UUID)`：返回替代挑战，继承规则见安全附件 §3；旧挑战不可继续作答。
- 应用从银行核验事实构成 VerificationResponse 并追加 TaskView，银行不直接写应用任务状态；公共安全代码依结果裁决是否继续。
