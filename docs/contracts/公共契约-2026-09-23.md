## 0 定位与使用方式

**这份契约为了什么**：把所有跨模块触碰点一次性钉死——谁提供什么、字段长什么样、语义是什么、错了返回什么、以后要改怎么办。它收进来的输入是五份 PRD 里已经定好的口径；它服务的是各模块的开发者。

**完成判据（契约的唯一验收标准）**：

> **任何一个模块的开发者，只读契约 + 自己的 PRD 就能开工，不需要问任何人任何问题。**

自测三问：字段名都知道了吗？错了返回什么都知道了吗？边界外找谁、边界内谁说了算都知道了吗？——哪一章答不上来，哪一章就没写完。

### 0.1 命名与版本规范（09-24 Erwin 已确认）

- 字段名统一用小写加下划线，例如 `task_id`；公开能力名称用「模块＋动作」，例如 `transfer.create_transfer`（命名示例，具体能力定义随各章填充）。中文说明业务含义。
- 2026-09-27 已由 Erwin 确认首次整体冻结为 **v1**；面向前端的 HTTP 接口统一放在 `/api/v1` 下。文档保留当前文件名，通过顶部日期和修订记录标明更新。
- 首次开发期只维护一套当前接口。兼容修改留在 v1；不兼容修改经第 8 章协同确认、统一切换并验证后，也可更新当前 v1，不必每次新开版本。
- **不同日期的 v1 不保证彼此兼容。** 联调与演示统一使用同一份已合入代码，具体修订由 Git 记录定位。
- 出现必须继续支持旧客户端或独立发布使用方的需求时，再评估 v2 与旧接口保留期；此时不能继续假设所有使用方可以一起切换。

## 1 总则

**金额与时间（09-24 已定）**：接口中的金额、余额、限额和费用统一使用整数分，例如 500 元传 `50000`，本期币种固定人民币；面向用户的界面与文案显示元。时间必须带时区，预约执行与自然日限额按北京时间解释。各字段的取值范围随银行规则定义，业务侧不复制银行限额校验。

三条铁律（唯一出处 AGENTS.md，此处只引用不复写）+ 两条通用规则升格为条款 + 全系统共用枚举。

### 2.1 银行结果共同约定（09-24 已定）

- 普通查询返回所需事实数据；执行返回调用方操作编号、处理状态及对应回执。银行交易编号由银行生成，不能要求调用方先拿到它才能回查。
- 提交与回查复用同一套操作结果结构；失败返回「原因码＋关键数字」，例如余额不足及差额，用户话术由业务模块组织。具体字段与错误码见银行附件 §2 / §8。
- 回查区分「查到原操作」「未查到记录」「本次查询失败」。只有查到原操作时，才提供该操作的实际结果；银行交易状态仍只有成功 / 失败 / 处理中。未查到或查询失败不增加新的银行交易状态，也不表示原操作失败。
- 回查覆盖 §3.1 列出的业务写操作，除交易回执外，可返回原操作产生的冻结编号、预约编号或订单编号。查原操作结果与查询这些业务对象当前状态分别表达，不能用当前余额等事实猜测某次操作是否成功。
- 查询需要服务端可信身份，银行校验原操作归属；登录过期或无权限按访问失败处理，不借回查暴露他人的操作记录。

### 2.2 流水查询完整性（09-24 已定）

- 本期一次返回指定账户、指定时间范围内的全部流水，不分页、不限制返回前若干条。查询支持最近 24 个月；超出支持范围明确报错，不能静默裁剪成残缺账单。
- 时间范围采用含开始、不含结束的区间，避免相邻月份重复计入边界上的同一笔交易；时间解释遵循第 1 章。
- 查询成功且没有记录时返回空列表；查询失败不能当作「没有消费」。返回数据截至时间，让账单模块明确统计依据。
- 完整流水供账单模块计算，不要求把全部原始明细直接塞入模型上下文或前端一屏；对外展示仍遵守脱敏与按需展示规则。

## 3 交易与资金语义（主笔：Erwin）

| 条目 | 口径 | 状态 |
|---|---|---|
| 稳定操作编号 | 调用方确定性代码生成 UUID 并在提交前保存，银行只认号；银行交易编号由银行另行生成 | **已定（09-24），见 §3.1** |
| 状态机与超时 | 首次提交 4 秒超时 → 结果未知 → 按原编号回查（每 3 秒、最多 10 秒） | 已定（D09/D09-b），失败码见银行附件 §8 |
| 幂等 | 同编号重复提交返回首次结果；同编号参数不符报「参数冲突」拒绝 | 已定（Mock Bank 验收例 4 / 14） |
| 限额 | Ⅰ / Ⅱ / Ⅲ 类户监管值 | 已定（D02）；本期不增加四层取最低引擎，沿用账户规则（Erwin 本轮确认）；个人预算不是银行额度 |
| 冻结语义 | 冻结 + 分笔核销 + 差额释放；不撤不退；「没花的不扣，花了的不退」；冻结与释放不进消费流水 | 已定（D10/D11/D06） |
| 预约执行语义 | 到点由**银行自动执行**（扣款、生成流水、不向用户二次确认）；月末按自然月月末；余额不足直接失败不补扣；执行触发不在应用侧 | 已定（01 三个子问题 + 09-24 执行归银行） |

### 3.1 操作编号与防重复范围（09-24 已定）

调用方的确定性代码为每个实际业务写动作生成随机 UUID（UUID v4），提交前持久化；不由模型填写，不用任务编号或模型工具调用编号替代。银行在可信身份范围内按操作编号去重；同一编号不同参数拒绝，不能覆盖原操作结果。

适用动作：转账、冻结、从冻结扣款、释放冻结、预约创建 / 取消、外部生活服务下单。普通查询不要求这个防重复编号；环境重置等演示管理操作随第 7 章另定。

同一动作恢复或核对沿用原编号；每个新动作使用独立编号。例如一个生日任务内的冻结、两笔扣款和释放余额各有自己的编号。参数改变形成新动作并重新检查授权，但旧动作结果未知时必须先核对，不得换编号重做。支持同编号去重，不代表超时后允许自动重发。

预约的每一期到点执行由银行负责防重复；应用侧只管理预约，不承担执行触发和期次去重。

### 3.2 超时与回查闭环（09-24 已定）

首次提交划转等待 4 秒未得到明确结果，进入应用侧「结果未知」。从首次提交超时起，自动回查阶段每 3 秒查询原操作一次，最多再等 10 秒；单次查询耗时计入这 10 秒，查询失败不重置计时，达到截止时间停止本轮自动等待。

| 回查情况 | 后续处理 |
|---|---|
| 查到成功或明确失败 | 保存银行实际结果；单笔转账据此更新任务，复合任务按各子动作结果推进 |
| 查到处理中 | 在剩余等待时间内继续查原操作，不宣布成功 |
| 未查到记录 | 在剩余等待时间内继续查询；不能推断原操作未执行 |
| 查询临时失败（如超时、服务暂不可用） | 在剩余等待时间内重试查询，不重新提交业务写操作 |
| 登录过期或无权限 | 停止查询，恢复合法访问条件后方可再次查询；原操作仍待核实，不伪造其失败结果 |
| 到达回查截止时间仍无明确结果 | 停止自动查询，任务进入 `needs_attention` 并保留原操作编号及已知事实 |

待核实界面提供「查询结果」，说明「这笔转账的结果暂时还没核实，我没有再次提交」。用户主动查询时再次检查登录身份与任务归属，只查原操作；查到明确结果后更新原任务。一直查不到就继续保留待核实，不能提供绕过核对的重转入口，也不因用户说「再转一次」就创建替代交易。此处不新增无限后台轮询。

### 3.3 预约范围与结束条件（09-24 已定）

- 本期支持单次预约与每月预约；每日、每周及无期限计划不进入首版。
- 单次预约明确一个未来执行时刻；每月预约明确首次执行时间、每月执行日，以及结束日期或执行次数（二选一）。结束条件未给出或含糊时先追问，不默认永久转账。
- 用户创建计划时确认，银行到点自动执行，不逐期再确认；原有月末处理、余额不足本期失败不补扣等规则沿用。
- 创建成功只表示预约已保存，不表示已转账；未来期次与已执行结果分别记录。已创建预约不支持修改；需要调整时先确认取消旧预约的未执行期次，核实取消成功后再以新任务、新操作编号重新确认并创建预约。取消失败或结果未知时不得先建替代预约；已执行记录保留，处理中期次先核实。

### 3.4 订单创建与付款结果（09-24 已定）

保持「冻结预算 → 外部下单 → 从冻结分笔扣款 → 释放差额」的已定顺序。订单创建成功时为未付款，只有银行扣款成功才能记为已付款；用户回执分别说明订单和付款结果，不能把「下单成功」说成「购买完成」。

付款绑定具体订单，银行核对订单归属、商户与金额，记录对应付款交易；同一订单最多成功付款一次，换操作编号也不能重复扣款。账本变更与订单付款关联由银行在自身边界内保持一致。

| 情况 | 处理 |
|---|---|
| 创建订单明确失败 | 不为该订单扣款；按原流程处理明确未花掉的冻结 |
| 下单成功，扣款明确失败 | 订单保留未付款，如实展示；明确未花掉的冻结可按原流程释放，不承诺购买成功 |
| 下单或付款结果未知 | 先查原操作，暂停依赖该结果的后续步骤；不重新下单、不重复扣款、不抢先释放可能仍用于在途付款的资金 |
| 付款已成功 | 订单关联实际付款交易并展示已付款；回执丢失时查询原操作找回结果，不再次办理 |

本期不新增订单取消或退款能力。「未付款」必须来自银行已知事实，不能把应用侧超时直接翻译为未付款。

### 3.5 结束时释放未消费冻结余额（09-26 Erwin 已确认）

首次冻结确认单明确展示：“本任务结束（完成、取消或安全终止）时，仅释放这笔冻结中未消费的余额回原账户；不会继续下单、付款，也不会退回已消费资金。”用户确认冻结时一并取得该限定授权，后端保存 FreezeReleaseAuthorization（字段见安全与审计附件 §3.1），不以模型承诺代替记录。

- 冻结成功后绑定银行 freeze_id；冻结结果未知时先按冻结原操作编号回查，不重复冻结。只有核实成功的冻结才能进入释放收尾。
- 结束时先停止新下单与扣款、核实全部在途资金动作，再查 B13；确定性代码以银行当前未消费余额调用 B12，余额为 0 时不提交零金额操作。仍有未知付款时暂停释放，不抢占在途资金。
- 释放使用独立、提交前持久化的 operation_id，并关联原冻结、限定授权及结束原因；仍经统一执行器、银行授权与审计。同一释放未知时只查原操作，不换号重做。
- 取消或安全终止不撤销该限定释放授权，也不恢复原购买流程；收尾只允许查原事实和释放原冻结余额。普通 resume 仍不能复活被终止任务。会话过期不得复用旧会话执行一般业务；限定收尾由后端受控身份执行，按记录核验原用户、原任务、原账户、当前轮次及资金归属，不将历史验证当作通用授权。
- 必要日志写入失败、无法取得可靠资金事实或释放失败时，保留“购买已停止、冻结款待处理”与原编号，任务为 needs_attention，禁止继续购买；只有银行确认后才报告释放金额。用户回执分别说明已消费、已释放和仍冻结金额。重置仍等待在途结束，旧轮次授权不能用于新轮次。

验收见 M14；安全侧对应 S07。

### 4.1 确认单与用户动作（09-24 已定）

后端保存确认单、具体动作参数与确认版本，前端展示后由用户点击「确认办理」。首版不以聊天中的「确认」或模型生成的通过标记替代按钮提交。冻结确认包含 §3.5 的限定释放授权；结束收尾不再另等一次确认，其他动作仍逐动作确认。多笔可在同屏展示，仍逐条确认，每笔关联自己的动作。

金额、账户、收款人、执行时间、商品、地址、数据范围等关键内容改变，原确认立即失效；重新校验、生成当前版本并让用户确认。旧版本按钮、重复点击、过期或已取消的确认不能授权新动作。确认有效期沿用 1 小时；内容未变且仅确认过期时只重确认，是否补验证按 §4.3 的有效记录判断。

### 4.2 验证码输入、有效期与失败处理（09-24 已定）

- 验证码在专用输入框提交，由后端交模拟银行核验；不经过 AI 对话，不进入模型上下文、日志或持久化检查点。演示用标明「模拟验证码」的专用提示区显示，不接真实短信，不由模型生成或宣告通过。
- 低风险验证码每次创建有效期 5 分钟；中风险验证码从本动作本轮首次创建起 5 分钟，重发（包括到期前）沿用原 code_expires_at，不延长截止时间。重发生成新码并立即使旧码失效；不能通过另建同动作挑战重置时限。人脸仍从首次创建该项起单独计时。
- 低风险输入错误可重试；本次任务内连续输错 3 次终止本次任务。过期可重新获取；重发不得清零连续错误计数绕过上限。终止后不在原任务内继续验证或执行。
- 中风险沿用已定的「新验证码＋模拟人脸」双因子，两项都通过才可继续；任一核验失败或超时按高风险终止，不进入低风险的 3 次重试路径。
- 网络或服务故障没有可靠核验结论时不得放行，也不能伪造验证通过；实际核验结论与技术故障在结果结构中分别表达。中风险核验超时仍按上述既定规则处理。

**第六批补充（Erwin 已确认）**：验证码和模拟人脸各有 5 分钟作答时间，分别从后端首次创建该项验证时计时（中风险重发不重新计时）；不另设双因子合计 5 分钟或人脸服务等待 10 秒的限制。模拟人脸不接实际识别服务，在演示前端提供「模拟成功 / 模拟失败」按钮，由具有演示管理权限的操作者为当前人脸验证作答。后端校验权限、演示轮次、用户 / 会话 / 任务、当前验证编号及截止时间，再由模拟银行保存结果；前端按钮不能直接生成验证通过记录或授权扣款。每项结果只生效一次，超时或任务终止后的按钮及迟到响应不能复活任务。页面断线本身不算核验失败，恢复后读取后端状态；真实时间继续计时。

### 4.3 验证记录的复用范围（09-24 已定）

| 验证记录 | 可复用范围 | 不能复用的情况 |
|---|---|---|
| 低风险基础身份验证 | 同一用户、同一有效登录会话内，由服务端查验记录后复用 | 登录会话失效或更换、记录无效、风险升档需追加验证 |
| 中风险双因子验证 | 当前已经确认的具体动作及其关键参数；同一动作跨模块交接可以复用 | 下一笔动作、关键内容改变、身份或会话不再有效；高风险直接终止 |

验证身份不代替逐动作确认、当前权限检查或银行提交时的条件检查。中风险关键参数改变后，旧的动作验证不再适用，必须重新确认并重新核验。仅确认到期、内容未变时不据此强制重验；仍需确认原验证记录有效、风险未升档。

### 4.4 跨模块安全上下文（09-24 已定）

06 调用 01 等跨模块交接时，只传递后端保存的确认记录、验证记录的引用，不传可由模型或业务模块自填的「已通过」布尔值。公共安全代码读取原记录，核对当前用户与会话、交接任务关系、具体动作、关键参数和有效性；符合才复用，不重复打扰用户。不符合则按缺确认、缺验证、权限拒绝等原因处理，不能为了复用而放宽安全检查。

### 4.5 对话与完整运行日志（09-24 第六批已确认）

日志保留完整的可观测运行过程，不能只保存业务结果摘要。包括用户每条输入、助手回复、每次模型调用实际送入的提示及上下文与实际返回、模型明确输出的计划、加载记忆与上下文压缩、模块调度、全部内部及公开工具的名称 / 调用参数 / 返回结果 / 执行顺序，以及权限裁决、确认、验证、异常、恢复与演示管理动作。内容脱敏后持久化，验证码、密码、密钥及登录凭据不落盘；受控内容快照须实际可读取，不能仅留失效链接。记录系统可获得的执行证据，不要求供应商未提供的模型内部思维，也不事后编造推理过程。

共同记录演示轮次、用户 / 会话 / 任务 / 运行与调用关联编号、模块、事件种类、真实时间、结果、错误原因及内容快照引用；涉及模拟业务时间另行记录，涉及资金时关联原操作与银行交易编号，涉及安全时关联确认与验证记录。完整字段以架构 §12 事件外壳为基础，见安全与审计字段附件 §4—5。

### 5.1 共用调用与返回

类型沿用银行字段附件的 `ID`（不透明字符串）、`Money`（非负整数分）、`Timestamp`（带时区时间）和本契约第 1 章任务状态。`?` 表示输入可省略；输出字段均存在，可空项显式标 `null`。统计差额用有符号整数分，不把净退款强行截为零。

所有入口由平台注入可信上下文：`user_id / session_id / task_id / run_id / parent_task_id:null|ID`；有副作用的具体动作另带服务端保存的 `operation_id / action_revision` 及 §4.4 确认、验证记录引用。模型业务参数里不能填写身份或通过标记。调用入口不等于授权执行；每项能力仍经过权限与必要安全检查。

开始类入口接收 `request_id:UUID`（由调用端确定性代码生成并保存，同次请求重传沿用）与下表业务输入。平台按用户和请求编号找回原任务，同号不同输入拒绝；这只防止重复创建任务，不替代每笔银行动作的 `operation_id`。缺少业务信息仍可建立澄清任务，不能猜值后提交。恢复使用平台原任务入口，禁止把恢复实现为重新调用开始入口创建新任务；具体前端协议在第 6 章定义。

统一返回 `ModuleResult<T>`，沿用架构 §8 的任务结果外壳：

| 字段 | 类型 | 含义 |
|---|---|---|
| task_id / run_id | ID | 本任务及当前运行编号；任务状态查询始终指向原任务 |
| status | 第 1 章 TaskStatus | 任务状态，与银行交易状态分开 |
| data | T 或 null | 已取得的结构化事实；没有事实时为 null，不能填造成功数据 |
| message | string | 可直接展示的脱敏说明，不作为机器判定成功的依据 |
| interaction | InteractionRequest 或 null | 需要补充输入、确认或验证时的交互；定义见下 |
| error | ModuleError 或 null | 请求拒绝、依赖故障等原因；等待用户不算技术错误 |
| allowed_actions | string[] | 当前确实可用的动作：provide_input / confirm / verify / query / cancel / resume；由状态和权限决定，不能一律提供重试 |
| recovery_required / recovery_reason | bool / string 或 null | 沿用架构恢复标志；有标志先核对，不能直接重跑 |

`InteractionRequest`：`interaction_id:ID`、`kind:input|confirmation|verification`、`prompt:string`、`required_fields:string[]`、`options:{id:ID,label:string}[]`、`record_ref:ID|null`。候选编号引用服务端候选；确认 / 验证时 record_ref 必填，指向 §4 的受控记录；输入澄清时允许空。确认和验证统一对应 waiting_approval，缺业务信息对应 waiting_input；验证码不经普通补充输入传递。

`ModuleError`：`code:string`、`source:platform|security|bank|transfer|bills|subscription|cross`、`field:string|null`、`reason:string`、`upstream_code:string|null`。reason 脱敏，原银行原因保留在 upstream_code；按 §5.7 处理，不提供通用“写入自动重试”开关。请求被拒绝且任务尚未创建时，仅返回 `{error:ModuleError}`，不伪造 task_id；对已有任务的拒绝不改写原任务结果。

### 5.4 联动模块入口与返回（06）

主 Agent 入口 `cross.start_task`：`request_id:UUID`、`goal:string` 必填；`scenario:birthday|budget|income_distribution?`、`constraints:CrossConstraints?` 可选。scenario 不明确时由模块识别或澄清，超出本期三场景返回 CAPABILITY_UNAVAILABLE，不扩展成任意任务执行器。

CrossConstraints 按场景取字段：生日为 `recipient_hint:string? / recipient_ref:ID? / birthday_on:日期? / deliver_by:Timestamp? / delivery_ref:ID? / budget_fen:Money? / budget_ref:BudgetRef? / preferences:string[]?`；预算为 `scope:BillScope? / personal_limit_fen:Money? / purpose:string?`；收入分配为 `payer_account_id:ID? / income_transaction_ids:ID[]? / income_hint:string? / allocation_rule_ref:ID? / allocations:Allocation[]?`。缺少 PRD 条件必填项时返回 waiting_input，不能为方便接口把未提供的预算、地址或收入填成默认事实。delivery_ref 只引用当前用户的受控收件资料；明文资料在受控录入端提交，日志脱敏。

Allocation 为 `destination:transfer|retain`、`target_account_id:ID? / payee:PayeeInput?`、`amount_fen:Money? / ratio_bps:int(1..10000)?`。amount 与 ratio 二选一；transfer 的 target_account_id / payee 二选一，且实际提交前解析为银行可核验收款信息；retain 不填写目标账户，只表示留在主账户、不生成转账。比例转换及最终金额合计由确定性代码计算，模型不能自行四舍五入形成多扣或少扣。

返回 `ModuleResult<CrossTaskView>`。CrossTaskView 为 `scenario:birthday|budget|income_distribution|null`、`plan_revision:正整数`、`steps:CrossStep[]`、`budget:BudgetView|null`、`summary:string`；场景尚待澄清时 scenario 为 null。CrossStep 为 `step_id:ID`、`action:string`、`child_task_id:ID|null`、`operation_id:UUID|null`、`status:TaskStatus|null`、`amount_fen:Money|null`、`order_id:ID|null`、`payment_status:unpaid|paid|null`、`result_ref:ID|null`、`error:ModuleError|null`。step_id 由服务端分配；计划中尚未启动、还没有执行状态的步骤 status 为 null，不冒充等待用户输入，也不改变八种任务状态。订单是否创建、是否付款分别说明；付款结果未知时 payment_status 为 null，待核实不能写成未付款。

BudgetView 为 `budget_ref:BudgetRef|null`、`purpose:string`、`scope:BillScope`、`personal_limit_fen:Money`、`used_fen:有符号整数分`、`remaining_fen:有符号整数分`、`facts_as_of:Timestamp`、`adopted:bool`。used 引用 L01 的消费净额，remaining = 用户限额 − used；负数如实表示超出。adopted 由后端记录用户是否已确认采用，不能由模型填写；不代表银行额度或购买授权，不改变银行规则。共享给后续任务时携带原 scope，不能跨月份默默复用；budget_ref 与 purpose 按下文采用记录生成。

`BudgetRef`：`budget_id:ID / version:正整数`。06 后端保存 `AdoptedBudget`：`budget_id / user_id / demo_round_id / source_task_id:ID`、`version:正整数`、`scope:BillScope`、`purpose:string`、`personal_limit_fen:Money`、`adopted_at:Timestamp`、`adoption_interaction_id:ID`、`status:active|superseded`；该记录是业务约束，不是记忆中的执行授权。采用通过原任务 InteractionRequest（kind=input、options=adopt/modify/decline）及 F10 明确选择完成；服务端核对当前计划版本及原范围／用途／金额快照，重复作答不重复创建，旧交互不能采用新方案。只有 adopt 后生成 budget_ref，未采用时为 null；改范围／用途／限额必须重新采用新版本，旧版 superseded，重置清除当前采用状态。

后续生日任务由服务端按当前用户、轮次、实际付款账户、消费日期及用途查找适用的 active 预算，并保存 task_id 与 budget_ref 的绑定。传入引用仍逐项核验；省略引用不能绕开已经适用的约束。用途含糊或多个记录重叠先澄清选择适用范围，不能由模型挑较宽松限额；明确不适用的预算不跨月份、账户或用途套用。采用的预算与生日当次 budget_fen 同时生效，不能把个人总限额直接当本次可花金额。

06 在方案确认前、恢复后及每次新资金承诺前重新调用 L01 summary，按当前消费净额计算 remaining，不复用采用时的余额。冻结本身不计消费：同预算已绑定任务的未消费承诺额另计占用，未知付款继续占用，银行已入账消费不重复计占用；本次新增承诺不得超过 remaining 减其他有效占用及本任务已有占用后的金额。后端按 budget_id 串行校验并记录占用，成功消费转为账单事实，确定未使用且释放成功才撤销对应占用；不引入银行限额引擎。按同一 budget_id 汇总所有版本尚未结清占用，换版本不能漏掉在途旧任务；预算版本变化、事实不足或余额不足时停止新增承诺，回到原任务澄清／调整，不擅自提高预算，也不影响 §3.5 限定释放。

预算占用保存在 06 原任务的受控业务记录中：`budget_ref:BudgetRef / task_id:ID / commitment_id:ID / committed_fen:Money / unconsumed_fen:Money / freeze_id:ID|null / operation_ids:UUID[] / settled_transaction_ids:ID[] / state:pending|active|unknown|closed / updated_at:Timestamp`，由确定性代码更新，不由模型填余额。提交冻结前持久化 pending 占用；冻结明确失败撤销，未知保留并只查原操作；绑定任务重新规划沿用或调整原占用，不重复占用。以银行交易编号将消费与占用核对，同一笔不得既算已用又算未消费占用。预算规则只约束本应用发起的后续任务，不保证银行外部并发支出不会改变余额；发现新事实后停止新增承诺。

任务查询、补充输入、取消与恢复复用第 6 章平台入口，不另发明 cross 私有恢复接口。部分成功逐项保留已成功结果；未知先核对，成功项不重办；取消停止未执行的购买／转账部分，不撤回订单或已支付资金；生日任务必须按 §3.5 完成限定释放收尾。

### 5.9 计算口径补充（09-24，Erwin 已确认）

1. **比例分配尾差**：存在留在主账户的一份时，各转出份额向下取整到分，剩余全部留主账户；不存在留存份额时，按最终确认单的固定顺序，前面各份向下取整，最后一份取得剩余金额。仅对已明确要分配的总额计算，不把未纳入分配的余额转走。最终金额在确认单逐项展示，执行时不重排份额；合计必须等于分配总额。100.01 元按 60/20/20 分配，转储蓄 60 元、转家庭 20 元、留存 20.01 元。
2. **跨月退款**：按退款实际入账时间归入账月并抵扣该月净消费，类别继承原消费且保留原交易关联；不回写原消费月份。消费支出、退款与净消费分别提供。8 月消费 800 元、9 月退 300 元，8 月消费仍为 800 元，9 月计入退款 300 元。
3. **月均消费按 30 天折算**：`monthly_average_fen = consumption_gross_fen × 30 ÷ statistical_days`，用确定性计算，最终四舍五入到整数分；先乘后除，不先把日均取整。分子仅为统计范围内实际花出去的消费支出，不扣退款、不混入转账或冻结。统计天数按北京时间统计区间覆盖的自然日期计算，开始日计入，结束时刻为零点时该日不计入；截至今天的查询计入今天，不把尚未到来的日期算入分母，有效截止不超过数据截至时间。多账户共享同一期间天数，不按账户数累加。有效统计天数为 0 时月均为 null 并说明原因；有天数但无消费时为 0。非整月同样可折算，标明真实期间和「按 30 天折算」；该数不是预测未来实际支出。20 天消费 600 元、退回 200 元：月均 900 元，期间净消费另记 400 元；即使退款超过消费，月均仍只看消费支出。
4. **周期扣款金额**：规则 4 首版要求同一商户、扣款金额整数分完全相同；39 / 39 / 42 元不按此规则命中，不引入金额浮动阈值。
5. **周期与日期容差**：只识别每月扣款，连续至少 3 个自然月各有匹配扣款，缺月不算连续。以候选序列首笔日期为锚点推算每月预期日，实际日与预期日最多相差 3 天（含边界），不逐月移动锚点造成漂移；首笔在月末则后续按各月实际月末对齐。每笔交易在同一序列只匹配一次，同月多笔不能凑足 3 个月。只提示疑似周期扣款，不能断言扣错或自动取消订阅，无后台主动推送。

### 6.3 登录口径（09-24 第六批已确认）

**演示环境固定演示用户 + 自动登录**。登录状态由模拟银行提供。会话从建立起按真实时间固定 2 小时有效，刷新页面沿用原会话、不重新计时。到期提示「演示登录已过期，点击重新进入」，点击后建立新会话。演示管理页另提供「立即使当前登录会话过期」，后端校验管理权限并立即使目标会话失效，便于演示过期分支。

过期保留任务及业务记录，但旧会话的确认和验证不能直接用于新会话；继续未提交动作需重新确认、按风险规则重新验证。已经提交银行的操作不会因会话过期自动撤销，恢复合法登录后先查原操作结果，不得重发；管理页提前过期遵循同一规则。环境整体重置仍按第 7 章使旧任务失效，与单纯会话过期保留任务区别处理。

### 6.4 HTTP 共同约定与聊天

所有路径前缀 `/api/v1`，下表省略。JSON 字段沿用 §5 类型与命名。成功返回 `{data:T}`；已受理且后台运行返回 HTTP 202，data 中说明状态；拒绝返回 `{error:ModuleError}`。HTTP 200 / 202 不等于转账成功，业务只认 data 中任务与银行结果。错误：400 为参数格式、401 为登录无效、403 为无权限、404 为当前用户范围内不存在、409 为版本 / 重复请求冲突或对象已失效、503 为依赖不可用。正常 waiting_input / waiting_approval / needs_attention 返回任务快照，不包装成 500。

登录凭据使用服务端会话及 HttpOnly Cookie，生产部署要求 HTTPS 和 Secure；修改请求验证同源 / 防 CSRF，普通前端不传 user_id 或 role。固定演示用户只适用于演示环境；管理员身份来自服务端受控配置，不能靠前端 role=admin 获得。普通演示登录不自动授予管理权限。管理身份如何部署配置属于实现配置项。

所有会改变任务、确认、导出或演示状态的 POST 带 `request_id:UUID`，客户端在首次发送前保存，重传沿用；同用户 / 轮次 / 入口同号同内容返回原受理结果，同号异内容 409。该编号既不替代银行 operation_id，也不用于自动重做未知交易。验证码 / 人脸另带确认验证字段附件的 submission_id；请求和响应内容按 §4.5 脱敏，验证码路径禁记请求 / 响应秘密。资源归属、会话有效性与当前轮次均由后端核验，ID 不是访问凭证。

| 编号 / 方法与路径 | 输入 | data 返回与语义 |
|---|---|---|
| F01 POST `/session/enter` | request_id | SessionView；首次进入或过期后用户点击重新进入，建立固定演示用户会话；已有有效会话则复用，不续期 |

| F03 POST `/threads` | request_id | ThreadView；建立新对话，不等于新登录会话 |
| F04 GET `/threads` | cursor?、limit? | Page<ThreadView>，本人当前演示轮次的对话 |

`SessionView`：`session_id / user_display / role:user|admin / demo_round_id / created_at / expires_at`；角色只由服务端输出，不返回登录凭据。`ThreadView`：`thread_id / title / created_at / updated_at / demo_round_id`。`MessageAccepted`：`message_id / thread_id / accepted_at / task_id:ID|null`，任务稍后产生时由 SSE 与历史查询补充关联。`MessageView`：`message_id / thread_id / role:user|assistant / text:string / created_at / task_ids:ID[] / report_ids:ID[]`；草稿流片段不算最终消息。

`Page<T>`：`items:T[] / next_cursor:string|null`；limit 默认 50、范围 1—100；游标不透明，只用于继续同一筛选条件的读取。该分页仅用于应用列表和历史，不改变银行流水一次完整返回的约定。列表按创建时间与 ID 稳定排序，不因更新进度重复或跳过记录。新登录会话可查看同用户当前轮次历史，但继续旧业务须遵守 §6.3。

本期验证码与模拟人脸各 5 分钟；模拟人脸实际成功 / 失败由 F27 管理入口作答，不存在真实识别服务调用。中风险任一失败或超时终止；低风险错误次数和重发沿用 §4.2。前端刷新和断线不能延长计时。

F36 的 payee_search.fields 为 `kind:name|phone|account_number|remark / value:string`，仅在任务需查找收款人时接受；后端调用 B03，detail_ref 引用受控查询结果，candidates 返回脱敏候选（无匹配为空列表），其他 kind 的 candidates 为 null。多候选用 F10 的选项继续原任务，不能默认选首个；查询原文不回传聊天、模型或审计。payee.fields 为 `account_number:string / account_name:string`，由后端构成银行 PayeeInput 并调用 B04，匹配成功才保存可办理引用及含开户行的展示；不匹配要求纠正资料，不生成可执行目标；delivery.fields 为 `recipient_name:string / phone:string / address:string`，供订单交付。后端绑定当前用户、任务和交互，校验后返回引用与掩码展示值；模型只接收所需引用和展示内容，实际办理时从受控记录取值。修改已确认对象或地址使原确认失效。资料引用的存储与清理服从安全 / 任务生命周期，不因表单提交自动变成长期记忆。

### 6.6 SSE 与断线恢复

事件外壳：`event_id:ID / thread_id:ID / session_id:ID / task_id:ID|null / run_id:ID|null / module:string / event_type:string / occurred_at:Timestamp / payload:按类型定义`。SSE 的 id 为 event_id。事件类型：

| event_type | payload | 前端用途 |
|---|---|---|
| message_delta | message_id、text_delta | 可选助手回复流片段，仅渲染文本；不能由文字触发提交或确认 |
| message_completed | MessageView | 完整回复落地，覆盖临时片段，按 message_id 去重 |
| task_updated | TaskView | 展示进度、计划步骤与当前状态；`data` 按 `module` 解释（口径见 §6.5；2026-10-14 轻量确认档，Issue #122） |
| interaction_required | task_id、InteractionRequest | 拉取正式确认 / 验证视图或展示澄清，不携带验证码 |
| report_ready | task_id、report_id | 按 F21 读取卡片，不广播全量交易明细 |
| session_expired | session_id、reason | 停止需登录的交互，提示重新进入 |
| stream_error | ModuleError | 流或连接故障；不据此将任务标为失败 |

首版以完整消息和任务快照为可靠来源，message_delta 为可选展示，不保证模型供应商均支持流式。不要求持久化并重放所有 SSE 片段；Last-Event-ID 不构成补齐保证。重连时先连事件流，再用 F06 / F08 / F09 拉历史与快照，期间缓存新事件；按 ID 去重并以 task_revision 拒绝更旧的任务快照；该版本由后端每次任务状态或交互变更时递增，避免同一时间戳乱序。收到更新提示可重新 GET 当前任务，避免旧事件覆盖新状态。前端从不因重连重发业务消息或银行写动作。会话过期即使未收到 SSE，也由后续 401 触发同一过期界面。管理员运行日志不走普通聊天 SSE。

### 6.9 平台内部注册与受控引用

`ModuleManifest`：`module_name / version / owner / description / implementation_kind:workflow|agent / capabilities:CapabilityDefinition[] / dependencies:string[]`。每项 CapabilityDefinition 为 `name / input_schema_ref / output_schema_ref / required_permissions:string[] / operation_level / side_effect:bool / confirmation_policy:none|per_action / timeout_ms:正整数 / retry_policy:none|read_only / handler_ref`。名称唯一，引用实际可解析公共类型，缺字段拒绝注册；只读查询重试不能套用到业务写入。敏感动作依安全策略执行，声明本身不能降低风险等级或替代逐动作验证。

处理函数逻辑签名统一为 `handle(input, trusted_context) → ModuleResult`；trusted_context 来自服务端，不放到模型可编辑的输入 schema。私有工具使用相同权限 / 副作用 / 确认 / 超时 / 重试声明并经公共执行器调用；模块不能借私有工具绕过审计。具体模块开始 / 查询语义按 §5，暂停通过平台适配返回 InteractionRequest。

`ResourceRef`：`resource_id / owner_user_id / task_id / purpose / media_type / size_bytes`。引用由服务端创建与读取，业务只在获准任务范围内使用 resource_id，不得把路径当作任意文件读取能力。重置清理临时任务材料前，审计与恢复必需证据须已持久化到各自存储；普通用户不能通过引用读取内部模型上下文。本期不另设定时清理时长，临时材料保留到演示重置；框架后端适配和模型配置文件格式属于实现选型，不改变此接口。记忆使用 §7.5 的框架机制与禁止清单，不另建每次保存确认接口。

资源读取另由平台关联的受控任务／会话记录核验会话、演示轮次及用途，不仅检查用户编号。新会话恢复旧任务时先按 §6.3 核对归属及在途，再建立当前会话的访问授权，旧确认和验证不能随资源复用；跨任务引用须检查来源、目标和委派范围。无需为此改变 ResourceRef 对外字段。旧轮次普通资源不可继续办理业务，历史审计证据仍按独立管理权限和获准历史轮次读取。

### 6.11 字段类型与一致性补充

本章表格省略的类型统一如下，不让实现方各猜一套：

- 所有 `*_id / *_ref` 为 ID；`request_id / submission_id / operation_id` 为 UUID；`*_ids / *_refs` 为对应类型列表；`*_at` 为 Timestamp；显式标 null 的允许空，未标的必填。URL 路径内 ID 从路径读取，不在请求体重复提供。
- `text / title / user_display / role / module / reason / phase / kind / media_type / file_name / download_path / evidence_status / missing_reason / action` 为 string，其中已列枚举的只允许对应值；`limit` 为整数，`cursor` 为 string，`effects` 为 string[]；各 ? 输入可省略，不把缺失与用户提供空串混为一谈。
- F36 的 `display_fields:DisplayField[]` 引用确认验证定义；SessionView.created_at / expires_at 使用真实时间，DemoView.initial_logical_at / logical_at 使用模拟业务时间；`faults.target_user_id:ID / kind:slow_transfer_6s / armed:bool`。
- ModuleResult.task_id / run_id 属任务语义，不是银行编号；query / export / admin 三类结果各自保留结构，禁止把其 success 当银行交易成功。TaskView.task_revision 单调增加，所有对外任务快照及 task_updated 携带同一版本。
- CategoryTotal.category 与 SpendingComparison.largest_change_category 使用银行 Category 代码，不在同一字段混用中文展示名；rank 为确定性金额排序，金额相同按银行 Category 顺序稳定排列。share_bps 和 change_bps 仅为展示比例，最后四舍五入，不影响整数分账本；占比因取整不要求相加精确等于 10000，界面不得为凑总额改金额。
- income 分配的目标本人账户转为 PayeeInput.kind=own，已保存收款人转 saved；二者都由银行核验，不能把 A5 本人账户要求成第三方常用收款人。跨模块 Ectx、Permission、risk / decision 代码值统一引用安全与审计附件。
- 模型调用、时间线和文件内容都使用受控输出，不将 ResourceRef.owner_user_id 等内部字段开放给模型自行选择。F19 的模拟码响应不计入普通内容快照，验证码提交的去重结果不能保存其明文请求。
- ExportView.task_id：敏感明细导出任务必填，普通卡片或管理审计导出无业务任务时可空；下载为文件响应而非 JSON data。HTTP 成功不等于所有字段有可执行授权。
- 本期上传语音、真实短信、人脸服务、第三方分享授权均不在这些接口中；前端不得因 PRD 示例存在语音 / 转发措辞而注册本期未提供的能力。

### 7.1 一次性故障与模拟结果

慢 6 秒等故障只作用于**指定演示用户的下一次对应操作**，触发一次后自动恢复正常。管理页显示「待触发 / 已触发」，避免影响后续演示；涉诈场景继续使用既有种子账户，不以开关放宽银行规则。重复查询原操作不重新触发故障。**模拟人脸按第六批修订为当前验证的前端「成功 / 失败」按钮**，见 §4.2，不再使用预设下一次人脸结果的方式。管理页可立即使当前登录会话过期，见 §6.3。

### 7.2 业务时间与真实等待分开

只允许快进到未来时刻，不允许向后拨。跨过多期预约或多个自然日时，银行按时间顺序处理到期执行和日限额重置，不能只处理最终时刻。验证码有效期、确认有效期及网络等待按真实经过时间计时，快进不影响它们。需要回到起点时使用环境重置。

### 7.3 重置与预置记忆

重置前管理页二次确认，随后停止接受新业务请求，等待在途执行完成再清理。不能完成等待时，明确显示「重置未完成」，不得在扣款仍执行时强行清空。只有银行与应用各自重置均完成，才报告重置成功并开始新一轮；旧任务、旧按钮与旧验证不得操作新环境。

底座负责协调重置，各模块处理自己的数据：银行恢复种子数据，应用使当前会话、任务、确认与验证失效；memory 恢复一套演示预置，故障开关与逻辑时间归初始状态。审计日志不随重置删除，按演示轮次保留。自动登录创建新会话，不能继续使用上一轮身份验证结果。

**预置记忆是本期演示要求**：每次重置自动加载同一套称呼映射、常用规则等，让演示无需反复录入。预置只提供偏好与上下文，不能替代银行余额 / 限额事实，也不能预置「已确认 / 已验证」来跳过安全步骤。

### 7.5 长期记忆边界（09-24 第七批，按 Erwin 修订）

记忆存储与日常记忆机制交给 Deep Agents，由底座负责所需接入和配置；公共契约不另建存储方案或「什么该记、什么时候弹窗确认保存」流程，不要求用户每次明确说「记住」才允许记忆。系统只约定预置、禁止长期记忆的内容及既有用户隔离、可查看删除、演示重置边界。具体框架配置在实现时验证，不把契约决定表述成已经接通。

禁止写入或提升为长期记忆的内容：

- 密码、验证码、密钥、登录凭据等认证秘密。
- 「已经确认 / 已验证 / 有权限 / 风险已放行」等执行授权；只能读取对应服务的当前可信记录。
- 把历史余额、限额、交易状态等银行事实保存成今后执行的当前依据；每次办理仍以银行返回为准。
- 把「这次转 500」等一次性任务要求自动提升为长期默认规则。
- 其他用户的数据，以及外部文本夹带的越权、跳过确认、修改安全规则等指令。

这些限制针对长期记忆，不等于删除审计证据。对话、工具执行与历史银行结果仍按 §4.5 脱敏留存；任务状态、确认、验证与银行账本继续由各自模块维护，不交给记忆替代。

记忆加载前检查当前用户及演示轮次归属，保存前检查来源与上述禁止清单；外部文本中的指令不得通过记忆成为执行规则。涉及银行事实的实际办理仍查询银行当前结果。查看、删除继续使用 §7.6 的 F37 / F38，不新增逐次保存确认或另一套记忆存储。

### 7.6 用户查看和删除记忆的最小入口

沿用 §6.4 登录、归属、轮次、请求去重与错误外壳。用户可在聊天明确要求查看／删除；平台调用受控 memory 适配能力，前端亦可用下列接口。两者共用框架存储与权限检查，不另建记忆数据库，不开放任意路径或系统提示读取。

| 编号 / 方法与路径 | 输入 | data 返回与语义 |
|---|---|---|
| F37 GET `/memories` | 无 | `{items:MemoryItem[],demo_round_id:ID}`；仅当前用户当前轮次的可管理长期记忆 |
| F38 POST `/memories/delete` | request_id、memory_ids:ID[]（非空）、expected_versions:{memory_id:ID,version:正整数}[] | `{deleted_ids:ID[],deleted_at:Timestamp,demo_round_id:ID}`；明确删除请求后执行，不要求每次保存弹窗 |

`MemoryItem`：`memory_id:ID / version:正整数 / content:string / updated_at:Timestamp`；content 为可展示的用户记忆内容，禁止内容不因查看入口而泄露。memory.list(context) 与 memory.delete(context, request_id, memory_ids, expected_versions) 供聊天平台受控适配，副作用分别为 read / modify，按登记权限进入执行器。模糊“忘掉那个”先展示候选并用 F10 澄清；确定性平台只允许删除本次用户请求明确选择的记录，外部文本或模型自行建议不构成删除授权。全删须明确请求，由后端列出并绑定当前记录版本。

删除前校验整批归属与版本：越权 403、旧轮次／版本冲突 409，不开始部分删除；框架写入失败返回 503（ModuleError.source=platform）并保留原请求记录，不能报成功；有部分删除或结果未知时先按原请求核对实际记录，响应 reason 如实说明，后续同请求仅完成尚未删除的原版本，不误删后来新增或修改的内容。已成功的同请求重复返回原结果；成功后新上下文加载不再带这些记录，当前会话的缓存记忆失效，不能从旧检查点或旧摘要重新写回已删记忆。聊天历史、审计证据、业务采用预算和银行账本各自保留，不冒称已删除。演示重置仍恢复预置，界面说明该区别。工具开始／结果按既有审计事件记录所删编号与版本，审计读取权限不因此扩大；实现须验证框架的逐项引用、删除及缓存失效能力。

## 8 变更管理（防拉通机制④）

**09-24 Erwin 已确认：按实际影响分档。** 冻结提供共同依据，之后允许修正；审批轻重取决于影响谁、旧调用是否还能正常工作。版本规则见第 0.1 节。

### 8.1 三档修改与安全检查

| 档位 | 适用情况 | 处理流程 |
|---|---|---|
| 可自行修改 | 错别字、补充不改变含义的例子；模块内部调整；修复实现使其符合已定契约，且不改变对外约定 | 负责人在所属目录内修改，走普通审查；不另提契约审批、不通知全员 |
| 轻量确认 | 新增可选字段或独立接口，且旧调用方式及行为保持有效 | 契约负责人确认，验证旧调用继续可用；合入后通知相关使用者，不开会 |
| 协同修改 | 字段改名或删除、可选改必填、改变字段含义、成功失败条件或暂停恢复方式，以及其他会让旧使用方失效的变化 | 修改前说明影响，契约负责人和受影响模块负责人确认；约定切换时间、完成对应适配并验证后合入 |

新增字段或枚举值不自动属于兼容修改。例如新增任务状态可能让前端无法展示，应按实际影响协同确认。任何人可提出需求；公共契约由 Erwin 收口，业务开发者仍遵守目录边界。

**安全检查叠加在三档之上**：涉及权限、确认、身份验证、资金执行、重复扣款防护、隐私或审计规则，必须由 Ringo 审查；涉及银行边界同时由 Erwin 确认。即使只改一行或名为「修 bug」，也按实际影响判断。业务流程涉安全必须主动告知 Ringo。

### 8.2 一份简短记录与定向通知

一次契约修改在 PR 中说明四件事即可，不另写审批文档：

1. 为什么改。
2. 原来是什么、现在是什么。
3. 影响哪些模块与使用方。
4. 旧代码是否仍可用；不可用时如何一起切换，以及验证结果。

小改动可当天确认；只有意见分歧或需要多条业务线共同讨论时才开会。轻量修改合入后通知相关使用者；协同修改提前通知并确认切换时间，合入后通知相关使用者同步代码。仅在全员受影响时通知全员，无关模块继续开发。

修改公共约定时，同步契约文档、对应公共模型和必要示例，记录本次修订；验证围绕受影响的调用与行为展开。首次开发期可协调相关 PR 按依赖顺序在同一窗口合入，不强求长期保留两套接口，也不把未完成适配的中间状态作为联调基线。

### 8.3 AI 协作规则

先判断是实现不符合契约，还是契约确实需要调整。前者在本模块修复；后者列出修改前后、使用方和影响，交契约负责人处理。不得为让自己的模块跑通，擅自改公共字段、复制一套契约或放宽安全规则。AI 可以发现问题、准备方案和执行已批准的修改；共同约定的变化由相关负责人确认。

## 附 A · 防反复拉通的四个机制（写契约时逐条自检）

1. **单向依赖**：银行 / 安全是纯提供方，业务是消费方；业务间只走公开能力表，伸手进对方内部即契约 bug；
2. **条目自带验收例**：每条契约挂至少一个验收例，判据内嵌；
3. **异常自治**：边界内的事各模块自己定，契约只管边界上的一来一回；
4. **变更管理**：冻结后「拉通」从开会变成走流程——没有第 8 章，前三条撑不过两周。
