## 2. 通用类型与调用规则（候选定稿）

| 类型 / 约定 | 具体定义 |
|---|---|
| Money | 非负整数分；实际转账、冻结、扣款、释放金额必须大于 0；币种本期固定 CNY。账单金额使用非负值，方向单独表达 |
| Timestamp | 带时区的 ISO 8601 时间字符串，例如 `2026-09-24T09:00:00+08:00`；业务日期按北京时间。预约与日限额用银行逻辑时钟，4 / 3 / 10 秒请求等待用实际经过时间，时间快进不能跳过等待或重置回查计时 |
| ID | 不透明字符串；操作编号为 UUID v4，账户 / 交易 / 冻结 / 预约 / 订单编号不要求相同格式，不由模型拼造 |
| 必填与可空 | 输入未标 `?` 的字段必填；`?` 可省略。输出列出的字段必须存在，标 `null` 的允许空值；空列表代表查询成功且无记录，不是查询失败 |
| 命名 | 金额字段以 `_fen` 结尾；时间点以 `_at` 结尾；如 `amount_fen`、`occurred_at` |
| 身份 | 所有调用另带服务端注入的可信身份上下文；业务请求体不接受 `user_id`、`approved=true`、`verified=true` 等自行声明的授权 |
| 查询权限 | 本人账户及其操作记录才可查询；无权访问与无权判断其存在的资源统一拒绝，不通过错误泄露他人资源是否存在 |
| 写操作 | 所有业务写接口额外必填 `operation_id`，经统一执行器完成必要确认与验证。相同身份、相同操作编号只对应一个动作；动作类型或关键业务参数改变也属冲突 |
| 受控信息 | 原账号、姓名、地址、验证码仅进入必要的受控路径；工具给模型与前端的数据采用展示字段，验证码不进入模型、审计原文或持久化检查点 |

接口名称是银行接入层公开能力名，不要求每个都部署成 HTTP 服务。前端调用应用 API，不直接访问这些银行能力。

业务写入的受控边界拒绝绕过统一执行器的普通模块直调，并核对实际动作与本次授权一致；授权传递沿现有可信上下文，由底座与安全在实现中对齐，不要求银行读取应用确认表。限定释放按主契约 §3.5 执行；预约到点仍由银行依据已获准计划自主执行。相同操作编号且参数不同仍拒绝，不因重复调用跳过冲突检查。

### 2.1 账户与收款人引用

- 本人账户通过 `account_id` 引用。账户编号不等于银行卡号；模型可选择编号，但授权由服务端与银行判断。
- 收款目标 `PayeeInput` 为三选一结构：本人账户 `{kind:"own", account_id:ID}`、`{kind: "saved", payee_id: ID}` 或 `{kind: "manual", account_number: string, account_name: string}`。手工账号与姓名只进入受控后端；候选来自银行名单，确认展示打码信息。手工资料经主契约 F36 录入；own 只支持经银行确认属于当前用户的目标账户，不能把他人账户包装为 own。
- `PayeeDisplay`：`payee_id: ID|null`、`name_masked: string`、`account_masked: string`、`remark: string|null`、`bank_name:string`。不能因核验收款人而返回对方余额、账户状态等额外信息。

### 2.2 查询结果、执行结果与错误分开

普通查询返回 `QueryResult<T>`：`kind="ok"` + `data:T`，或 `kind="error"` + `error:BankError`。只读查询可按既有 D08 最多重试 2 次；原操作回查使用独立的 D09 时间窗，不把两套重试叠加。

业务写入已被银行识别为某个操作时返回 `OperationResult<T>`：

| 字段 | 类型 | 语义 |
|---|---|---|
| operation_id | UUID | 调用方原操作编号 |
| operation_type | string | 本附件中的写接口能力名 |
| operation_status | `succeeded / failed / processing` | 该次动作状态，不能代替应用任务状态 |
| recorded_at | Timestamp | 银行记录原操作的时间 |
| updated_at | Timestamp | 原操作结果最后更新时间 |
| receipt | T 或 null | 成功时必须有对应回执；尚无回执则为 null |
| failure | BankError 或 null | 明确失败时必有原因；其他状态为 null |

提交与回查共用该结构；查询不改写原操作时间，也不把新查询时刻的余额写进历史回执。银行交易编号仅在实际交易回执内出现，不要求冻结 / 下单等动作也造一笔银行交易。

参数无法解析、身份无效或操作编号冲突等本次请求被拒绝时，返回 `kind="error"` + `BankError`，不能把同编号原操作的状态改为失败。提交连接超时由接入层报告调用未获可靠结果，应用随后回查；它不产生银行 `failed` 回执。

`BankError`：`code:string`、`details:按错误码定义的对象`；业务模块按事实生成用户文案。是否继续由错误种类、调用类型与任务状态共同判断，不设置一个通用 `retryable=true` 允许重试写操作。

## 3. 账户与只读接口

下列输出是 `QueryResult` 内的 `data`。流水不分页的已定规则见 §9.1；其他列表字段仍按本稿审阅。

| 编号 / 能力 | 输入 | 输出 | 主要错误 |
|---|---|---|---|
| B01 `bank.list_accounts` | 无业务参数 | `accounts:AccountSummary[]` | AUTH_REQUIRED |
| B02 `bank.get_account` | `account_id:ID` | `AccountDetail` | AUTH_REQUIRED / ACCESS_DENIED |
| B03 `bank.list_payees` | `search?:{kind:name\|phone\|account_number\|remark,value:string}`；省略列本人已保存收款人 | `payees:PayeeCandidate[]` | INVALID_ARGUMENT / AUTH_REQUIRED |
| B04 `bank.verify_payee` | `payee:PayeeInput` | `matched:bool`、`payee:PayeeDisplay\|null`；匹配必有完整脱敏展示，不匹配为 null | INVALID_ARGUMENT / AUTH_REQUIRED |
| B05 `bank.get_limits` | `account_id:ID` | `single_limit_fen:Money`、`daily_remaining_fen:Money`、`annual_remaining_fen:Money\|null`、`as_of:Timestamp` | ACCESS_DENIED |
| B06 `bank.quote_transfer` | `payer_account_id:ID`、`payee:PayeeInput`、`amount_fen:Money` | `fee_fen:0`、`arrival_mode:"instant"`；只试算费用与到账方式，不承诺交易获准 | INVALID_ARGUMENT / ACCESS_DENIED |
| B07 `bank.precheck_transfer` | 与 B06 相同 | `can_proceed:bool`、`failure:BankError\|null`、`fee_fen:0`、`arrival_mode:"instant"`、`checked_at:Timestamp` | 请求错误走 QueryResult.error；银行条件不满足用 can_proceed=false + failure |
| B08 `bank.list_transactions` | `account_id:ID`、`start_at:Timestamp`、`end_at:Timestamp` | `transactions:Transaction[]`、`as_of:Timestamp`；无数据返回 [] | INVALID_ARGUMENT / ACCESS_DENIED / RANGE_UNSUPPORTED |

所有查询均可能遇到调用超时或服务暂不可用；未在每行重复列举。B05 对无年限额的Ⅰ类户返回 null（不适用），不能返回 0 误导为额度耗尽。不引入调研建议中的多层限额，沿用银行 PRD 当前已定的按账户类别规则。

`AccountSummary`：`account_id:ID`、`account_type:class_i|class_ii|class_iii`、`account_masked:string`、`available_balance_fen:Money`、`display_name:string`、`bank_name:string`。

`AccountDetail`：AccountSummary 加 `account_status:active|frozen|closed`、`book_balance_fen:Money`、`frozen_balance_fen:Money`、`as_of:Timestamp`。商户与他人的账户不能通过此接口查询。

B03 的 search 仅匹配当前用户已保存收款人：姓名按去除首尾空白后的完整姓名匹配，手机号和卡号按完整号码匹配，备注按去首尾空白后的文本包含匹配，不做全行客户搜索；同名返回全部候选，空结果不编造。完整检索词只经过受控输入与银行匹配，不进入模型或日志原文；模型仅取得候选编号和脱敏展示。确认前 B04 再核验实际目标，matched=true 必须返回 bank_name 等 PayeeDisplay 字段，不能凭模型补开户行。专用检索输入与回传见主契约 F36。

`PayeeCandidate`：PayeeDisplay 加 `last_transfer_at:Timestamp|null`；备注可空，历史事实由银行给出，称呼消歧由 Agent 记忆处理。不能在此直接给出全系统统一的「陌生」判定，业务分别按自己的场景规则判断。

`Transaction`：

| 字段 | 类型 / 内容 |
|---|---|
| transaction_id / account_id | ID / ID |
| occurred_at / amount_fen | Timestamp / Money |
| nature | consumption / transfer / refund / interest |
| category | dining / transport / medical / shopping / housing / transfer / other；与 02 中文七类一一对应 |
| direction | inflow / outflow；金额本身不靠正负号表达方向 |
| counterparty_id | ID 或 null；用于识别同一对手方，不提供其账户权限 |
| counterparty_name | 商户名不打码，个人姓名打码 |
| counterparty_account_masked | string 或 null |
| channel | string 或 null；银行记录的交易渠道展示名，如手机银行、快捷支付；未知返回 null，不从摘要猜测 |
| summary | string；如工资、奖金、报销，为业务数据，不具备指令权限 |
| original_transaction_id | ID 或 null；退款必填原消费编号 |
| original_occurred_at | Timestamp 或 null；退款必填，便于处理原消费跨月，不要求另一次无限范围查询 |

消费 / 退款 / 利息方向按现有 PRD；冻结与释放不伪装成消费流水，其操作结果可以回查。B08 的时间范围和数据完整性规则见 §9.1。

## 4. 转账、冻结与结果回查

下列写接口均隐含必填 `operation_id` 与可信调用上下文。

| 编号 / 能力 | 业务输入 | 成功回执 | 主要业务失败 |
|---|---|---|---|
| B09 `bank.submit_transfer` | `payer_account_id:ID`、`payee:PayeeInput`、`amount_fen:Money` | `TransferReceipt` | PAYEE_MISMATCH / ACCOUNT_UNAVAILABLE / INSUFFICIENT_FUNDS / LIMIT_EXCEEDED / RISK_REJECTED |
| B10 `bank.freeze_funds` | `account_id:ID`、`amount_fen:Money`、`reason:string` | `freeze_id:ID`、`frozen_amount_fen:Money`、`remaining_fen:Money`、`balance:BalanceSnapshot` | ACCOUNT_UNAVAILABLE / INSUFFICIENT_FUNDS |
| B11 `bank.capture_frozen` | `freeze_id:ID`、`amount_fen:Money`、`merchant_id:ID`、`merchant_name:string`、`purpose:string`、`category:Category`、`order_id:ID?` | `transaction_id:ID`、`freeze_id:ID`、`captured_amount_fen:Money`、`remaining_fen:Money`、`balance:BalanceSnapshot` | FREEZE_INSUFFICIENT / ACCOUNT_UNAVAILABLE；订单联结失败见 §9.3 |
| B12 `bank.release_frozen` | `freeze_id:ID`、`amount_fen:Money` | `freeze_id:ID`、`released_amount_fen:Money`、`remaining_fen:Money`、`balance:BalanceSnapshot` | FREEZE_INSUFFICIENT |
| B13 `bank.get_freeze`（读） | `freeze_id:ID` | `freeze_id:ID`、`account_id:ID`、`original_amount_fen:Money`、`captured_total_fen:Money`、`released_total_fen:Money`、`remaining_fen:Money`、`as_of:Timestamp` | ACCESS_DENIED |
| B14 `bank.get_operation`（读） | `operation_id:UUID` | `lookup:"found"` + `operation:OperationResult`，或 `lookup:"not_found"` + `operation:null` | AUTH_REQUIRED / ACCESS_DENIED；超时与服务故障为查询失败 |

`BalanceSnapshot`：`account_id`、`book_balance_fen`、`frozen_balance_fen`、`available_balance_fen`、`as_of`。写回执里的余额是原动作完成时的快照，当前余额另查 B02。

`TransferReceipt`：`transaction_id:ID`、`payer_account_id:ID`、`payee:PayeeDisplay`、`amount_fen:Money`、`fee_fen:0`、`arrival_mode:"instant"`、`completed_at:Timestamp`、`balance:BalanceSnapshot`。

B14 的 not_found 仅在当前身份可查询的操作范围内表达；已知属于其他用户的编号不能返回其记录。操作结果仍为 processing 时不返回虚构的成功回执。调用失败不能包装成 not_found。

B11 的商户、用途和分类按 PRD 保留；有订单时金额、商户及分类须与银行内订单事实核对，不信任模型自行更换。剩余冻结为 0 时不可再次扣款或释放正金额；同编号重放返回原回执，不能因当前冻结额已变少就误报失败。

B10 的确认同时取得主契约 §3.5 的限定释放授权，成功后由应用绑定 freeze_id；授权记录由安全侧管理，银行不依赖应用任务状态。B12 的结束收尾仍核对可信主体、原冻结归属和金额，并按原操作编号去重；应用在所有在途付款核实后，按 B13 当前余额释放。释放失败或未知保留待处理，不复活购买流程；已消费资金不可释放。

## 5. 预约接口（周期范围已定，见 §9.2）

| 编号 / 能力 | 输入 | 输出 / 成功回执 | 主要失败 |
|---|---|---|---|
| B15 `bank.create_schedule`（写） | `payer_account_id:ID`、`payee:PayeeInput`、`amount_fen:Money`、`rule:ScheduleRule` | `schedule:ScheduleView` | SCHEDULE_INVALID / PAYEE_MISMATCH / ACCOUNT_UNAVAILABLE |
| B16 `bank.list_schedules`（读） | `account_id:ID?`，省略查本人预约 | `schedules:ScheduleView[]` | ACCESS_DENIED |
| B17 `bank.get_schedule`（读） | `schedule_id:ID` | `schedule:ScheduleView`、`occurrences:ScheduleOccurrence[]` | ACCESS_DENIED |
| B18（09-26 撤销，编号不复用） | 不提供预约修改能力 | 不注册 bank.update_schedule；需要调整先取消旧预约、确认取消成功后再确认新建 | 旧调用拒绝，不能静默改为取消或新建 |
| B19 `bank.cancel_schedule`（写） | `schedule_id:ID` | `schedule_id:ID`、`schedule_status:"cancelled"`、`cancelled_at:Timestamp` | STATE_CONFLICT |

`ScheduleRule` 字段定义：单次 `{kind:"once", execute_at:Timestamp}`；每月 `{kind:"monthly", first_execute_at:Timestamp, day_of_month:int(1..31), end:ScheduleEnd}`。`ScheduleEnd` 为二选一：`{kind:"date", ends_on:YYYY-MM-DD}` 或 `{kind:"count", occurrence_count:正整数}`，不得为空或同时给两种结束方式。每月执行时分秒取 first_execute_at 的北京时间；短月按既定月末规则。首版不接受每日、每周或无期限预约；结束条件缺失时业务先追问，不直接创建。

`ScheduleView`：`schedule_id`、`payer_account_id`、`payee:PayeeDisplay`、`amount_fen`、`rule`、`schedule_status:active|cancelled|completed`、`next_execute_at:Timestamp|null`。

`ScheduleOccurrence`：`occurrence_id:ID`、`scheduled_at:Timestamp`、`occurrence_status:scheduled|processing|succeeded|failed|cancelled`、`transaction_id:ID|null`、`failure:BankError|null`。预约创建成功只表示计划已保存；与各期是否转账成功分别表达。银行负责每期只执行一次。

创建预约不冻结或扣款，不把未来余额当成已保障；到点检查余额、限额和风险。已创建预约不能修改；取消只作用于未执行期次，处理中期次先核实，不能伪装为已取消。取消结果未知时不能先创建替代预约。创建 / 取消所需确认与验证按安全底座规定执行，不能因当前没有扣款就直接放行。

## 6. 商品与订单（付款语义已定，字段定义见下）

| 编号 / 能力 | 输入 | 输出 / 成功回执 | 主要失败 |
|---|---|---|---|
| B20 `bank.list_products`（读） | `merchant_id:ID?`、`purpose:string?`、`deliver_by:Timestamp?` | `products:Product[]` | INVALID_ARGUMENT |
| B21 `bank.create_order`（写） | `product_id:ID`、`quantity:int>0`、`expected_total_fen:Money`、`delivery:DeliveryInput` | `order:OrderView` | PRODUCT_UNAVAILABLE / DELIVERY_UNAVAILABLE / PRICE_CHANGED |
| B22 `bank.get_order`（读） | `order_id:ID` | `order:OrderView` | ACCESS_DENIED |

`Product`：`product_id`、`merchant_id`、`merchant_name`、`product_name`、`unit_price_fen`、`category`、`earliest_delivery_at`。来自银行内价目表，无库存引擎；送达能力按固定 mock 数据表达，不虚构真实物流。

`DeliveryInput`：`recipient_name:string`、`phone:string`、`address:string`、`deliver_by:Timestamp`。仅经授权的受控路径传给模拟商户；订单回执使用 `recipient_name_masked`、`phone_masked`、`address_masked`，经主契约 F36 受控输入，仅本任务和获准模拟办理路径读取；审计只保留脱敏快照，临时原文随演示重置清理，不作为聊天内容。

`OrderView`：`order_id`、`product_id`、`quantity`、`merchant_id`、`merchant_name`、`total_fen`、`created_at`、`deliver_by`、打码收件信息；用 `payment_status:unpaid|paid`、`payment_transaction_id:ID|null` 表达已确认的付款语义（§9.3）。创建订单 OperationResult 成功不代表付款成功；已付款必须关联实际交易编号。付款调用超时是应用侧待核实，不得由应用自行写成 unpaid。

银行按价目表计算总价，与已确认的 expected_total_fen 不符返回 PRICE_CHANGED，不接受调用方指定任意成交价。正式场景仍逐项确认，商品或价格变化需重新确认。取消 / 退款接口不在本期能力表中。

## 7. 模拟身份验证与演示管理的接口位置

## 7A. 签约代扣接口（2026-10-19 激活，支撑 05 订阅代扣管理）

| 编号 / 能力 | 输入 | 输出 / 成功回执 | 主要失败 |
|---|---|---|---|
| B29 `bank.list_subscriptions`（读） | `account_id:ID?`、`status:active\|cancelled?`；省略查本人全部签约代扣协议 | `mandates:SubscriptionMandate[]`、`as_of:Timestamp` | AUTH_REQUIRED / ACCESS_DENIED / INVALID_ARGUMENT |
| B30 `bank.cancel_subscription`（写） | `mandate_id:ID`（隐含必填 `operation_id:UUID` 与可信上下文） | `SubscriptionCancelReceipt` | AUTH_REQUIRED / ACCESS_DENIED / RECORD_NOT_FOUND / STATE_CONFLICT / ACCOUNT_UNAVAILABLE / OPERATION_CONFLICT |

`SubscriptionMandate`：`mandate_id:ID`、`account_id:ID`、`account_masked:string`、`merchant_id:ID`、`merchant_name:string`、`service_name:string`、`amount_fen:Money`、`cycle:monthly|yearly`、`next_billing_at:Timestamp|null`、`last_billed_at:Timestamp|null`、`status:active|cancelled`、`signed_at:Timestamp`、`cancelled_at:Timestamp|null`、`cancel_operation_id:UUID|null`。商户名与服务名不打码，卡号只展示 `account_masked`。

`SubscriptionCancelReceipt`：`mandate_id:ID`、`account_id:ID`、`account_masked:string`、`merchant_id:ID`、`merchant_name:string`、`service_name:string`、`amount_fen:Money`、`cycle:monthly|yearly`、`previous_next_billing_at:Timestamp`、`effective_stop_at:Timestamp`（等于解约前 `next_billing_at`，表示从该期起不再自动扣费）、`status:"cancelled"`、`cancelled_at:Timestamp`。

> **2026-10-19 同日补充**：B29 返回包装类型为 `SubscriptionMandateList`（`mandates` + `as_of`）；B30 调用形态为 `(可信身份上下文, operation_id:UUID, mandate_id:ID)`，写路径与 `bank.submit_transfer` 同样做超时保护（超时返回 `CALL_TIMEOUT`，由调用方按 B14 回查），回执复用 `OperationResult<SubscriptionCancelReceipt>`。

B30 规则：仅允许对当前用户本人名下 `status="active"` 且绑定账户状态为 `active` 的行内签约协议执行解约；跨用户协议返回 `ACCESS_DENIED`，不存在返回 `RECORD_NOT_FOUND`，账户冻结或销户返回 `ACCOUNT_UNAVAILABLE`。同 `operation_id` 同 `mandate_id` 重复提交返回首次 `OperationResult<SubscriptionCancelReceipt>`（幂等重放）；同 `operation_id` 不同参数返回 `OPERATION_CONFLICT`；换新 `operation_id` 对已 `cancelled` 协议再次解约返回 `STATE_CONFLICT`。B14 `bank.get_operation` 支持按 `operation_id` 回查解约回执。解约只停止下一期及之后的自动扣款，不退回历史已扣资金。

## 8. 错误码提案

下列 code 由程序判断，details 只含该错误所需事实。未列出的未知技术异常返回服务不可用语义并留诊断记录，不能一概宣称交易失败。

| code | 含义 | details | 处理要求 |
|---|---|---|---|
| INVALID_ARGUMENT | 字段格式或取值不合法 | `field:string`、`reason:string`，不回显敏感原值 | 修正输入；写请求是否已接受需结合原操作记录 |
| AUTH_REQUIRED | 登录状态无效 | 空对象 | 停止调用，恢复合法登录 |
| ACCESS_DENIED | 无权访问目标 | 空对象 | 停止，不透露目标是否存在或属于谁 |
| OPERATION_CONFLICT | 同操作编号对应不同动作或参数 | 空对象 | 拒绝本次请求，原结果不变；不得自动换号重做 |
| PAYEE_MISMATCH | 转账提交的收款信息不匹配 | 空对象 | 重新核对；B04 的正常不匹配用 matched=false |
| ACCOUNT_UNAVAILABLE | 本人账户状态不允许当前操作 | `account_status` | 停止该动作；不暴露他人账户状态 |
| INSUFFICIENT_FUNDS | 可用余额不足 | `available_fen`、`required_fen`、`shortfall_fen` | 用户修正后重新确认，不由业务复刻规则 |
| LIMIT_EXCEEDED | 本笔超过适用限额 | `scope:single\|day\|year`、`allowed_fen`、`requested_fen` | 解释银行结果，不拆单绕过 |
| RISK_REJECTED | 银行风控拒绝 | `reason_code`（如涉诈收款方） | 停止，遵守安全裁决 |
| FREEZE_INSUFFICIENT | 当前冻结余额不足以扣款或释放 | `remaining_fen`、`requested_fen` | 核对原操作与冻结事实 |
| RANGE_UNSUPPORTED | 流水查询超出最近 24 个月支持范围 | `earliest_supported_at` | 明确拒绝，不静默返回残缺账单 |
| SCHEDULE_INVALID | 执行时间或周期规则无效 | `field`、`reason` | 澄清或修正后重新确认 |
| STATE_CONFLICT | 当前状态不支持修改 / 取消 / 付款 | `reason`，仅在授权范围内 | 查询目标当前状态后决定，不能强行覆盖 |
| PRODUCT_UNAVAILABLE | 商品不在当前 mock 可用清单 | `product_id` | 重新选择并确认，不建设库存系统 |
| DELIVERY_UNAVAILABLE | 固定 mock 无法满足送达时间 | `earliest_delivery_at` | 修改计划并重新确认 |
| PRICE_CHANGED | 当前银行计算总价与确认金额不同 | `expected_total_fen`、`actual_total_fen` | 重新确认，不能悄悄多扣 |
| ORDER_PAYMENT_MISMATCH | 付款金额、商户或订单不对应 | `reason` | 停止，核对订单，不能换号重扣 |
| BANK_UNAVAILABLE | 无可靠银行答复（服务不可用） | 空对象 | 查询可有限重试；提交按结果未知核对 |
| CALL_TIMEOUT | 接入层等待超时 | 空对象 | 调用故障，不是银行交易失败；按原操作回查 |

一次预检查若有多个不满足条件，建议返回一个主要原因；种子要求余额不足例优先于限额提示，检查优先级由银行统一实现，不散在业务侧。权限拒绝必须先于受保护的账户事实输出。

## 9. 三项业务选择与确认状态

### 9.1 流水查询的完整性（09-24 Erwin 已确认）

本期一次返回指定范围内的全部记录，不做分页；查询范围为 `[start_at, end_at)`，即含开始、不含结束，最多最近 24 个月。空结果明确返回 []；范围超出支持窗口则明确报错，不能偷偷截断。银行返回数据截至时间 as_of。完整数据交给账单模块计算，不代表把全部原始流水直接送进模型上下文。已定规则见正式契约 §2.2。

### 9.2 预约周期的首版范围（09-24 Erwin 已确认）

本期支持单次和每月，覆盖现有案例；每月须明确结束日期或执行次数，二选一；用户没给结束条件时追问，不默认为永久。每周 / 每日暂不做。§5 已按此补齐结束条件字段定义；已定业务语义见正式契约 §3.3。

### 9.3 下单成功但付款失败（09-24 Erwin 已确认）

已定先冻结 → 下单 → 扣款。订单创建成功后标记未付款，扣款成功才标记已付款；两类结果分别展示。06 从冻结付款时携带 order_id，银行核对订单所属用户、商户、金额，并在同一次银行本地提交中记账及关联付款结果。一张订单最多成功支付一次，换操作编号也不能重复付款。已定业务语义见正式契约 §3.4。

明确扣款失败后订单继续未付款，不算购买完成，已明确未花掉的冻结可按既定流程释放；不新增订单取消或退款。下单或扣款结果未知先查原操作，依赖该结果的后续步骤暂停，不抢先释放可能仍用于在途付款的冻结。付款成功而应用未收到回执时，按原操作查询能找回交易与订单关联。

## 11. 字段补全与演示管理边界

补充通用错误：`RECORD_NOT_FOUND` 表示授权范围内目标对象不存在，details 为空；无权判断对象是否存在时用 ACCESS_DENIED，不返回存在性线索。B14 查原操作未查到仍走 lookup=not_found，不改为该错误。

未逐项标注类型的结构统一如下，不能自行猜测：

- `BalanceSnapshot`：account_id:ID；book_balance_fen / frozen_balance_fen / available_balance_fen:Money；as_of:Timestamp。
- `ScheduleView`：schedule_id / payer_account_id:ID；payee:PayeeDisplay；amount_fen:Money；rule:ScheduleRule；schedule_status:active/cancelled/completed；next_execute_at:Timestamp|null。ScheduleOccurrence 按 §5。
- `Product`：product_id / merchant_id:ID；merchant_name / product_name:string；unit_price_fen:Money；category:Category；earliest_delivery_at:Timestamp。
- `OrderView`：order_id / product_id / merchant_id:ID；quantity:正整数；merchant_name:string；total_fen:Money；created_at / deliver_by:Timestamp；recipient_name_masked / phone_masked / address_masked:string；payment_status:unpaid/paid；payment_transaction_id:ID|null。
- `Category`：dining / transport / medical / shopping / housing / transfer / other。账单展示七类中文名，但接口始终传这组代码。
- B19 / B21 等缺省错误同样可返回 AUTH_REQUIRED、ACCESS_DENIED、INVALID_ARGUMENT、OPERATION_CONFLICT、BANK_UNAVAILABLE、CALL_TIMEOUT；不要求每行重复列举。
- 预约 ends_on 含该北京时间日期；首次执行不得在结束之后；每月首次日期须与执行日经月末调整后的日期一致。不符合返回 SCHEDULE_INVALID。创建 / 取消回执与各期实际交易分开。
- B23 创建核验、B24 提交验证码、B25 提交模拟人脸是认证流程，不套用业务资金写入的 operation_id 去重；按 challenge_id / submission_id 保持结果一致。关联动作的 operation_id 是授权范围，不代表发起扣款。人脸开始由前端 F20 对应后端核验记录创建，不另接识别服务。
- B26—B28 是演示管理能力索引，不伪装成银行普通业务工具。B26 的平台入口为 F30—F32，平台停收并排空后，银行内部 `bank.reset_demo(management_operation_id, source_round_id, target_round_id, initial_logical_at)` 只恢复银行存储；应用与记忆由各自组件重置。B27 内部 `bank.advance_demo_time(management_operation_id, demo_round_id, target_at)` 按时间推进。B28 内部 `bank.set_demo_fault(management_operation_id, demo_round_id, target_user_id, kind:slow_transfer_6s, enabled:bool)` 仅设置银行故障；会话过期仍是平台 F28。
- 三个内部管理方法均返回 `{management_operation_id:ID,status:running|succeeded|failed,demo_round_id:ID,logical_at:Timestamp,error:BankError|null}`，同管理操作编号重复读取原结果，参数冲突拒绝。只接受受控管理调用，不纳入 Agent 工具注册。平台管理状态不要求银行操作应用表。
- B26—B28 在银行入口核验受控管理身份、目标轮次及管理操作编号；普通业务上下文或仅携带目标用户编号不能授权。失败或结果未知时先核对原管理操作，不换编号绕过在途等待。
- 手工账号、姓名与配送资料作为本轮受控办理输入；秘密不入日志，字段内文本不具备指令权限。个人姓名统一打码，商户名称保留。退款按实际入账月记账，保留原消费编号和类别供追溯，月均规则由账单模块执行。
