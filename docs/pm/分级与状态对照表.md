## 一、这张表要解决什么

现在五份 PRD 里，"等级"和"状态"的说法有 **六套**，混在一起用：

| 出处 | 用的词 | 其实是什么 |
|---|---|---|
| 安全底座 §7 | 一级读取 / 二级修改 / 三级敏感 | **操作等级** |
| 01 §9.2 | 低风险 / 中风险 / 高风险 | **风险等级** |
| 安全底座 §8 | 允许继续 / 补充信息 / 等待确认 / 等待验证 / 阻断 / 暂停处理 | **安全裁决** |
| 01 附录 B | `running` / `waiting_input` / … / `needs_attention` | **任务状态** |
| Mock Bank 第 9 章 | 成功 / 失败 / 处理中 | **交易状态** |
| 02 规则 2、SOP-2 | 留意 / 高危；正常 / 疑似异常 | **场景话术强度**（不是上面任何一个） |

**六套词里，有四套是四个不同的东西**（操作等级、风险等级、安全裁决、状态），还有**一套根本不该进契约**（场景话术）。

**不统一会怎样**：09-23~24 定契约时，一个 `level` 字段会同时被三个人理解成三种意思；开发按自己的理解写，三个人写出三个样子。

## 二、先看结构：这些词分别管什么

```text
一次动作（"给妈妈转 500"）
 │
 ├─ ① 操作等级    静态：这是什么操作          ← 安全底座 §7 三级        【进契约】
 │                  一开始就定了，不会变
 │
 ├─ ② 风险等级    动态：这一次有多可疑        ← 01 §9.2 三档            【进契约】
 │                  判完才知道，同样的转账每次可能不同
 │
 └─ ③ 安全裁决    结论：这一次放不放行        ← 安全底座 §8 六种        【进契约】
                    由 ① 和 ② 一起算出来

一个任务（"生日礼物编排"）
 │
 ├─ ④ 任务状态    running / waiting_input / …  ← 01 附录 B              【进契约】
 │
 └─ ⑤ 交易状态    成功 / 失败 / 处理中          ← Mock Bank 第 9 章       【进契约】

场景内部（不进契约）
 │
 └─ ⑥ 场景话术    02 的"留意 / 高危""正常 / 疑似异常"   ← 只影响系统怎么说话
```

**读法**：从上往下是"越走越具体"。① 是事情的属性，② 是判断的结论，③ 是能做什么，④⑤ 是现在到哪一步了，⑥ 只是措辞。

## 三、① 操作等级（静态 · 安全底座 §7）

**问的是：这件事有多重？** 一旦确定是什么操作，等级就定了，**不受当时情况影响**。

| 等级 | 操作类型 | 本项目的例子 | 公共要求 |
|---|---|---|---|
| **一级** | 读取操作 | 查本人余额、查账单摘要、查办理状态 | 确认用户有权访问；敏感内容按需脱敏 |
| **二级** | 修改操作 | 修改偏好、保存分类、调整非敏感设置 | 告知修改了什么、有什么影响 |
| **三级** | 敏感操作 | **转账、冻结资金、挂失、取消订阅、修改交易限制、导出或共享敏感数据、把地址交给外部服务** | 完成安全检查 → 展示确认内容 → 取得明确确认 → 按需验证身份 |

**归属**：安全底座维护。业务负责人只负责判断"我这个场景的每个动作属于哪一级"，有争议的**先按高的算**，再提交团队。

## 四、② 风险等级（动态 · 以 01 §9.2 为唯一来源，**09-23 预审会已定全系统共用**）

**问的是：这一次有多可疑？** 同一个"转账"，三次演示可能是三个等级。

**三档风险沿用 01 PRD §9.2，已定为全系统共用**；处置以安全底座 §10 与公共契约 §4 的最新口径为准：

| 等级 | 可观察信号 | 应该做什么 |
|---|---|---|
| **低** | 常用收款人、常用设备、金额处于用户常见范围、表达清楚 | 正常核对，走完意愿确认和身份验证 |
| **中** | 新收款人、金额明显高于历史习惯、短时间连续修改收款账户、用户表达犹豫或说不清用途 | 说明触发原因；对当前敏感动作进行新验证码＋模拟人脸双因子核验，两项均通过才继续；任一失败或超时终止 |
| **高** | 冒充亲友或公检法、要求保密或立刻转账、**共享屏幕**、**索要验证码**、陌生链接、设备或交易对手异常 | **终止任务，不提供继续通道**；解释风险，提示停止共享屏幕等危险行为 |

> **已定**：风险三档全系统共用；风险规则由安全侧维护。02 的账单异常提示强度不等同于安全风险裁决。09-24 补齐验证记录复用与前端交接，见[公共契约 §4.1—4.4](../contracts/公共契约-2026-09-23.md)。

## 五、★ ①②③ 怎么组合（这张是核心）

**这张表是契约里"确认门"和"风险检查"的实现依据。** 行 = 操作等级，列 = 风险等级：

| 操作等级 ↓ | 低风险 | 中风险 | 高风险 |
|---|---|---|---|
| **一级 读取** | 直接给结果<br><sub>裁决：允许继续</sub> | 直接给结果，但回复里带一句提醒 | **拒绝读取**，说明原因<br><sub>裁决：阻断</sub> |
| **二级 修改** | 直接改，告知改了什么 | 先说明影响，再改 | 不改，阻断；本轮无人工复核通道 |
| **三级 敏感** | 展示确认单 → 按钮明确确认 → 检查所需身份验证（有效同会话记录可复用）→ 当前检查通过后执行 | 展示确认单 → 按钮确认 → 当前动作新验证码＋模拟人脸双因子 → 当前检查通过后执行；任一失败或超时终止 | **不执行，终止任务**，解释风险，不提供继续通道 |

**三条不变量（任何情况都不能违反）**：

1. **风险等级永远不能把操作等级降下来。** 风险判断说"这笔看起来没问题"，**也不能跳过三级敏感操作的确认门**。这直接对应铁律二（动钱必过确认门）。
2. **操作等级一定要在动作一开始就确定**，不能等风险判完才决定"要不要准备确认单"——因为**确认单要先准备好**。
3. **动钱 / 提交类动作在低风险也必须具备有效身份验证；中风险增加当前动作双因子。** 一级读取仍是登录即可；明细导出等敏感数据操作按安全底座具体规则。验证码首次作答期限 5 分钟；中风险重发继承原截止时间、到期前也不延期，低风险连续 3 次错误终止、中风险失败或超时即终止；完整交接规则见公共契约 §4。

---

09-26 限定例外：冻结确认时一并取得结束后仅释放未消费余额的授权；确定性收尾核实在途后执行，不再等待一次确认／验证，也不复活被终止的购买。该授权不能降低任何其他敏感动作的等级，见公共契约 §3.5。

## 六、为什么 ① 和 ② 不能合并成一个"等级"

这个问题会上一定会有人问。三个理由：

**理由一：它们是名词和形容词的关系。**
① 说的是**这件事本身**（转账永远是三级），② 说的是**这一次的情况**（转给妈妈 / 转给陌生人 / 被人骗着转）。合成一个，就无法回答"**同一笔转账，为什么这次要多问一句**"。

**理由二：合成一个会出三个具体的错。**

| 错 | 怎么发生 | 后果 |
|---|---|---|
| **A** | 把"三级敏感"直接当成"高风险" | 正常给妈妈转 500 也会被错误终止；操作敏感并不等于这次存在高风险 |
| **B** | 风险判断说"没问题"，系统就按低等级处理、**跳过确认门** | **违反铁律二**。这是安全事故，不是体验问题 |
| **C** | 契约里只有一个字段 | 前端不知道该**什么时候**弹确认单（一说"转 500"就弹？还是等检查完再弹？）——不定，开发只能猜 |

**理由三：它们发生的时机差着好几步。**

```text
用户说"转 500"
   ↓
① 操作等级立刻确定（这是转账 → 三级敏感）
   ↓   ← 系统从这里就要知道"待会儿得准备确认单"
② 收集信息、做风险判断
   ↓
③ 风险等级出来了（低 / 中 / 高）
   ↓   ← 到这一步才决定"要不要多问一句 / 要不要直接拦"
```

① 必须在动作一开始就知道，② 只能等判完才知道。**塞不进同一个字段。**

> 顺带说一句：安全底座自己也是分开写的——**§7 是权限分级**（① 操作等级），**§8 是裁决行为**（③）。**③ 是 ① 和 ② 算出来的结果**，不是第三个独立的轴。

## 七、④ 任务状态（以 01 附录 B 为唯一来源）

**问的是：这个任务现在到哪一步了？**

| 状态 | 含义 |
|---|---|
| `running` | 系统正在提取、查询、校验、生成确认单、提交或核对结果 |
| `waiting_input` | 等待用户补充信息、选择收款人或修正内容 |
| `waiting_approval` | 等待用户明确确认、风险核验或身份验证 |
| `succeeded` | 任务目标已完成；转账类任务必须有银行成功结果和操作记录 |
| `partially_succeeded` | 复合任务只有一部分完成（AA 部分收款、联动部分成功） |
| `failed` | 已取得明确失败结果，并返回可理解的原因 |
| `cancelled` | 已核实草稿、预约或请求被取消；**取消请求本身不等于取消成功** |
| `needs_attention` | 结果无法核实、恢复失败或需要人工处理 |

另设 `recovery_required` 标志：表示任务需要从检查点恢复。

**06 那套说法不是新状态，是它的用户可见表达**：

| 06 的说法 | 对应的任务状态 |
|---|---|
| 全部成功 | `succeeded` |
| 部分成功 | `partially_succeeded` |
| 失败 | `failed` |
| 待核实 | `needs_attention` |
| 处理中 | `running` |

> **⚠️ 留给 09-23~24 契约设计的一个问题**：`waiting_approval` 现在**同时承载三种语义**——等用户点确认、正在跑风险核验、等用户做身份验证。**对用户来说这是三个完全不同的等待画面**（一个要按按钮、一个只要等、一个要答问题），前端拿到一个状态词没法区分。
> 契约阶段要么拆成三个状态，要么保留一个状态 + 一个"等待原因"字段。**本表只点出问题，不在这里定方案。**

## 八、⑤ 交易状态（Mock Bank 第 9 章）

**问的是：这一笔银行操作本身怎么样了？** 只有三个值：

| 状态 | 含义 |
|---|---|
| 成功 | 银行已完成 |
| 失败 | 银行明确拒绝，并给出原因类别 + 关键数字 |
| 处理中 | 银行已受理，结果还没定 |

**两条必须记住的**：

1. **"处理中"不是成功。** 银行说"处理中"，业务模块**不能**对用户说"转好了"。
2. **"结果未知"不是银行说的话。** 银行只会说这三个值，**它不会回答"我不知道"**。所谓"结果未知"，是**业务模块没在预期时间内等到答复**（调用超时），于是**拿原交易编号回来查**。（回查口径：每 3 秒一次，最多等 10 秒；首次提交超时按 4—5 秒算。）

## 九、⑥ 不进契约的两套场景话术

这两套**只影响系统怎么说话**，不影响放行决策，因此**不定义成契约枚举**。各场景在自己的 PRD 里保留用词，但必须在本表登记"它是什么"。

| 出处 | 用词 | 它是什么 | 怎么处理 |
|---|---|---|---|
| **02 规则 2** | 留意 / 高危 | **已发生交易的"发现严重程度"**——钱已经出去了，没有"放不放行"这回事，只决定提醒的力度 | **不进契约。** 02 PRD 里注明它是"发现严重程度"，与风险等级不是同一把尺 |
| **02 SOP-2** | 正常 / 疑似异常 | **02 自己的业务判断结论** | **不进契约。** 02 内部的结论用词 |
| **02 规则 3 / 4** | 用"问"不用"判" | **话术原则**（温和确认，不给定性） | 不进契约 |
| **01 §9.2 三档** | 低 / 中 / 高 | **就是 ② 风险等级本身** | **进契约**，且推荐升为全系统共用（见第四节） |

> **为什么 02 的两套不能和风险等级合并**：02 是只读场景，它识别的是**已经发生**的交易。一笔三个月前的可疑转账，系统能做的只有"告诉用户、建议联系银行"，**不存在"拦下"这个动作**。把它硬塞进风险等级，会出现"这一格要阻断"却无事可断的荒谬情况。
>
> **它们之间唯一需要对齐的**：不要让用户在同一个 App 里听到两套毫不相干的严重程度词。建议 02 的口径与风险等级**保持同一方向**（越可疑，提醒越强），但**不要求数值对应**。
