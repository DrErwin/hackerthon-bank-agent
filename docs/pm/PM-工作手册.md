## 一、总纲：三条元原则

1. **质量靠机制，不靠事后审查。** 你不可能逐行读完三个人的代码。要做的是把「坏代码能造成的破坏」在发生之前框死，而不是事后逐行审出来。
2. **契约只有一个 owner。** 多人一起定契约会协商成一锅粥。正确的顺序是：讨论 → 你定 → 冻结 → 他们实现。
3. **守住接缝，容忍深度。** 你拥有所有接口（接缝），成员拥有接口背后的实现（深度）。

## 二、流程建立：从 PRD 到开工

```
PRD（共识） → wayfinder（解迷雾） → to-spec（规格） → to-tickets（拆票） → implement（每人一票）
```

**关键纪律：**
- spec 和 ticket 必须在**同一个不断开的上下文**里产出，别中途 compact，否则规格和票据会建立在不同思考上。
- 每张 ticket 是**自包含**的，implement 之间要 clear 上下文。
- 切 spec 用**垂直切片**，不用模块切，更不全量一起。

### 为什么第一刀是「基座 + 转账」的垂直切片

两个反例都要避开：

| 错误切法 | 为什么错 |
|---|---|
| 全部系统一次讲完再变 spec | 6 场景 × 五层 × 25 工具 × 安全 × 评测 × 前端，远超一次会话容量，会在 to-tickets 前撑爆窗口、降智产出票据 |
| 按模块切 | 横向底座（编排、工具注册表、模拟银行、统一安全执行器、审计日志、评测）脱离真实场景**没有用户可见行为**，单独拿不出来，且是所有场景的共享契约层；各写各的会得到 6 份互不兼容的规格 |

**垂直切片 = 一个能端到端跑通、能被验证的场景，纵向贯穿所有层。** 第一刀用转账，因为它把基座逼出来：

| 基座组成 | 第一刀建多少 | 暂时不建 |
|---|---|---|
| Agent 底座编排循环（Deep Agents） | 全量（意图→计划→执行→回复），只挂 5 个工具 | 局部重规划高级策略 |
| 工具注册表 + 风险元数据 | 格式全定，先装 ~5 个工具 | 其余 20 个工具 |
| 模拟银行数据模型 | 账户 / 流水 / 常用收款人 | 理财产品、订阅、卡片 |
| 统一安全执行器 | 五段形状全通（安检→政策→确认门→注入隔离→输出过滤） | 各场景风控规则 |
| 确认门状态机 | 完整（pending_operation 全生命周期） | —— |
| 审计日志 | 完整 | —— |
| 记忆层 | 常用收款人最小版 | 偏好、事件记忆 |
| 评测框架 | 形状全定，只装转账用例 | 其余场景用例 |

**每个横向基座的「形状」都在第一刀定死，深度只做到转账够用。** 后面场景 spec 只加工具、加数据、加规则，并顺手验证形状对不对。形状要改，改在第 2 刀，而不是第 6 周集成时。

### 第一刀拆成的 ticket（曳光弹，每张薄但纵向到底）

1. 仓库骨架 + 工具链 + CI 跑通一个空测试 → **能跑起来**
2. 模拟银行最小模型（账户/流水/收款人）+ 种子数据 + 一条查询测试 → **数据能取出来**
3. Agent 底座薄接口接默认模型（GLM），跑通一次纯文本对话 → **LLM 通了**
4. 工具注册表 + 第一个只读工具（查余额）+ 风险元数据 → **问余额 → 生成计划 → 调工具 → 回复**
5. 统一安全执行器骨架套上第 4 步 → **链路有安检了**
6. 转账工具 + 确认门状态机 + 回执 → **动钱要确认了**
7. 前端最小对话界面 + 计划卡片 + 确认面单（SSE）→ **用户看得见了**
8. 转账评测集 + 红队用例 → **能自证了**

**第 1–5 张就是「基座」，每张都有可验证产出，不是搭两周什么都没有。**

### 哪些地方要走 wayfinder（迷雾）

`/wayfinder` 产出**决策**而非交付物，只给路径不清的地方，别用来拖慢清楚的部分：

- **安全层设计** —— 权限分级、四类攻击防御、确认门状态机，kickoff 后就被推迟，是真正的迷雾。
- **Agent 编排内部** —— 执行器细节、失败局部重规划、幻觉防护。

六个场景**不走 wayfinder**，它们的业务流程 PRD 已在写，路径清楚。

## 三、契约管理（最核心的机制）

### 四步：讨论 → 你定 → 冻结 → 实现

- **讨论**：白板把领域理清，让非技术和新手搞懂「转账有哪些环节、什么时候要确认」。买的是理解和 buy-in。
- **你定**：讨论的产出物**必须是你一个人写的**。契约只有一个 owner，否则会被协商成粥。
- **冻结**：契约定稿后版本化，sprint 中途不许改，要改只能走你。
- **实现**：他们照着写，写错也错不出圈。

### 契约是可校验的代码产物，不是文档

这是让新手贡献变安全的第一杠杆。**如果契约只写在 markdown 里，新人一定跑偏；如果契约是 Pydantic 模型 + 校验规则文件，类型与运行时校验就是第一个、也是最不知疲倦的 reviewer。**

工具注册表、计划对象、确认门状态、审计日志、模拟银行模型——**全部写成 `backend/app/contracts/` 下的真实代码文件（Pydantic 模型）**。成员 import 模型去写，字段写错、类型不匹配，运行时校验与静态检查直接报错。**你不读代码，也知道他没跑偏。**

### 你拥有「接缝」，他们拥有「深度」

- 一个工具 = 一个签名的函数 + 一份元数据。你把签名和元数据格式定死，成员怎么实现函数内部你不必太关心——**他那点烂代码被封在小接口后面，最坏是重写这一个函数，坏不到系统里。**
- **绝不放手**：接口本身、统一安全执行器路径、模拟银行 schema、编排器核心。
- 策略：**守住接缝，容忍深度。** 新手模块内部丑一点没关系（可替换）；接缝歪了才是事故。

## 四、质量保障：三层机制 + 三道闸

### 三层机制（让坏代码从机制上限死）

1. **类型**：契约是编译产物，编译期报错。
2. **测试**：在接缝处验证行为。
3. **小 PR 小接口**：影响半径被接口框住。

### 三道闸（收口）

- **PR 模板清单**：一票一分支一 PR，提交前自答「对照规格做完了吗？跑了测试吗？符合规范吗？」（code-review 的「标准 + 规格」双轴）。清单替他做第一遍过滤。
- **CI**：`mypy` / Pydantic 校验（类型）+ `ruff`（规范）+ `pytest`（测试），**不过不给合**。这是你的「第二个 reviewer」，从不错过一个类型错误。
- **合并权**：`main` 保护，**只有你合并**。

### 验收标准可执行化

对没经验的人，「把转账做出来」是废的验收标准。**每个 ticket 的「完成」必须是客观可验证信号**：一条测试名、一个 schema 能过、一条命令的输出。所以**你（或我）先写测试骨架和验收标准，他们去让测试变绿**。测试就是规格的可执行形态——**测试红着就是没做完，不能吹。**

## 五、精力分配：别把自己变成瓶颈

你的稀缺资源是**架构判断力 + review 能力**，不是写代码的手速。

| 你亲自写 | 你深度审 | 你抽查即可 |
|---|---|---|
| 契约文件（Pydantic 模型） | 安全执行器与确认门 | 叶子工具实现 |
| 编排核心 / Deep Agents 底座薄接口 | 模拟银行 schema | 前端组件 |
| 测试骨架、样板（可交给我） | 确认门状态机 | 测试用例 |

**尤其别同时再领两个场景模块自己开发。** 你如果又要写基座、又要审 3 人 PR、又要自己写 2 模块，你会变成全队阻塞点，质量全线崩。安全层（占 30% 评分）已交由 **Ringo** 负责（金融背景对口），你只审确认门与拦截策略；你该守的第三件事是**银行接入层 / 模拟银行接缝**（全系统最重要的外部边界）与前端收口。

## 六、团队管理

- **合作不是上下级**：不拿工资、谁也不欠谁，凭良心和责任心推进；你自己也是合作者，只负责推进度。
- **CV 激励**：这是实打实的 0→1 agent 研发 + 5 人协作，能写进简历。
- **卡点三渠道**：① 问 AI ② 群聊 ③ 私聊 / 艾特你。
- **随时调分工**：有人临时有事、时间不充足，你重新排或顶上。
- **例会**：一周至少一次（理想两次），倾向周二/周四，提前协调；组会形式，每人讲推进/卡点/下一步，不用 PPT。
- **群聊**：闲聊无妨，越紧密越好协作；重要消息会后私聊确认有没有看到。

## 八、一句话总结

**别靠事后 review 保证质量，靠「编译不过的契约 + 小接口封死影响半径 + 测试当验收 + CI 当第二 reviewer」四层机制，把坏代码的危害在发生前框死。你守住接缝和合并权，容忍他们模块内部的深度，质量自然就稳。**
