## 一、先看推进顺序

**你现在先整理 PRD 问题，再开联合评审。会上定业务范围、职责和关键规则；会后各负责人补业务，你更新架构和接口；最后用真实运行验证约定。**

| 阶段 | 什么时候做 | 主要由谁做 | 得到什么 |
|---|---|---|---|
| 1. 收集与预审 | 收齐前就能开始，建议评审前 1 天完成 | 你；各负责人补缺 | PRD 收件清单、待决问题表、会议议程 |
| 2. 联合评审 | 材料可讨论后，建议 90 分钟 | 全员，你主持 | 范围、职责、关键状态和硬规则的决议 |
| 3. 会后补齐与架构更新 | 建议会后 1 天形成修订稿 | 各负责人分别补，你汇总 | 一致的业务 PRD、架构及遗留问题 |
| 4. 公共接口设计与核对 | 建议随后 1—2 天形成草案 | 你牵头，使用接口的人核对 | 可用于开发的接口协议和示例 |
| 5. 最小链路实现与验证 | 关键约定明确后，按实际工作量估时 | 你牵头，转账、安全、前端配合；联动随后验证 | 可运行链路、验证记录、可复用接入示例 |

以上是建议节奏，不是已经承诺的日期。先确认每个人的可用时间，再填实际截止时间。若与既有排期冲突，由你更新计划并同步团队。

每完成一阶段，先更新项目进度：完成了什么、证据在哪里、还有什么问题、接下来谁做什么，再进入后续阶段。未受影响的工作可以继续，不必让全员等一个局部问题。

## 二、执行时始终遵守的原则

1. **先处理返工代价大的决定。** 优先定业务范围、规则归属、关键状态、安全约束，再讨论字段和内部实现。
2. **按变化原因划分职责。** 转账规则、账单统计、联动安排、银行规则各有自己的变化原因；人员分工不应成为唯一拆分理由。
3. **每类事实有明确来源。** 银行决定是否扣款，模拟购买服务记录订单结果，业务任务记录办理进度，不能互相替代。
4. **先讲清业务，再统一机制。** 公共确认、安全、恢复机制复用；各业务允许有自己的步骤。
5. **接口要包含行为约定。** 除了输入输出，还要说明等待、失败、取消、结果未知和继续办理怎样处理。
6. **实际验证后才算能用。** 文档通过评审不等于程序已经支持重启恢复或防重复执行。

## 三、已确认的前提与还要决定的问题

### 已确认：作为本轮评审前提

- 外部生活服务使用模拟能力，提供商品选择、价格、下单与付款。
- 本轮购买流程到下单付款完成为止，不建设配送、退款等后续服务。
- 主 Agent 理解用户目标并选择业务能力；联动模块负责复合任务安排；转账、账单等模块负责自己的业务办理。
- 公共机制尽量复用，不强制不同业务共用完全相同的步骤或节点表。
- 模型负责理解、建议和回复；程序负责允许哪些动作、是否执行，以及检查实际结果。
- 敏感动作必须经过确认；银行规则与银行操作结果归模拟银行。

### 待决定：带到评审或指定负责人会后提出方案

| 问题 | 谁应参与 | 需要得出的答案 |
|---|---|---|
| 模拟商品、订单、购买能力由谁建设 | 你、联动负责人 | 明确能力范围、负责人和交付时间 |
| 下单与付款怎样组合 | 你、联动、安全、购买能力负责人 | 是否可能一项成功另一项失败；若可能，怎样记录与展示，不承诺不存在的退款能力 |
| 总预算怎样维护与检查 | 联动、你、Ringo | 谁维护已用和待核实金额，在哪检查，怎样防止绕过 |
| 子任务等待、失败、取消时整体怎样变化 | 联动及被调用模块负责人 | 父子任务的推进与结果规则 |
| 前端与适老化交互由谁实现 | 你与团队 | 指定能交付确认、等待、查询和结果展示的人 |

预算职责的讨论起点：建议联动模块维护整体预算，在执行前由确定性代码检查，公共执行机制保证该检查不会被跳过；模拟银行仍检查余额、账户权限和银行限额。**这是一份待评审方案，不是已经定稿的架构结论。**

不需要等所有 PRD 写到完美。只要能讲清主要业务，就可以先预审。

### 你按顺序怎么做

1. **登记收件情况。** 记录负责人、最新文件位置、更新时间、缺少的材料。确认大家讨论的是同一份版本。
2. **每个任务检查六件事。** 用户想做什么；做到什么算成功；正常怎样办理；哪里等用户；异常与取消怎样处理；需要别人提供什么。
3. **给缺口分类。** 单个业务内部问题交给负责人补；涉及多人或公共规则的问题带上会；实现细节留到接口或开发阶段。
4. **写出你的初步建议。** 能判断的先提方案；判断不了就写清需要什么信息、请谁提出方案，不强行猜答案。
5. **选两个走查例子。** 一个普通转账，一个多项模拟购买。提前发给大家，让他们准备正常和异常处理。
6. **发会议通知。** 写明时间、参与人、材料、需要当场决定的问题，并请负责人在会前补主要缺口。

## 五、阶段 2：主持联合评审

### 开始前准备什么

### 90 分钟怎么安排

| 时间 | 你怎样主持 | 当场记录什么 |
|---|---|---|
| 0—20 分钟 | 请各负责人说明“本轮做什么、怎样才算成功”；确认模拟购买边界 | 范围及完成标准 |
| 20—40 分钟 | 问“这一步需要谁提供什么能力”；检查重复实现和无人负责的部分 | 职责与依赖 |
| 40—75 分钟 | 走转账和联动例子，加入修改、取消、失败、结果未知 | 关键状态变化、必须执行的检查 |
| 75—90 分钟 | 复述已定结论，逐项分配遗留问题 | 负责人、交付内容、截止时间 |

### 走查时照着问

**例子 A：普通转账。** 用户要求转 500 元，展示确认信息后又改成 600 元；随后提交时超时。

1. 哪个模块负责补齐和确认信息？
2. 修改金额后，旧确认能否继续使用？
3. 哪一步才真正向银行提交？
4. 超时后知道什么、不知道什么？
5. 谁查询原操作，怎样避免重复转账？
6. 用户看到什么，什么时候才可以报告成功？

**例子 B：模拟购买。** 总预算 500 元，购买花和蛋糕；花已购买成功，蛋糕付款结果未知，此时用户要求取消。

1. 谁管理整个任务，谁管理每项购买？
2. 花的成功结果由谁提供？
3. 蛋糕结果未知时如何占用预算，是否允许执行其他购买？
4. 取消后哪些动作停止，哪些结果还要核对？
5. 不提供退款时，怎样如实保留已成功购买？
6. 子任务状态怎样汇总成用户能理解的整体结果？

每问一个问题，让负责该部分的人先回答；有冲突时回到范围、事实来源和安全约束决定。超过约 5 分钟仍缺信息，就指定会后提案人，不在会上靠猜测定稿。

3. 标明每个问题阻塞哪一部分；无关模块可以继续准备。
4. 不在本次会议中逐个设计接口字段、数据库表和代码节点。

### 你按顺序怎么做

1. 会后当天发分工，每项写“补什么、交到哪里、何时交”。
2. 收到修订后，先比对有依赖的两方：一方需要的结果，另一方是否明确提供。
3. 整合总 PRD 的共同部分：本轮目标、范围、跨场景关系、整体验收标准。各业务详细流程仍由原负责人维护。
4. 更新架构中被决议影响的部分：模块职责、模拟购买归属、预算检查、父子任务关系、公共安全与恢复职责。
5. 用“改动检查”审视模块：转账内部换步骤是否迫使账单修改？换商品数据是否迫使银行修改？若是，检查是否暴露了不必要的内部细节。
6. 修正相关规范中与决议冲突的表达，包括“所有业务必须共用同一套节点”等过强限制。
7. 把改动摘要发给受影响的人，核对职责和依赖，不要求全员再读完整架构。
8. 更新进度记录，未决问题继续保留负责人和期限。

### 得到什么、怎样算完成

- [ ] 各业务流程与会议决议一致。
- [ ] 总体范围、模块职责、能力依赖已经对上。
- [ ] 关键规则有负责方，公共机制与业务流程分工清楚。
- [ ] 架构中没有把待讨论方案写成已确认结论。
- [ ] 后续接口要解决的问题清晰，不再靠各模块自行猜测。

## 七、阶段 4：形成公共接口协议，交给使用者核对

### 开始前准备什么

修订后的业务 PRD、职责依赖表、状态变化表、硬规则表，以及正常和异常例子。

这里的“接口协议”就是模块之间的约定：你给我什么、我替你做什么、我返回什么、事情没办完时怎样继续。

### 你按顺序怎么做

1. **列出必要接口。** 从实际依赖里提取，先覆盖最小转账和最小联动需要的能力，不预先设计所有未来场景。
2. **先写业务含义。** 为每项接口填写下面的卡片，再落实字段与格式。
3. **统一公共部分。** 统一任务标识、等待、结果、错误、允许的后续动作和可信身份传递方式。业务专属参数留给对应模块定义。
4. **给出实例。** 每项关键能力至少提供正常、等待或处理中、失败或未知结果的具体样例；不适用的说明原因。
5. **请调用方走一遍。** 转账、账单、联动负责人用自己的例子检查：缺哪些输入？结果能否支持下一步？等待后能否继续原任务？
6. **请 Ringo 核对。** 身份、确认、权限和防重复执行是否有明确承载方式，调用方是否可能绕开检查。
7. **解决阻塞问题，形成开发基线。** 记录版本和修改责任。发现验证问题可以修订，但必须通知受影响的人，不能各自偷偷改。
8. **落实为唯一代码契约。** 进入实现时，公共输入输出由 Pydantic 模型等可校验形式承载，各模块引用同一来源；Markdown 协议通过评审不等于代码契约已交付。

### 每项接口的填写卡片

| 项目 | 填什么 |
|---|---|
| 能力名称、提供方、使用方 | 谁为谁完成哪件事 |
| 调用前提 | 需要登录、原任务、确认或其他条件吗 |
| 输入 | 必须提供什么，哪些可选，身份来自哪里 |
| 结果 | 成功依据是什么，返回哪些数据或结果引用 |
| 等待 | 等用户还是等服务；原任务怎样继续 |
| 异常与未知 | 哪些是明确失败，哪些只能查询核对 |
| 修改与取消 | 哪些状态允许，已完成动作如何保留 |
| 重复请求 | 怎样识别同一动作，能否安全重复调用 |
| 验证例子 | 正常、等待、拒绝、未知等具体输入与期望结果 |

### 得到什么、怎样算完成

- [ ] 关键调用方和提供方均核对过协议。
- [ ] 接口包含行为规则，既有字段，也有异常和继续办理方式。
- [ ] 最小链路所需接口没有阻塞性未决问题。
- [ ] 有统一样例，能够据此模拟依赖返回。
- [ ] 代码契约是否已实现单独记录，没有用“文档已写完”替代。

## 八、阶段 5：实现最小链路，验证后展开开发

### 开始前准备什么

- 最小链路的业务流程、接口基线和验收例子。
- 虚构账户、模拟银行和可控异常数据的建设安排。
- 明确的底座、转账、安全、前端负责人。
- 每个人能投入的时间；先估工作量，再排具体日期。

### 你按顺序怎么做

1. **限定第一条完整链路。** 普通转账：用户发起 → 补齐信息 → 确认 → 安全检查 → 银行执行 → 返回真实结果。
2. **只为当前链路细分实施任务。** 先形成实现规格，再拆成每项可验收的任务，最后开发。Matt 生成的 spec 和 tickets 放在 `.scratch/`；未来能力暂不拆票。
3. **给每项任务写验收结果。** 不写“完成确认模块”，而写“用户未确认时不能执行；改金额后必须重新确认；确认后继续原任务”。
4. **落实代码契约与统一接入示例。** 确保开发者引用相同公共定义，按示例接入，不自建另一套安全或恢复机制。
5. **先跑通正常链路，再验证关键风险。** 由开发负责人执行并留下记录，你按验收例子检查实际结果。
6. **修复并更新协议。** 若真实运行暴露规则或接口缺口，修订后同步依赖方，再针对受影响行为复验。
7. **增加一个最小联动例子。** 验证预算、子任务等待、部分成功、取消和未知结果，不只重复演示两笔成功调用。
8. **确认可复用后扩大接入。** 提供公共契约、模块样例、模拟数据和验证入口，各业务据此继续开发。

### 必须看到的验证结果

| 验证 | 期望看到什么 |
|---|---|
| 正常转账 | 用户确认后执行，展示结果与银行记录一致 |
| 未确认或确认后改金额 | 原批准不能授权新金额，不能提前扣款 |
| 权限拒绝 | 无权操作的账户不能因为模型要求或用户点击而被放行 |
| 重复确认 / 重复请求 | 同一动作不会导致两次扣款 |
| 等待期间重启 | 找回原任务和等待位置，用户可以继续 |
| 银行成功但应用未保存结果时中断 | 恢复核对原操作，不重新扣款 |
| 银行结果未知 | 保留待核实，不能误报失败或换编号重做 |
| 联动部分成功与取消 | 成功结果保留，未执行部分按规则停止，未知部分继续核对 |
| 联动预算 | 总预算检查有效，待核实金额不会被错误当作可再次花费的余额 |

### 其他成员可以同时做什么

- 账单负责人用约定的模拟返回值验证统计和展示流程。
- 联动负责人用模拟子任务结果验证等待、部分成功与取消。
- Ringo 准备拒绝、参数篡改和绕过检查的用例。
- 所有模拟依赖都遵守同一接口，不另造一套银行规则。

### 得到什么、怎样算完成

- [ ] 最小转账链路实际运行通过，关键异常有验证记录。
- [ ] 最小联动例子验证了跨模块规则。
- [ ] 发现的公共接口问题已经同步修正。
- [ ] 团队拿得到统一契约、接入示例和验证方法。
- [ ] 进度记录区分“已通过、失败待修、尚未验证”，不把一次正常演示当作全部验收。

## 九、每天怎么推进，遇到问题怎么处理

每天花 10—15 分钟检查：今天该收到什么、实际收到什么、谁被什么问题卡住、需要你决定什么。

| 遇到的情况 | 你的处理方式 |
|---|---|
| 某份 PRD 没写清 | 指出具体任务和缺口，请负责人补，不替他重写所有内容 |
| 两个人都认为对方提供某能力 | 明确一个负责人和交付范围，记录谁使用、何时需要 |
| 业务问题你不会判断 | 请相关负责人提出可选方案、影响和建议，你组织决定 |
| 技术可行性不确定 | 安排最小实验，先定义验证标准，再根据结果定案 |
| 问题只影响一项能力 | 暂停依赖它的部分，其他人继续不受影响的工作 |
| 新需求会改变范围或公共协议 | 说明收益、成本和受影响模块，再决定纳入或后放 |
| 到期仍没有结论 | 明确卡在哪里，重新分配或调整范围和排期，不默认问题已解决 |

每次记录决议用同一格式：

| 编号 | 决定了什么 / 还有什么未定 | 影响哪些业务 | 谁执行 | 截止时间 | 验收依据 | 当前状态 |
|---|---|---|---|---|---|---|
| 待填 | 待填 | 待填 | 待填 | 待约定 | 待填 | 待开始 |
