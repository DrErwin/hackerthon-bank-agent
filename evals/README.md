# 评测集编写指南

> 用途：让每位负责人知道自己的评测集放哪里、写哪些用例、怎样判断通过。排期和分工以 [项目跟踪](../docs/01-项目跟踪.md) 为准；业务规则以对应 PRD 和[公共契约](../docs/contracts/公共契约-2026-09-23.md)为准。本文不代替业务需求。

评测集是系统的“考题和标准答案”：给出用户请求及必要的初始状态，写清系统应该做什么、不能做什么，再用实际运行结果核对。**先写少量代表性用例支持开发，随后补齐完整覆盖；不要等全部用例写完才开始编码。**

## 一、分为哪几类

| 类别与位置 | 负责人 | 应包含的内容 | 重点回答的问题 |
|---|---|---|---|
| 01 转账：[`transfer/`](transfer/) | 梁爽 | 不同转账说法、收款人与金额澄清、确认和取消、定时转账、银行失败与结果待核实等 | 转账业务是否按 01 PRD 办理，是否只报告银行实际返回的结果？ |
| 02 账单：[`bills/`](bills/) | Ethan（本轮排期；原目录归属为六水，待 09-28 全员会同步） | 查询与分类、异常识别、报告生成、导出及失败情况 | 账单结论是否有流水依据，结果和导出权限是否正确？ |
| 06 联动：[`cross/`](cross/) | Ethan（周恩宇） | 任务 A／B／C 的拆解、预算、跨模块调用、逐项确认、部分失败与收尾 | 多步骤任务是否按顺序完成，并准确说明哪些步骤成功或失败？ |
| 安全：[`security/`](security/) | Ringo | 权限拒绝、确认与验证、诱导、越权、提示注入、敏感信息泄露等正反例 | 不该执行的动作是否被挡住；合法请求是否正常放行？ |
| 模拟银行：[`mockbank/`](mockbank/) | Erwin | 余额／限额、重复提交、超时回查、涉诈拦截、冻结与释放、预约到点等银行规则 | 同样的输入是否得到可核对的银行结果，是否避免重复动钱？ |
| 端到端：首批用例建立时放入 `evals/e2e/` | Erwin | 少量贯穿“用户请求 → Agent 选择能力 → 业务处理 → 安全确认 → 模拟银行 → 用户回执”的完整任务 | 各部分接起来后，用户能否真正完成任务或得到准确的失败说明？ |

**Agent 框架怎样测**：先在业务和端到端用例中检查它是否选对业务能力、记住必要上下文、暂停等待确认后继续原任务、没有自行执行资金动作。现阶段不另建一套庞大的框架评测集；若以后发现与任何业务无关的共性问题，再单独补充。

**分类原则**：按“这条用例主要想定位谁的问题”放入一个主目录，其他关注点写在期望结果里。例如“用户取消转账后不得扣款”以 01 业务为主；“伪造确认信息试图绕过检查”以安全为主；“全链路能否完成一笔转账”以端到端为主。可以引用同一需求，不必复制同一条用例到每个目录。

## 二、每条用例至少写什么

| 内容 | 写法 |
|---|---|
| 用例编号与分类 | 唯一编号，能看出所属业务或类别；标注正常、异常、边界或安全正／反例 |
| 需求依据 | 指向对应 PRD、公共契约条目或验收例，说明为什么要测 |
| 输入与起始条件 | 用户原话、已登录用户、已有对话、账户或流水等必要的模拟数据；只放影响结果的信息 |
| 预期过程 | 应选哪个能力、是否应澄清、是否应暂停等待确认、是否需要验证、能否调用模拟银行 |
| 预期结果 | 用户最终看到什么状态；银行是否发生资金或数据变化；失败时如何说明 |
| 通过标准 | 可核对的事实，例如“确认前没有提交转账”“银行返回失败时不说成功”；避免只写“回答合理” |
| 运行记录 | 实际结果、通过／失败、失败原因及证据链接；编写初稿时可留待运行后填写 |

**最小示例（01 转账）**：用户说“给张三转 100 元”，模拟数据中张三是可识别收款人。预期先展示收款人、金额和扣款账户，并暂停等待用户明确确认；确认前银行转账次数为 0。用户确认后才提交一次，最终回执以模拟银行返回为准。若用户取消，最终转账次数仍为 0。成功与取消应分成两条用例，便于分别判断。

使用虚构用户和模拟银行数据；不要把真实账户、验证码或个人资料放进评测集。一个用例只围绕一个主要判断点，复杂任务可以拆成多条。

可直接复制下面的简表填写首批用例，后续确定运行格式时再转换，不必现在先设计复杂字段：

```markdown
| 编号 | 类别 | 依据 | 用户输入与起始条件 | 预期过程 | 预期结果与通过标准 | 运行结果 |
|---|---|---|---|---|---|---|
| 01-001 | 正常 | 01 PRD 对应验收例 | …… | …… | …… | 待运行 |
```

## 三、按开发阶段怎样交付

1. **首批代表性用例**：01 先覆盖正常完成、取消／拒绝、银行失败或待核实；其他业务与安全负责人同步写各自的少量正常、关键异常和边界用例。写出输入、预期结果和通过标准即可开工。
2. **代码跑通后扩充**：根据实际接口和出现的问题补充不同说法、缺信息、权限、暂停恢复、部分失败等分支；端到端集由 Erwin 选少量关键路径，不复制全部业务集。
3. **完整验收集**：沿用 09-23 预审会定的规模目标——每个功能至少 10 条、每类异常至少 3 条。数量不能代替质量；每条都应有明确依据和可判断的结果。公开数据若与本项目需求吻合，可注明来源并改成虚构场景；不吻合就自行编写。

用例与契约的关系按[公共契约第 9 章](../docs/contracts/公共契约-2026-09-23.md#9-验收对照防拉通机制②)维护：**契约条目 ↔ 验收例 ↔ 评测用例**。运行后记录通过情况，才能作为开发验证和答辩证据；仅有用例文本不算验证通过。
