## 一、背景（一句话）

我们的系统里**不接真实银行**，而是自己造一家"模拟银行"。它**不是一个面向用户的场景**，而是**转账、账单、跨场景联动三个场景共用的一家银行**——用户不会直接跟它说话，是业务模块在用它办事。

**已定前提**：行业通用规则优先采用真实监管口径，不自创。相关调研已完成，规则条目与出处见 [mock-bank-rules.md](../research/mock-bank-rules.md)。

**这份 PRD 写什么、不写什么**：

| 要写（业务能力） | 不写（留给技术规格） |
|---|---|
| 银行对外提供哪些能力 | 接口地址、字段名 |
| 每项能力的业务规则 | 数据表设计 |
| 用户和业务系统会看到什么 | 内部实现方式 |
| 什么情况拒绝、拒绝时说什么 | 错误码的数字编号 |
| 哪些场景在用、以后谁会来用 | 代码怎么组织 |

**衡量标准**：读完这份 PRD 的人，应该能讲清楚"我们模拟的银行像不像一家真银行"，而不是"程序怎么写"。

## 三、逐章要写什么

### 第 1 章 · 这个场景是什么

| 小节 | 写什么 |
|---|---|
| 1.1 和其他场景有什么不同 | 它不是面向用户的场景，是所有业务共用的银行 |
| 1.2 一句话目标 | 给整个系统提供一个"像真的"银行：有一本账、有真实规则、说一不二 |
| 1.3 谁在用它 | 现在：转账、账单、联动；以后：理财、卡片、订阅代扣 |
| 1.4 它不做什么 | 不猜用户意图、不跟用户直接对话、不替业务做判断 |

### 第 2 章 · 功能范围：六个能力域

**这是全篇地基。** 一上来摆出"银行一共能提供这几类服务"，后面每章是其中一类的展开。

| 能力域 | 一句话 | 现在谁用 | 以后谁用 | 本阶段 |
|---|---|---|---|---|
| 账户 | 谁的钱、多少、什么状态，还剩多少能转 | 转账、联动 | 理财、卡片 | 做 |
| 交易 | 把钱转出去、付出去 | 转账、联动 | 订阅代扣 | 做 |
| 查询 | 查余额、查流水、查一笔交易到底怎么样了 | 账单 | 全部 | 做 |
| 清算 | 钱多久到、收不收手续费 | 转账 | 联动 | 做 |
| 资金管理 | 先把钱冻住，花多少扣多少，剩下的放回来 | 联动 | 理财 | 做 |
| 签约授权 | 约定"以后每月自动扣" | 还没有人用 | 订阅代扣 | **预留，不实现** |

**六个域按"能力"命名，不按"业务"命名**——不说"给转账用的接口"，说"资金划转能力"。这样以后新业务来了，需要的是同一件事就直接复用，不用新加一整套。

**每个域内部要守的一条划分原则：把「查、验、算」和「真的动钱」分开。** 银行不能只有一个"转账"动作——得先能问"这个收款人是谁、户名对不对"（验），先能问"今天还剩多少额度"（查），先能问"这笔收多少手续费、几点到"（算），最后才是"扣钱"。少了前面这几个，业务模块就没法在动钱之前把方案确认清楚。**这条原则贯穿第 3—7 章。**

### 第 3—8 章 · 逐个能力域展开

每个域统一写成两块：**「这个域管什么」+「业务规则表」**。

| 章 | 能力域 | 要写哪些业务规则 |
|---|---|---|
| 3 | 账户 | 账户分几类（demo 只用Ⅰ类，但字段留三类）；有哪几种状态、各状态能做什么（**分三种：正常 / 冻结 / 销户**）；余额和"能用的余额"差在哪；**核验收款人——给账号和姓名，返回是否匹配 + 打码后的姓名（张\*三）**，转账确认单上要显示；**限额余量查询——问"今天/今年还剩多少额度"，供业务在动钱前排多笔支出** |
| 4 | 交易 | 一次能转多少（单笔/日累计/年累计）；~~分不分行内跨行~~（**D03 已定：不模拟行内 / 跨行差异，两者都即时到账**）；~~收不收手续费~~（**D03 已定：一律不收，恒为 0，不做收费开关**）；**动钱前先试算**（算出这笔手续费——恒 0——和预计到账时间，业务拿着这个去问用户）；转给谁算"陌生账户"；**预置一个涉诈黑名单账号，向它转账时银行直接拦下并给出拒绝原因**（对应反诈法第十八条的处置动作，这是安全演示的必走一幕） |
| 5 | 清算 | ~~有哪几种到账速度；**必须让用户挑，挑完才能办**~~（**D15 已定：本轮不做非实时到账，主线与确认单只有"实时"一种取值**；字段保留三种取值以备后续） |
| 6 | 查询 | 能查多久以前的流水；一笔流水里有什么信息——**必须带分类标签：交易性质（消费/转账/退款/利息）+ 商户类别 + 方向（流入/流出），否则账单场景没法做分类统计**；~~消费统计基线（近 N 月平均、单笔最高）~~（**X4 已取消：银行不给基线，账单模块从全量流水本地自算**）；数据是实时还是有延迟；**单笔交易回查**（凭交易编号查某一笔到底怎么样了，跟查流水是两件事） |
| 7 | 资金管理 | 能不能"先冻住"一笔钱；**冻住的钱可以直接扣——先冻 500，花 300 就从里面扣 300，剩 200 释放**（这是多笔外部支付能跑通的关键，不能只支持"全冻全解"）；冻住的钱算不算已花（**D06 已定：冻结/释放不计消费流水，只留痕；从冻结扣款才生成流水**）；**已完成的交易能不能撤——没提交的能撤，已经到账的一律不能单方面撤销或退款**（**D11 已定：不给撤销/退款，但没花完的冻结必须释放**）；~~本阶段做到哪一步（待拍板）~~（**D10 已定：冻结 + 分笔核销 + 差额释放**，详见 PRD 正文） |
| 8 | 签约授权 | 只写一段：为"订阅/代扣"预留，当前不实现，未来提供什么（**写一段就够，不展开**） |

> **初始化与演示支撑（两句话说清，够用）**：Mock Bank 启动时要预置一套种子数据——**1 个主测试账户 + 近 3 个月的消费流水**（流水要带不同分类标签、能支撑月度对比和异常识别）。空库跑不了账单演示。
>
> 另外要有一个**演示开关：让某一次交易"故意慢一次"**（不按时返回）。用来演"结果未知 → 按原编号回查 → 绝不重发"这条路。**不开时一切正常**，不影响其他演示。这是这条安全用例唯一可靠的触发方式——回查窗口只有 10 秒，自然超时几乎撞不上。

> **刻意不写进这份 PRD 的东西**（真实银行有，但 demo 走不到，写了就是为不做的功能写需求）：跨行退票与资金退回、清算时间窗口与日终维护、认证方式分级限额（四层孰低）、睡眠户等扩展账户状态、卡片自主锁卡、理财持仓展示、代扣协议的限额与频次细则。**以后真扩到卡片/理财/订阅场景时再回来补。**

> **答辩时怎么解释这些排除**（可直接引用）：本项目是端到端实时演示，为保障链路稳定性与聚焦核心交互，上述非关键路径做**环境假设豁免**——即"默认清算全天候、默认无介质差异、默认无退票"。这是范围选择，不是能力缺失。

### 第 9 章 · 关键输入、输出与所需能力

**这章回答"银行和业务之间怎么交接"。** 不写字段名，只写业务含义。

| 能力 | 谁给它什么 | 它返回什么 | 对方拿到后能干什么 |
|---|---|---|---|
| 核验收款人 | 账号 + 姓名 | 是否匹配 + 打码姓名（张\*三） | 转账确认单上显示，让用户认人 |
| 查限额余量 | 哪个账户 | 今天还剩多少额度、今年还剩多少 | 排多笔支出前先算够不够 |
| 试算费用与到账时间 | 金额（**不再区分行内 / 跨行**） | **手续费恒为 0、到账时间恒为即时**（D03） | 动钱之前拿给用户看 |
| 划转资金 | 金额、付谁收谁、一个交易编号 | 成功 / 失败 / 处理中 / **结果未知**；**涉及风控时返回"拒绝办理"及原因** | 决定下一步能不能继续 |
| 冻结金额 | 金额、冻结原因 | 冻住多少、编号 | 下单前先占住钱 |
| 从冻结里扣款 | 冻结编号、本次扣多少 | 扣掉后还剩多少冻着 | 多笔支付一笔一笔核销 |
| **释放冻结金额** | 冻结编号、释放多少 | 解冻成功，钱回到可用余额 | 多笔支付结束后，把没花完的预算退回来 |
| 查询流水 | 哪段时间、哪个账户 | 流水明细（带分类标签）；没有就说没有 | 做分类统计、找异常 |
| 查询消费基线 | 哪个账户、看几个月 | 月均消费、单笔最高 | 判断某笔消费是不是"异常地高" |
| 查交易结果 | 交易编号 | 那笔钱现在到底怎么样 | 超时后核对，避免重复扣款 |

**这张表是业务模块找银行要能力的唯一入口。** 第 3—8 章正文里写了的能力，这里都要有一行——**正文有、表里没有，业务同事就不知道该管银行要什么。**

**本章核心一条**：**银行说的才算数。** 业务系统不能自己猜"应该成功了吧"。这是整个系统的铁律之一。

> **超时后怎么查（已定）**：每 **3 秒**回查一次，**最多等 10 秒**。10 秒还没确认下来，就转成"需要关注"如实告知用户，**绝不重发交易**。
> 时间定得短是为了不拖累演示体验；但**"结果未知"这条路必须能演出来**——演示时用一个可控的延迟场景（模拟网络抖动）触发，让评委看到"不确定时先查、不重发"这个动作。

### 第 10 章 · 主要异常、修改与取消

| 类别 | 银行该告诉用户什么 |
|---|---|
| 条件不满足 | 钱不够差多少、超了哪个限额、账户什么状态 |
| 交易失败 | 为什么失败，用人话讲 |
| **结果不明** | "还没确认成功还是失败"——不能说成失败，更不能说成成功 |
| 用户取消 | 没办成的能撤；已经办出去的要查了才知道 |
| 重复请求 | 同一笔交易重复提交，只能扣一次钱 |

### 第 11 章 · 安全与确认考虑

- 银行侧要做哪些检查：是不是本人账户、账户能不能用、钱够不够、超没超限额
- 哪些动作必须用户确认：动钱之前
- **欺诈防范**：转账前防骗提示；发现可疑交易可采取的处置措施
- 别人来查别人的账：一律拒绝，且不告诉对方"这个账户存不存在"
- 适老化：老年人看得懂的提示，防骗话术更直白

### 第 12 章 · 简单业务流程图

一张总图即可，画出业务模块去银行办事的主干道：

```
业务模块（转账 / 账单 / 联动）
        |
        | ① 先查：账户能不能用、钱够不够、超没超限额
        v
   银行检查 ──不通过──> 说清原因（钱不够 / 超限额 / 账户异常）
        | 通过
        v
 ② 业务模块拿完整方案找用户确认   ← 这一步在业务模块里，不在银行
        |
        v
 ③ 提交交易（带一个交易编号）
        |
        v
   银行执行 ──> 成功 / 失败 / 处理中 / 结果未知
                                      |
                                      v
                          ④ 按原编号回查，确认到底怎么样
```

**图里要能一眼看出**：银行只管"查条件、办事、给真实结果"，中间"找用户确认"是业务模块干的。

### 第 13 章 · 验收例子与待确认问题

验收例子按六个能力域各出至少一条：

| 验证什么 | 期望 | 绝对不能发生 |
|---|---|---|
| 限额到了 | 拒绝办，说清超了哪一项 | 悄悄放行 |
| 钱不够 | 拒绝办，说清差多少 | 办成"部分转账" |
| 提交后超时 | 说"结果未知"，按原编号回查 | 当失败重发一次 |
| 同一笔重复提交 | 只扣一次钱 | 扣两次 |
| 查别人账户 | 拒绝，不说账户是否存在 | 泄露任何信息 |
| 账户被冻结 | 拒绝办，说明状态 | 照常扣款 |
| **转给涉诈黑名单账号** | 银行直接拦下，给出拒绝原因和处置动作 | 照常转出；或拦截了却不说原因 |
| **先冻 500，分两笔花掉 800** | 第二笔拒绝，说清冻结额度只剩 200 | 超冻结额度照扣 |
| **花掉 350 后退回剩余 150** | 解冻成功，钱回到可用余额，回执说清 | 钱一直冻着、或回执不提 |
| **已经到账的交易要求撤销** | 明确说不能单方面撤销，指引联系收款方 | 承诺退款、假装能撤 |
| **查一笔超时的交易** | 按交易编号给出真实状态 | 查不到就当成没发生 |

**待确认问题分两类，分开列**：

- **需要产品拍板的**：限额具体定多少、资金冻结做到哪一步、**能不能取消退款（到账后一律不可单方面撤销）**、要不要模拟风控拦截
- **查不到权威出处的**：柜面限额、脱敏格式、超时后回查的间隔——**如实标注"这是我们的设计选择"**，不假装是行业规定

## 四、范围纪律

**这份 PRD 的取舍标准只有一条：演示里会不会走到这一步。**

真实银行有的功能，如果我们的三个场景永远触发不到，就不写进来——**写了就是为一份不做的功能写需求，既是负担也是失焦**。已在第 3—8 章下方列出刻意排除的清单。

对应地，扩展性不靠"提前把以后的功能写细"来体现，而靠三件事：

| 在哪体现 | 怎么做 |
|---|---|
| 第 2 章能力域表 | 每个域标出「现在谁用 / 以后谁用」，扩展方向一眼可见 |
| 第 8 章签约授权 | 显式保留、标注"预留，不实现"——**不假装做得完，也不让它消失** |
| 命名规范 | 按"能力"命名而非"业务"命名，新业务复用已有能力 |

**答辩时的用处**：如果被问"只做三个场景，扩展性呢"——直接翻第 2 章，六个域盘过了，缺的是哪几个、加能力即可。

## 五、为什么这样分章（供审查参考）

| 考虑 | 说明 |
|---|---|
| 按能力分，不按业务分 | 业务是变的，能力是稳的。按业务分会逼着以后每条新业务都加一章 |
| 域内区分「查/验/算」和「动钱」 | 银行不能只有一个"转账"动作。少了前置的查、验、算，业务没法在动钱前把方案确认清楚 |
| 每个域对应"一个能说清谁在用"的服务 | 说不清谁在用的章节，多半是技术细节混进来了 |
| 不写技术实现 | 初步 PRD 的定位。字段、接口、错误码编号留到技术规格 |
| 验收例子并入各域 + 第 13 章汇总 | 交付要求要"每类异常有例子"，散在各域里反而容易漏 |

## 六、审查记录

### 第二轮审查（采纳 4 处交接缺口 + 1 项初始化要求）

第二轮按"演示会不会触发"逐帧推演，发现的都是**第 9 章交接表漏行**——正文写了能力，业务模块却看不到该管银行要什么：

| 采纳 | 落点 | 为什么是真缺口 |
|---|---|---|
| **涉诈风控拦截** | 第 4 章规则 + 第 9 章返回 + 第 13 章例子 | 转账 T12 与安全底座四类威胁都靠它，是 30% 安全分的演示重头戏，原先交接表一行都没有 |
| **释放冻结金额** | 第 9 章新增一行 | 原先表里只有"冻结"和"从冻结扣款"，**缺"释放"**；06 生日场景必然走到（冻 500 → 花 350 → 退 150） |
| **核验收款人** | 第 3 章 + 第 9 章 | 转账附录 A 明确要"候选列表、掩码信息、匹配情况" |
| **查询消费基线** | 第 9 章 | 第 6 章写了规则，交接表没列，账单同事不知道要什么 |
| **种子数据要求** | 第 3—8 章下方一句话 | 账单演示需要近 3 个月流水，空库跑不了 |
