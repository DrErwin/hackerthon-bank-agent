## 一、用户目标与功能范围

> **本章已由 BP 填好，是从赛题与团队决议推出来的前提。** 你不用重新论证，读懂就行；后面所有章节都要跟这一章对得上。
> 出处：赛题 06 场景要求、团队 kick-off 决议（用户群走适老化、演示场景锁定这三个）。

### 1.1 谁用、遇到什么问题

- **目标用户**：已登录的个人银行用户，重点客群是**银发人群（适老化场景）**。他们的共同困难是：**有意愿办事，但不擅长在多处之间来回操作**——不熟悉比价、不爱反复填表、对"钱分几笔扣、扣了多少"看不清楚。
- **用户问题**：当用户有一个**既要动钱、又要协调多个外部服务**的完整生活目标时（比如给家人过生日），现在只能自己分头做：先估自己还有多少钱、再一个个挑商品比价、分别下单、分别付款、还要自己盯配送时间。过程繁琐、容易漏项、更麻烦的是**看不清总共花了多少**。
- **用户想要的**：用一句自然语言把整套安排说出来，系统帮他把事办成；同时**在真正动钱之前，把花了多少、买什么、送到哪、什么时候到，一次看清楚**。

### 1.2 这个场景和普通业务场景有什么不同

**这一节是整份文档的地基。** 拿 01 转账当参照物对比：

| | 普通业务场景（01 转账 / 02 账单） | 06 跨场景联动 |
|---|---|---|
| **用户说什么** | 指令明确："给妈妈转 500" | 目标模糊："我妈生日快到了，你帮我安排下" |
| **要做几件事** | 固定一件 | **数量不定**，可能买一样，也可能买三样；由 AI 判断 |
| **流程固定吗** | 固定：一条流程走到底 | **不固定**：允许 AI 在范围内自行选路、自行决定拆几件事 |
| **PRD 要定义什么** | 这条流程怎么走 | **AI 被允许做什么、不许做什么** |
| **谁提供能力** | 自己实现 | **自己几乎不做事，靠串联其他场景的能力** |

**由此得出三条核心要求，后面每一章都在为它们服务：**

| # | 要求 | 落在哪 |
|---|---|---|
| R1 | **AI 能自主编排**：同一句话能拆出不同的件数、不同的路径 | 第 2.4 节节点表 + "哪些交给 AI" |
| R2 | **约束不可绕过**：AI 再自由也越不了线 | 第 5 节 + 第 2.4"必须固定"栏 |
| R3 | **能力可复用**：加新的联动任务只换配置和用例，不重写流程 | 第 2.4 节节点表 |

### 1.3 一句话目标

> 用户说一句带**预算**和**时间**要求的生活目标，系统在预算、时间和授权范围内自行拆解、串联银行与外部服务能力，在用户**明确确认**后完成办理，并**只依据实际返回结果**报告。

**三个词是关键，写别的内容时不能丢**：预算（全局约束）、确认（动钱前必须停）、真实返回（不许模型编结果）。

### 1.4 功能范围

本轮只做这三个任务，它们不是三个独立功能，而是**同一套编排能力的三个用例**：

| 功能 | 本阶段建议 | 说明（它联动了什么？） |
|---|---|---|
| **生日礼物编排** | 建议包含 | 联动"银行资金能力 + 外部生活服务"：一句话完成花样数目的礼物预订，并保证总价不超预算、送达时间可满足 |
| **账单驱动的预算约束** | 建议包含 | 联动"账单分析 → 消费决策"：用近期支出算出还能花多少，**把这个额度交给别的任务当约束用** |
| **收入 / 资金分配** | 建议包含 | 联动"收入到账 → 多笔资金动作"：把一笔钱（工资、奖金、报销等）拆成几份分别处理 |

**为什么是这三个**：
- 第一个覆盖"多件商品 + 未来时间 + 外部不确定性"，是**编排能力的主要证明**；
- 第二个覆盖"**真的去调用另一个场景**"，证明 06 是编排者不是自己干活；
- 第三个覆盖"**多笔动钱**"，证明同一套节点能撑起资金型任务。

**每个新增任务都必须复用第 2.4 节那套节点。** 如果某个任务需要发明一堆新节点，说明它不该放进这一轮。

## 二、正常业务流程

> **一个 SOP 对应一个完整任务**，三个任务各写一组。
> **先写完 2.1—2.3 的全部步骤，再去做 2.4。** 顺序不能反——节点是从步骤里抽出来的。

### 2.1 任务 A · 生日礼物编排

**一句话目标**：<用户说一句什么话，系统帮他办成什么>

#### 怎么填「触发」

**怎么想**：把自己当成用户，想想他会怎么开口。**故意想几个说得不全的**——因为真实用户不会把预算、地址、时间一次说全。

**填什么**：至少 5 句，覆盖这几种：

| 类型 | 你得想出至少一句 | 你想的（填这里） |
|---|---|---|
| 信息完整 | | |
| 没说预算 | | |
| 没说地址或时间 | | |
| 说得特别含糊 | | |
| 只要其中一部分东西 | | |

**为什么要凑齐这几种**：第 2.4 节要证明"流程不能写死"。如果五句触发都是完整指令，你就没法证明这一点，评审时会被问倒。

#### 怎么填「步骤」

**怎么想**：从用户说完话开始，一步一步走到"结果告诉用户"，中间每一步都问自己三件事——

1. 这一步**需要什么信息**？信息从哪来？
2. 这一步**帮用户做了什么**？
3. 这一步**得到了什么**，交给下一步？

**填什么**：① …… ② …… ③ ……

**提示**：步骤写到"能看出信息怎么流动"就够了，不用写到界面动作。

#### 怎么填「例外」

**怎么想**：**永远假设用户不按流程走。** 逐个问题逼自己：

| 逼自己的问题 | 你的答案 |
|---|---|
| 信息不够怎么办？ | |
| 办不成（超预算 / 没货 / 送不到）怎么办？ | |
| 用户中途改了关键信息怎么办？ | |
| 用户反悔了怎么办？ | |
| 只办成一半怎么办？ | |
| 办理超时、不知道成没成怎么办？ | |

**提示**：每个答案都要写"告诉用户什么 + 系统接着做什么"两件事，只写"报错"不算。

#### 怎么填「确认点」

**怎么想**：回到步骤表，**圈出所有会动钱、会改数据、会读敏感信息的步骤**。然后问：这些步骤执行前，用户需要看到什么，才敢点"确认"？

**填什么**：<哪几步？确认时给他看什么？>

**提示**：别忘了写两条——"什么不算确认"（含糊回答）和"什么变化会让确认作废"。

#### 怎么填「回执」

**怎么想**：**按实际会显示的样子写完整句子，不要写"告知用户结果"。** 而且要分情况写：

| 情况 | 你的文案 |
|---|---|
| 全部成功 | |
| 只办成一半 | |
| 结果不确定 | |
| 用户取消 | |

**提示**：成功回执里**不要写"预计某时送达"就当成功**——送达是以后的事，要单独一句。另外，如果本轮没有取消/退款能力，就别在文案里承诺"可以帮你取消"。

### 2.2 任务 B · 账单驱动的预算约束

**一句话目标**：<填写>

**触发怎么想**：用户想知道"自己还能花多少"时会怎么问？注意他可能不是直接问数字，而是带着目的问（"想给我妈过个生日，看看预算"）。

| 项目 | 填写内容 |
|---|---|
| **触发** | <至少 3 句；包含一句带目的的> |
| **步骤** | <这条链上，"查数据"和"算额度"分别是哪一步？> |
| **例外** | <没有账单数据怎么办？用户不认这个额度怎么办？> |
| **确认点** | <这条链不动钱。那还需要用户确认什么？> |
| **回执** | <额度是怎么算出来的，必须说清楚> |

**提示**：这条链的价值是**给别的任务提供依据**。所以「步骤」的最后一步应该是"把这个额度交出去"，而不是"结束"。

### 2.3 任务 C · 收入 / 资金分配

> 用户拿到一笔钱（工资、奖金、报销、退款等），系统按约定分成几份分别处理。

**一句话目标**：<填写>

| 项目 | 填写内容 |
|---|---|
| **触发** | <至少 3 句；包含一句"老规矩"这种依赖过去的说法> |
| **步骤** | <"分几份"是谁定的？"每份多少"怎么来的？> |
| **例外** | <实际到账和用户说的不一样怎么办？"老规矩"但没有历史记录怎么办？> |
| **确认点** | <这条链每一笔都动钱。方案单上要逐笔列什么？> |
| **回执** | <三笔里成功两笔，文案怎么写？> |

**提示**：如果用户说"老规矩"但系统没有历史记录，**不能自己编一套比例**——这是很容易漏的一个例外。

### 2.4 三个任务共用的节点表 ★整份文档的重点

> **这一节是 06 的 PRD 和普通 PRD 最大的区别。**
> 前面三节写的是"每个任务长什么样"，这一节写的是"它们底下共用什么"。

#### 第一步：先把三个任务的步骤摊在一起

填完 2.1—2.3 后，把它们全部步骤抄到一个大列表里。**别急着抽象，先看清有哪些动作。**

#### 第二步：找重复出现的动作

**怎么合并**：逐个问自己这两个问题——

| 问题 | 是 → 怎么办 |
|---|---|
| 这两个动作，**做的是同一类事**吗？ | 合并成一个节点 |
| 它们**动钱 / 可逆 / 要确认**的属性一样吗？ | 不一样就**分开**，不要硬合并 |

▸ **合并示范**（看这条推导，比看答案有用）：

```
三个任务摊开后的原始动作：
  A：识别生日需求 / 问缺的地址 / 查余额 / 定买几样 / 查花和蛋糕 /
     算总价 / 出确认单 / 付款 / 下单 / 报结果
  B：识别预算需求 / 问查哪段时间 / 查账单数据 / 算可花额度 / 确认额度 / 报结果
  C：识别分配需求 / 问分几份 / 查是否到账 / 定分几份 / 算每份金额 /
     出方案单 / 逐笔转账 / 报结果

合并过程（只演示几个）：
  "识别生日需求" + "识别预算需求" + "识别分配需求"
      → 都是"把原话变成结构化信息"，属性一样（不动钱、不用确认）
      → 合并成一个节点

  "查余额" + "查账单数据" + "查是否到账"
      → 都是"只读获取事实"，属性一样
      → 合并成一个节点

  "付款/转账" + "下单"
      → 都动钱，但"转账"部分可撤销、"下单"不可撤销
      → 属性不一样 → 分开成两个节点

  "出确认单" + "出方案单" + "确认额度"
      → 都是"展示+等用户明确确认"，属性一样
      → 合并成一个节点
```

**推导到这里你自己就能得出结论**：合并的依据不是"名字像"，而是**这三列属性一样不一样**。

#### 第三步：填表

| 编号 | 节点 | 干什么 | 会不会动钱 | 能不能撤销 | 要不要用户确认 |
|---|---|---|---|---|---|
| N1 | | | | | |
| N2 | | | | | |
| N3 | | | | | |
| N4 | | | | | |
| N5 | | | | | |
| N6 | | | | | |
| N7 | | | | | |
| N8 | | | | | |
| N9 | | | | | |
| N10 | | | | | |

**填的时候注意三件事**：

1. **"干什么"要写成同类动作的共性，不要写成某个任务的具体动作。** ✗"查花和蛋糕" → ✓"查方案/数据"。
2. **后三列是这张表存在的理由。** 第 5 节的安全规则全靠它。
3. **编号顺序按事情发生的先后排**，方便第 4、6 节引用。

#### 第四步：三个任务分别用到哪些节点

| 节点 | A 生日 | B 预算 | C 收入分配 |
|---|---|---|---|
| N1 | | | |
| N2 | | | |
| N3 | | | |
| N4 | | | |
| N5 | | | |
| N6 | | | |
| N7 | | | |
| N8 | | | |
| N9 | | | |
| N10 | | | |

**怎么自检**：如果 B、C 需要加很多新节点，说明你**抽得太细了**——回去看第二步，把"做的是同一类事"的再合并。
目标状态是：**三个任务的流程图不一样，但节点表是同一套。**

#### 第五步：哪些必须固定、哪些交给 AI

**这一栏是整份 PRD 里唯一直接回答"AI 自由度"的地方，必须填。**

**怎么想**：对着节点表**一行一行过**，每行问两个问题：

| 问自己 | 如果答案是"是" | 如果答案是"不是" |
|---|---|---|
| 这一步不做，会不会出事？ | 写进**必须固定** | —— |
| 这一步的顺序能不能换？ | 写进**必须固定** | —— |
| 这一步的做法不同，结果会不会不一样？ | —— | 写进**交给 AI** |

**还有一条一定不能漏**：跨任务的**全局约束**。三个子任务的金额加起来能不能超过预算？这个不变量必须写进"必须固定"。

| | 内容 |
|---|---|
| **必须固定（AI 不许变）** | <哪几个节点必须做；哪些顺序不能换；哪些数不能超> |
| **交给 AI 自己定** | <哪几个环节允许它自己决定> |

**填完自检**：假设 AI 完全失控、想尽办法绕过流程，它最多能自由到哪一步？
如果答案是"最多换个商家、改个顺序、多问一句"，你就写对了。
如果答案是"它可以不做核对、可以跳过确认、可以超预算"，说明"必须固定"那栏写漏了。

## 三、关键输入、输出与所需能力

### 3.1 整个任务的输入与最终输出

**怎么想**：输入 = 没有它这活干不成的东西。输出 = 用户最终拿到什么。

**填什么**：
- **任务需要的信息**：<逐项列出，每项标"必填 / 可选 / 条件必填">
- **任务最终返回**：<用户拿到什么；哪些结果需要后续再查>

**提示**：「条件必填」这种最容易被漏——比如"预算"就是条件必填：用户给了就用他的，没给才去查。

### 3.2 关键步骤依赖

**怎么想**：从 2.4 的节点表里，**挑出那些需要别的模块帮忙的节点**。普通的展示、内部整理不用列。

**填什么**：

| 关键步骤（填节点编号） | 需要什么信息，来自哪里 | 需要什么能力 / 可能由谁提供 | 希望返回什么 |
|---|---|---|---|
| N? | <用户给的还是系统查的？> | <哪个模块？不确定就标待确认> | <用人话描述结果> |
| | | | |
| | | | |

**提示**：能力暂时不存在也可以写，标"待确认"。**不要默认别人会给你做。**

**06 的边界**：<06 不做什么？>

**怎么想**：翻回 1.2 那张对比表。06 是编排者不是执行者，所以——不直连银行、不复刻别人的业务规则、不读别的模块的私有数据。

## 四、主要异常、修改与取消

**怎么想**：第 2 节写例外时，你是**站在单个任务里**想的。这一节要**跳出来**，把三个任务的例外归归类，看能不能用同一套说法覆盖。

**填什么**：每类都写"告诉用户什么 + 随后怎样处理"。

| 类别 | 告诉用户什么 | 随后怎样处理 |
|---|---|---|
| **信息不足或含糊** | <缺什么要追问？多个候选怎么办？> | |
| **业务条件不满足** | <超预算、钱不够、没货怎么解释？> | |
| **用户修改、取消或重复请求** | <哪些信息要重新核对？已经开始办了还能取消吗？怎么避免重复？> | |
| **查询或办理失败、超时、结果不明** | <先查、等，还是停？> | |
| **中断 / 重新打开** | <怎么确认已经办到哪？> | |

**只办成一半怎么写**

**怎么想**：这是 06 最常见、也最容易写砸的情况。挑生日场景具体想一遍：花成功、蛋糕失败，用户此刻看到屏幕，他想知道什么？

**填什么**：<三个任务各写一遍——用户看到什么、能不能继续、已经花的钱怎么算>

**提示**：绝对不要用"任务已部分完成"这种系统口径，要用用户能懂的话说清"哪个成了、哪个没成、扣没扣钱"。

## 五、安全与确认考虑

### 5.1 哪些步骤涉及敏感信息或动钱

**怎么想**：**直接从 2.4 节点表抄过来**——"会不会动钱"和"要不要确认"两列打了勾的，就是这一节要写的。

**填什么**：<按节点编号列出来>

### 5.2 不许做的事

**怎么想**：先别写"要小心"。用这个办法找素材——**翻回前面所有章节，把"AI 有可能走错"的地方都找出来**：

| 从哪找 | 会找到什么 |
|---|---|
| 2.4 节点表的"要不要确认"列 | 哪些动作不能没确认就做 |
| 2.4"必须固定"栏 | 哪些数不能超、哪些顺序不能换 |
| 2.1 的「例外」 | 哪些失败情况不能糊弄过去 |
