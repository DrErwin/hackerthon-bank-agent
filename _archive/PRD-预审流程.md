# PRD 预审流程

> 用途：在联合评审会前，快速检查各负责人提交的初步 PRD，找出缺失内容、跨模块问题和需要拍板的事项。
>
> 定位：初步 PRD 不要求达到可以直接写代码的程度，但必须能够讲通主要业务、关键异常、模块交接和安全边界。字段、接口、数据库和代码结构留到技术规格阶段。

## 一、预审要得到什么

预审不是替负责人重写 PRD，也不是提前设计全部技术方案。预审完成后，应得到四项结果：

1. 每份 PRD 是否已经具备开会讨论的基础。
2. 哪些内容由原负责人在会前补充。
3. 哪些跨模块或公共规则需要在评审会上讨论。
4. 哪些问题需要 PM 或对应负责人最终拍板。

## 二、什么样的初步 PRD 可以进入评审

至少能够回答下面七个问题：

- 用户是谁，想办成什么事，最后得到什么结果？
- 当前阶段做什么、暂缓什么、明确不做什么？
- 正常情况下，从用户提出需求到返回结果怎样走完？
- 信息不足、修改、取消、失败、超时或结果未知时怎么办？
- 哪一步需要其他模块、模拟银行、安全底座或前端提供能力？
- 哪一步会动钱、读取敏感信息或产生外部影响，确认时给用户看什么？
- 至少一个正常例子和几个关键异常，什么算正确，什么绝对不能发生？

如果主流程、责任边界、关键安全规则或结果含义仍说不清，应先请负责人补充，再进入联合评审。

## 三、逐份 PRD 的预审顺序

### 第一步：一句话复述目标

尝试写出：

> 谁在什么情况下，希望系统帮他完成什么，最后拿到什么结果。

无法用一句话说清时，记录为“目标或范围不清”。

### 第二步：走一遍正常流程

按照下面的顺序阅读：

```text
用户提出需求
→ 系统获得必要信息
→ 查询、计算或生成候选结果
→ 用户补充、选择或确认
→ 系统执行实际操作
→ 核对真实结果并回复用户
```

在每个关键步骤检查六件事：

| 检查项 | 要问的问题 |
|---|---|
| 谁负责 | 用户、业务模块、安全底座、模拟银行、前端还是其他模块？ |
| 输入 | 这一步需要什么业务信息？ |
| 来源 | 信息来自用户、系统查询还是其他模块？ |
| 输出 | 返回候选、确认请求、操作结果还是报告？ |
| 异常 | 没有结果、失败或结果未知时怎么办？ |
| 用户体验 | 用户此时能看到什么，是否需要等待、选择或确认？ |

### 第三步：检查主要异常

初稿不要求穷举全部异常，但至少检查：

- 信息不足或表达含糊。
- 出现多个候选。
- 业务条件不满足。
- 用户修改、取消或重复请求。
- 工具或银行调用失败。
- 超时、处理中或结果未知。
- 多步骤任务部分成功、部分失败。

每个异常至少说清两件事：告诉用户什么，系统接下来怎么办。

### 第四步：检查模块交接

每当 PRD 出现“调用安全模块”“从银行查询”“交给其他业务模块”“由前端展示”等交接时，检查：

1. 谁调用谁。
2. 传递什么业务信息。
3. 对方需要返回什么业务结果。
4. 返回失败或未知时怎样处理。

初步 PRD 不需要写字段名，但业务含义必须明确。

### 第五步：检查安全与确认

检查 PRD 是否说明：

- 读取和修改了哪些敏感数据。
- 哪一步会动钱、修改重要数据或产生外部影响。
- 执行前需要向用户展示什么。
- 哪些内容变化后必须重新确认。
- 越权、诱导或要求跳过确认时怎么办。
- 哪些内容绝对不能进入模型、普通日志或对外展示。
- 至少两项“绝对不能发生”的反向要求。

安全底座负责公共规则，业务负责人负责回填本场景的具体事实。

### 第六步：检查结果与验收例子

至少应有：

- 一个正常成功例子。
- 一个信息不足或多候选例子。
- 一个失败、超时或结果未知例子。
- 一个修改、取消或重复请求例子。
- 一个权限或安全拒绝例子。

初稿不要求写成自动化测试，但应能够判断系统的处理是否正确。

## 四、发现问题后的分类

### A. 会前由原负责人补充

适用于单个 PRD 内部就能解决的问题，例如：

- 主流程缺少明显步骤。
- 没有成功、失败或未知结果的用户回执。
- 没有说明当前是否实现。
- 缺少明显异常或确认内容。

### B. 评审会上讨论

适用于跨模块或公共规则问题，例如：

- 某项能力到底由哪个模块提供。
- 数据能否跨场景使用。
- 一个子任务失败后，后续步骤是否继续。
- 多项操作采用总确认还是分项确认。
- 最终结果由谁汇总和解释。

### C. 由 PM 或指定负责人拍板

适用于讨论后必须形成唯一答案的问题，例如：

- 当前版本范围。
- 模块职责重叠或无人负责。
- 公共契约由谁维护。
- 某项能力是否在本期建设。
- 团队无法自行统一的公共规则。

### D. 留到技术规格阶段

不在 PRD 评审中过度展开，例如：

- API 地址和字段名称。
- Pydantic 模型和状态枚举名称。
- 数据库、存储和代码结构。
- LangGraph 节点怎样拆分。
- 内部算法和 Prompt 怎样实现。

### E. PM 统一整理

适用于不改变业务含义的工作，例如：

- 统一章节、术语和状态叫法。
- 给流程和问题编号。
- 集中整理待确认事项。
- 将会议决议同步到相关文档。

业务内容缺失仍由原负责人补，PM 不替所有人重写。

## 五、预审问题记录表

| 编号 | 来源 PRD / 步骤 | 问题与例子 | 分类 | 影响 | 初步建议 | 负责人 / 决定人 | 状态 |
|---|---|---|---|---|---|---|---|
| Q01 | 待填 | 待填 | 会前补充 / 会上讨论 / 需要拍板 / 技术后置 / PM 整理 | 待填 | 待填 | 待填 | 待补信息 |

状态统一使用：`待补信息`、`待讨论`、`已决定`、`待验证`。

“已经讨论”不等于“已经决定”；决定后还要注明影响哪些 PRD、流程或公共契约。

## 六、预审完成标准

- [ ] 能用一句话说清每份 PRD 的用户目标和最终结果。
- [ ] 当前范围、后续范围和非目标基本可区分。
- [ ] 正常流程可以从头走到尾。
- [ ] 主要异常、修改、取消和结果未知有去处。
- [ ] 模块交接点及双方期望基本明确。
- [ ] 敏感操作、确认内容和禁止行为已标出。
- [ ] 缺口已分为会前补充、会上讨论、需要拍板、技术后置和 PM 整理。
- [ ] 每个重要问题都有负责人或决定人。
- [ ] 已选择一条高风险单场景流程和一条跨场景流程用于会上走查。

达到以上标准即可进入联合评审，不需要等待 PRD 达到可以直接写代码的程度。

## 七、与后续流程的关系

```text
PRD 预审
→ 原负责人补主要缺口
→ 联合评审并形成决议
→ 更新各业务 PRD 和公共范围
→ 用代表性流程验证系统边界
→ 同步定稿架构与公共契约
→ 各模块进入 to-spec → to-tickets → implement
```

本流程是预审清单；完整的会议、契约和开发验证安排见《PM-从PRD评审到开发验证的工作计划》。
**已按本流程完成五份 PRD 的预审，会议安排见 [PRD-预审会安排](PRD-预审会安排.md)**（含冲突清单、议程与走查例子）。
