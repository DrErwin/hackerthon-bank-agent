## 生日配送与资金回执（v05-cross-business/05）

配送阶段 `interaction.required_fields == ["delivery"]`：页面将原文仅提交
`POST /api/v1/tasks/{id}/details`（`kind="delivery"`）；收到 `detail_ref` 后，
用同一交互的 `/inputs` 自动发送 `text=detail_ref`。用户无需抄编号，聊天不接收配送原文。
重复请求保留原 `request_id`；旧交互、失效会话与跨用户/轮次/任务仍按既有规则拒绝。
2026-10-25 用户确认不新增配送引用独立有效期。

开始有银行写入事实后，等待输入、确认、验证及最终回执均保留 `CrossTaskView.steps`。
页面按 `action` 区分 `bank.freeze_funds`、`bank.create_order`、`bank.capture_frozen`、
`bank.release_frozen`；`amount_fen` 来自对应银行回执，`operation_id/result_ref` 可追溯。
订单的 `order_id/payment_status` 区分创建和付款，付款未知时不填 `paid`。
只读行 `birthday-remaining`（`bank.get_freeze`）给出银行最后核实的未消费冻结金额；
存在未知写入时金额留空。收尾服务返回消费总额时，`birthday-consumed` 同样直接转呈该事实。
释放未知/被拒时不填释放金额、不关闭占用，恢复仅做原操作核实与限定收尾。
`birthday-*` 行是银行事实的展示投影，不注册新工具、不派发新子任务。

## 生日个人预算（v05-cross-business/06）

`CrossStartInput.constraints`保留本次上限、个人预算范围/用途/限额或准确引用、付款账户和受控配送/送达时间。
生日预算问题中的“设置本月当前账户全部消费的个人预算”也可提出候选；候选不是生效约束。
只有原任务的专用F10当前来源、原交互/计划及完整候选相符，Cross才保存采用；模型代答不采用。
修改限额先显示新候选再采用，连续版本和原占用保留；不采用不会撤销已有预算。采用本身不授权资金动作。

省略引用仍查已有适用预算；范围/用途不清、重叠、改版或缺账单/结算归属时暂停新办理。
个人`used/remaining`来自准确scope的公开L01，未消费占用和账单尚未反映的已核实消费另列，不能把冻结算消费。
冻结前先持久pending与原操作编号，未知保留；每次新写重新核对，停止仅沿原号核实与限定收尾。
无真实采用时不造月度预算编号或BudgetView。本次生日上限与个人预算分开。
支持原Demo单worker进程内user/round串行，不承诺多进程预算原子性。
开发验证、替身/真实只读接线与未运行的实际E2E分层记录；数量/待执行编辑见下节（business/08）。

## 生日数量与未执行方案调整（v05-cross-business/08）

选品后可直接输入正整数调整刚选商品的数量，选品页与采用页另有“改数量/移除”选项；
采用页逐项展示数量、单价、小计、商品合计、预算上限、送达时间与付款账户。非法量（0、负数、
小数、空篮子）只重问，不冻结、不下单、不付款。

每个计划行有服务端稳定 `item_id`（与 `product_id` 分开）；订单/付款/回查按稳定项，不按商品或
`plan_revision` 重建。同款替代是新执行项、新订单、新付款，历史已付项与操作编号不改写。
下单前重读报价，行小计=最新单价×当前数量；发现新价时先重算并提升计划版本，再重走
下单检查生成新确认（不把新单价直接写进行后沿用旧确认/旧尝试提交），用户按新价重新采用
并确认后才会提交。改后仍需重新采用（冻结前）或重新确认（冻结后），旧确认/验证不能执行
改后参数。已建未付/已付/失败/未知保留原事实，不撤单、不退款、不追加冻结、不换账户、
不自动加预算。受控编辑只提供票面范围的“改数量/移除/替换尚未成单且无在途的项”，
不提供任意“再加一件商品”的购物车入口。

确认/验证卡上的受控编辑由平台 03 发起：`birthday_handoff.py` 实现
`CrossBirthdayHandoff.prepare(trusted, CandidateRequest) -> CrossCandidate`，只读取平台已核验的
精确源检查点并返回新普通 input 交互内容，不自行写预留 namespace；平台 05 一次封存、03 同次任务
CAS 发布。`register_cross` 装配时自动把本实现挂到 `birthday.handoff.cross`（`install_cross_handoff`），
组合无需重复接线；显式 stand-in 不会被覆盖。

原下单被银行明确失败时，只有沿原 operation 读到的 **OperationResult 为终态 failed、带明确银行错误码
且无订单回执**，才记录第二依据并在原普通 input 发布替代选项（新执行项、新确认）；证据不足（无结果、
非终态、有回执或错误码缺失）时降级为原跳过/停止行为，不宣称“已核实无订单”。

已知平台边界：03 撤离原尝试后，参数完全相同的动作再次 check 会被安全门判为已撤离
（`ACTION_RETIRED`），同参新尝试接缝属平台目录（票 09）。接缝未就绪时 Cross **fail-closed 保留任务**：
冻结/订单/核销三种卡都进入可恢复的“稍后再试（保留现状）”等待态，不取消任务、不释放冻结、
不改写已发生订单/付款；用户显式取消仍走原有限收尾。票 09 接缝就绪后由“稍后再试”继续。

## 养老金入账与本人去向（v05-cross-business/07）

养老金前置退订选择页说明项目来自银行签约盘点；减支页另按实际账单比较状态说明来源（v05-cross-business/11）。

父卡的待处理步骤显示“已暂停”，具体原因复用原子任务已公开的脱敏说明。真实未知结果继续沿原子任务和原操作编号查询，办理状态、继续/停止及资金安排占用保持原逻辑（v05-cross-business/12）。

本月入账候选取 L01 明细的真实 `direction=inflow / nature=transfer`，只列当前付款账户。
多笔候选分别展示日期、来源、摘要和金额，用户选定后保留原交易编号，不把所有流入自动认作养老金。
退款、利息、转出不混入；金额文本只作核对线索，不生成流水或改用余额。

去向同时展示 `transfer.list_accounts` 的其他本人账户和 `transfer.list_payees` 的家人联系人。
本人账户使用 `OwnPayee(account_id)`，联系人继续 `SavedPayee(payee_id)`，沿原转账公开入口办理。
不将本人储蓄账户伪造成联系人，不以收款账户余额筛掉零余额账户；原银行执行规则仍有效。
联系人暂时查询失败时，已查到的本人账户仍可选择，并保留重新查询入口。
每笔原确认/验证、安全暂停及未知查询照常；本票没有修改风险事实、策略或参数夹具。
