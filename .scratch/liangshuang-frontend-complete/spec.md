## Problem Statement

现有 React 简易前端已验证普通转账联调，但不是正式前端；现有 HTML 原型缺少收款人候选、等待、模拟人脸、刷新恢复和修改五类关键画面。v0.4 需要先把这些交互走查清楚，再以「通用底盘 + 转账 / 账单插槽」实现正式前端，并替换简易前端且不回退安全与资金闭环。

## Solution

先在现有单文件原型中补齐五类画面，用可点击流程确认交互，不引入后端或新数据格式。Erwin 走查通过后，基于现有 React + Vite + TypeScript 工程实现通用底盘；业务数据先复用冻结公共契约和契约形状 stub，随后分别接转账与账单真实接口。最后切换主入口并回归恢复、防重复、异常与适老化。

## User Stories

1. 作为用户，我能从多个收款人候选中明确选择目标，也能返回修改而不是被系统替我猜。
2. 作为用户，我能在系统处理中看到清楚的等待状态，不会因无反馈重复提交。
3. 作为中风险操作用户，我能在独立验证步骤选择验证码或模拟人脸，并看见验证结果。
4. 作为刷新页面后的用户，我能继续查看原任务和已有记录，不会无意中重新发起转账。
5. 作为转账用户，我能在最终确认前修改收款人、账户或金额，并重新确认完整交易事实。
6. 作为账单用户，我能从同一前端进入账单能力并查看后端返回的明细或报告。
7. 作为银发用户，我能以大字号、高对比、清楚按钮和简单文案完成关键任务。

## Implementation Decisions

- 只修改 `frontend/` 业务目录；不在前端复制公共契约、权限、安全或银行规则。
- 第一票只修改原型并完成浏览器走查，不把静态演示视为真实 API 联调。
- 原型中的人脸为明确标注的模拟交互，不调用摄像头、不采集生物信息。
- 正式前端复用公共契约导出的类型；契约未覆盖的必要字段先记录缺口并提公共变更，不自行创造事实字段。
- 确认卡和验证卡保留在会话历史中并转为只读状态，不物理删除；刷新恢复只查询 / 恢复原任务，不重新提交。
- 结果中的交易状态、交易号、费用、银行、账单数字等事实只展示接口返回；stub 必须明确是演示数据。
- 每张开发票仅对应 `frontend/`，每票一分支一 PR；Ringo 审查确认 / 验证交互，Erwin 做集成验收。

## Testing Decisions

- **P-01 原型完整性**：390×844 手机视口下，从输入到候选、修改、确认、验证码 / 模拟人脸、等待、结果可点击走通；刷新后出现恢复入口且不会自动提交。
- **FE-01 / FE-03 / FE-04**：React 组件测试覆盖转账主路径、中断恢复、旧确认 / 过期 / 重复点击；契约 demo 或真实 API 路径就绪后再记路径通过。
- **FE-02**：账单以契约形状 stub 验证卡片与报告，真实公开能力可调用后再做联调证明。
- **FE-05**：替换主入口后重跑确认、验证、刷新恢复、防重复和真实结果展示。
- **FE-06**：按两份 v0.1 规范在桌面与 390×844 视口走查字号、对比度、按钮触达和横向溢出。
- 局部单测、原型演示和 stub 全绿都不能表述为真实端到端完成。
