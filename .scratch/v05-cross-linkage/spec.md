## 1. Problem Statement：用户面临的问题

用户说的是“安排养老金”“减少不用的扣费”“准备生日”，现有系统主要完成单项账单、转账或退订。用户仍需自己串起这些业务；中途失败后，也缺少一张能核对已办、待办和资金状态的总回执。

## 2. Solution：要交付的体验

保留一个生活目标和一份可调整的方案。AI 根据真实资料选择查询、追问与候选步骤，Harness 承接这些步骤和暂停恢复，确定性业务程序检查约束并办理。每次敏感动作继续使用原业务的确认、验证和执行流程。

三个目标全部在本期。PM 已确认首先贯通 XL-S 减支，然后接通 XL-P 养老金安排；生日的银行与服务前置同步准备，随后贯通 XL-B。这是开发及联调顺序，不是三个新版本，也不缩减生日范围。

## 3. User Stories：用户故事

1. 作为老人，我希望直接说生活目标，让系统确定必要步骤。
2. 作为老人，我希望系统只问影响办理的缺项，不反复索取已给信息。
3. 作为老人，我希望从可读账户、收款人、签约及商品中选择，不记编号。
4. 作为老人，我希望看到方案依据和未知事项，分清建议与已经办理。
5. 作为老人，我希望先只查询，或只选择部分建议，不被迫接受全部动作。
6. 作为养老金用户，我希望按实际入账和我选定的资金范围安排，不把其他余额转走。
7. 作为养老金用户，我希望明确生活费是否包括已知代扣，防止重复预留。
8. 作为养老金用户，我希望每笔转账前重新核对资金，生活费不被擅自降低。
9. 作为查开销的用户，我希望看到实际消费及对照期证据，不把猜测当异常。
10. 作为查开销的用户，我希望自己决定保留哪些服务，系统只取消我选定的真实签约。
11. 作为查开销的用户，我希望知道退订停止的是未来扣费，不误以为已退款。
12. 作为准备生日的用户，我希望在预算和配送要求内比较真实可订的花、蛋糕或其子集。
13. 作为准备生日的用户，我希望价格变化时重新选择，不能沿用旧确认购买新商品。
14. 作为准备生日的用户，我希望明确哪些订单已建、已付，多少资金仍被冻结。
15. 作为准备生日的用户，我希望停止后续购买后，尚未消费且无在途风险的冻结得到释放。
16. 作为用户，我希望采用方案和授权办理分开，每项敏感动作有明确确认。
17. 作为用户，我希望修改待办部分而不丢失已经成功的结果。
18. 作为用户，我希望失败、部分成功和结果未知分别说明，并看到下一步。
19. 作为用户，我希望刷新、断线及重登录后继续原任务，不重复退订、转账或付款。
20. 作为用户，我希望插入查询或切换任务时，确认仍归属正确的业务。
21. 作为用户，我希望账户、验证码、收件原文只在受控位置使用。
22. 作为验收人，我希望从页面、任务、操作及银行事实核对结果，而不是只相信助手说成功。

### 4.2 AI、Harness 与业务的边界

沿用 PRD N1—N10。AI 可选择必要查询、追问顺序、商品组合、分配候选和未执行部分的替代方案。它只能提出候选，不能填写生效的授权、银行结果、预算采用状态或成功标记。

Harness 提供已注册能力的受控调用、可信上下文、父子关联、持久暂停恢复、运行限制与审计。具体留存计算、预算占用和生日资金顺序由确定性业务代码负责；银行余额、限额、账户状态及执行结果仍由模拟银行判定。

采用最小接入：为三目标提供受控子调用，不建设任意任务引擎，不另建 Planner、权限系统或恢复框架。复用现有模块；查到具体公开数据缺口时才向该负责人加票，不预先安排转账、账单和订阅重写。

### 4.3 父子任务与确认（待公共约定确认的方案）

1. 一个联动父任务保留目标、当前计划版本、稳定步骤编号、已执行事实及子任务/操作关联。父任务不能用一个最终状态覆盖所有步骤的实际结果。
2. 一个父任务同一时刻只推进一个需要用户响应或产生副作用的业务步骤。必要的只读查询可按目标变化选择顺序；本期不建设多子任务并行调度。
3. 用户确认仍绑定真实动作所属任务、交互和参数版本。父页面可呈现子任务的原确认卡，但不能重新生成一份“整体批准”代替它。
4. 改方案只改变未执行部分；旧交互不能确认新动作。若旧动作结果未知，先回查，不能在新方案中当作未发生。
5. 父任务的取消和恢复协调子任务；已成功动作保留，未知只查原编号。生日取消后仍可进入限定资金收尾，不能复活购买。
6. 沿用既有任务状态；部分成功由步骤和汇总表达，不随意扩展 TaskStatus。具体父状态映射、可用按钮与等待对象在契约确认时明确。

### 4.4 三条业务主线

**XL-S 减支**：账单事实 → 当前银行签约 → 用户选择 → 逐项调用订阅退订 → 真实结果与清单刷新。关联采用既有商户标识与账户范围，同商户多个协议仍由用户选择；无可靠关联时只显示候选。不以商户名称相似自动解约。一项失败或未知后先说明，是否继续未办项由用户决定。

**XL-P 养老金**：实际入账及资金范围 → 账单/签约事实 → 用户确定留存及去向 → 所选退订 → 刷新资金与依赖 → 逐笔调用转账 → 总回执。金额以分计算；历史消费不从当前余额再减，退订不增加当前资金，未纳入范围的余额不自动转走。按约定计算比例尾差。留生活费不是冻结，也不是保证外部支出后余额不变。

同应用的并发安排须在“读取最新事实—核对本次约束—登记待执行动作”间有一致性保证；单父任务串行本身不足以解决两个父任务同时安排一份钱。相关写入未知时暂停依赖转出。采用最小的受控记录/串行接缝，不创建跨系统资金保底产品。

**XL-B 生日**：真实商品与送达条件 → 采用预算及商品方案 → 有效确认/验证 → 冻结 → 下单 → 订单绑定核销 → 回查在途 → 释放差额。下单、付款分别记录。取消或安全终止停止新购买，按冻结时的限定授权释放可释放部分；未知不能抢先释放。已采用的个人预算跨任务检查范围、版本、已用及未消费占用，不得双算或省略引用绕过。

共同行为及数值判据以 PRD 和 26 条 E2E 设计为准，不在实施票中各抄一套规则。

## 5. Testing Decisions：验收框架

用户已明确验收为 E2E，本规格沿用“真实页面 → 真实模型 → HTTP → 实际业务模块 → 隔离模拟银行/生活服务”，无需重新选择较低层验收。局部测试用于定位缺陷，不能替代该链路。

| 核心路径 | 稳定编号与范围 | 核心判据 | 联调开始条件 |
|---|---|---|---|
| 减支 | XL-S01；分支 XL-S02—S05 | 实际选中签约取消，保留项不变，未来少扣与已退款区分 | 联动子调用、API、总览与原退订卡片真实接通 |
| 养老金 | XL-P01；分支 XL-P02—P06 | 按案例实际退订、转出 2500/1000，1500 留存不造交易 | 前述接缝 + 入账/留存/分配约束真实实现 |
| 生日 | XL-B01；分支 XL-B02—B07 | 冻结 500，消费 467、释放 33；订单付款关联正确 | 银行及资金安全接入、受控配送、生日模块和页面真实接通 |
| 共性 | XL-X01—X08 | 自主调整、旧确认失效、隔离、恢复、限制、隐私与可追溯 | 随各路径就绪先测相关项，最后完整检查三主线 |

验证顺序：单目录外部行为检查 → 可运行主线立即做核心 E2E → 修复失败并复验 → 26 条设计的全部关键变体和自然表达体验走查 → 专业安全审查及 PM 验收分别记录。

复用既有任务 API、真实页面和隔离演示运行器作为验证入口。父子交互需覆盖原 API 的确认、取消、刷新、断线及新会话恢复；银行通过原操作编号与账本核验写入次数。生日还核对订单、冻结未消费额与核销。故障可在隔离银行可控注入，模型不能用固定答案替代；仅离线可测的分支单列，不写成真实 E2E 通过。

每条记录：基线提交、环境/业务时间、种子与故障条件、页面步骤/截图、脱敏模型与 HTTP 记录、父子任务/操作/订单/冻结关联、实际副作用次数、预期与实际、结论及遗留。结果为未运行/通过/失败/阻塞，保留失败批次。缺陷回所属目录修复，联调票只验证和记录。

本轮全为设计，未运行 E2E。#160 检测器装配和真人安全签核保持独立状态；不把它们的未完成自动包装成已接受例外，也不拿既有安全证据覆盖新生日动作。

## 6. Out of Scope：本轮与产品范围之外
