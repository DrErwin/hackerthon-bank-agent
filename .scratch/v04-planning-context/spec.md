# v0.4 规划入口上下文修复规格（v04-planning-context）

Status: in_progress
Owner: Erwin（PM 自拆，不开交付包）
Source issue: [Issue #84](https://github.com/DrErwin/hackerthon-bank-agent/issues/84)（规划入口无对话历史与待办状态）
Deadline: **不晚于 2026-10-15**（为安全线 33+14 轮全量转正复跑留 10-16～10-18 窗口）

## Problem Statement

银发用户在等待确认（确认单已生成、页面正显示待办）或等待验证时随口应答「嗯 / 确认 / 快要多久」，助理的回答却与当前待办脱节——甚至否认业务存在（「没有查到您所指的待确认业务」）。页面事实与模型回答互相矛盾，用户会以为自己刚才的操作丢了。真实复核（GLM-4.7，24 轮）显示 11 轮脱节、2 轮否认业务；零资金动作，属交互理解质量问题而非安全违规。根因在规划入口：`DeepAgentPlanner.select` 只把当前一条消息交给模型，无对话历史（`checkpoint_ns` 每次随机且不挂 checkpointer，属有意设计——规划期原始消息可能含秘密），待确认单/验证状态也不注入。

## Solution

规划入口在理解用户消息时能看到**受控的**上下文：最近对话的结构化摘要与当前待办状态（待确认单要点、验证状态），使等待期应答与待办一致、不否认业务。上下文注入的是结构化摘要而非原始消息，原始消息与秘密仍不落盘、不外泄；确认、验证与资金安全语义分毫不动。固定话术场景可另走确定性短路（可选增强）。

## User Stories

1. 作为等待确认的银发用户，我回复「嗯」，助理应提到我当前待确认的转账（如「您有一笔给妈妈转 500 元的确认单待办理」），而不是答非所问。
2. 作为等待确认的用户，我说「确认」，助理应告诉我确认需在确认单上点「确认办理」按钮，聊天里说确认不算数，且不产生任何资金动作。
3. 作为等待确认的用户，我问「快要多久」，助理应基于当前待办给出状态说明，不否认业务存在。
4. 作为等待验证的用户，我说「应该可以吧」，助理应说明当前处于验证阶段及下一步，不把模糊应答当作验证通过。
5. 作为用户，我说「我刚才已经同意了」，助理应说明仍需在当前确认单上操作（或该确认已过期），不据此执行资金动作。
6. 作为等待确认的用户，我改口「那算了，不转了」，助理按既有取消/结束路径处理——本修复不改变取消语义，只是让回答不与待办矛盾。
7. 作为用户，我在等待期间聊别的（如「今天天气不错」），助理能正常闲聊回复，且不影响待办继续等待。
8. 作为用户，我问「我刚才是要转多少钱来着」，助理能从最近对话摘要中引用关键信息作答，而不是说不知道。
9. 作为同一会话多次往返的用户，我的后续消息能被结合前文理解（如「改成 600」指同一笔待确认转账的修改）。
10. 作为用户，无论我怎么应答，聊天内容都不构成批准——确认必须仍走确认单按钮，验证必须仍走专用通道（既有铁律不变）。
11. 作为安全审查者（Ringo），我要确认注入规划上下文的只有结构化摘要字段，原始对话消息与任何秘密不因此进入长期存储、审计正文或外部出口。
12. 作为安全审查者，我要确认修复没有为模型增加任何资金、授权或越权判断的通道。
13. 作为调试人员，我要能在运行时间线里区分「确定性应答」与「模型应答」（若短路采纳），核对等待期回复来源。
14. 作为评测执行者，我要能用既有安全评测实例（SEC-C-001 各变体、TF-CNF-03[嗯] 共享轮）真跑验证改善，不新增评测基建。

## Implementation Decisions

- **基线（必做；用户 2026-10-10 拍板「交互最起码要带上历史数据」）**：规划入口注入受控上下文——当前待办状态摘要（状态短语 + 该业务的原请求文本，经 `redact(free_text=True)` 打码）。注入的是摘要而非原始模型消息；规划期不持久化原始模型消息的既有原则保持。
- **实现修正（2026-10-11，#95/#96）**：原决定的「稳定会话 `checkpoint_ns`」**不采纳**——规划 backend 是 `StateBackend` 且每次调用新建，稳定 ns 无实际效果；反而在将来误挂持久 checkpointer 时会让原始模型消息落盘，与秘密边界冲突。上下文改由摘要注入单独交付。「最近对话」原始轮次摘要（User Story 8 的完整覆盖）需 api 接缝，见 Further Notes。
- **秘密边界口径（PM 代行记录，2026-10-11；Ringo 可复核）**：注入字段 = 待办状态短语 + 该业务原请求文本（已 redact：电话/账号/地址打码，姓名仅前缀规则命中）；不含原始模型消息、不含验证码/凭据、不含银行账号原文。
- **可选增强：确定性等待应答短路**——等待确认/验证期的固定话术（嗯/确认/催促类）走确定性分支不经模型。采纳判据：基线复验后仍余留问题才做；基线复验全绿则按 YAGNI 不做。
- **秘密边界口径**（哪些结构化字段可进规划上下文）：由 Ringo 定；PM 代行时如实记录代行（执行记录见上）。
- 修复不改变确认、验证、权限与资金安全语义；聊天文字仍不构成批准；不新增模型可调用的资金/授权工具。
- 单一实施目录：`backend/app/agent_platform/`；涉及 `memory/`（摘要存储）、`modules/transfer/`（待办摘要来源）、`contracts/`/`api/`（仅当公开行为变化）的接缝改动另开票，不混入基线票。
- 短路若改变对外回复形态，先判断是否触及公共契约/API 契约，触及先走契约变更流程。

## Testing Decisions

- 只测外部行为：从 harness 入口断言「回复与当前待办一致、不否认业务、零资金副作用、秘密不落盘」，不断言内部提示词拼装细节。
- **离线缝（既有）**：`agent_platform` 现有 scripted planner 工厂驱动的 pytest 模式——在 harness 层构造等待确认/等待验证状态后注入各类应答，断言回复口径与安全底线。
- **真跑缝（既有）**：安全线已建好的 `run_instance` / `run_shared_round` 入口——SEC-C-001 v01—v06 实例与 TF-CNF-03[嗯] 共享轮，按[用例正文 4.4 节](../../evals/security/安全评测集-v0.1-2026-10-07.md)解释口径人工复核。
- 不新建评测基建；两缝均为既有缝。

## Out of Scope

- 不改确认、验证、取消、资金执行的任何安全语义。
- 不做 #85（确认/验证历史只读回放接口）——另一工作组。
- 不做通用长期记忆或跨会话记忆扩展。
- 不持久化规划期原始模型消息（transient 原则不变）。
- 不动前端页面。
- 不做安全线全量转正复跑（33+14 轮）——修复复验后移交 [v04-security/01](../v04-security/packages/01-detector-and-coverage.md)。
- 不新增安全评测用例（evals/security 归 Ringo）。
