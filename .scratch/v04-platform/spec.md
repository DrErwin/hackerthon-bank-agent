## 1. 目的

v0.4 要在 v0.3 已验证的纵向框架上跑**转账 + 账单双场景**：账单模块、前端账单插槽与安全线都必须通过同一套底座能力接入，不另建运行体系。

v0.4 启动时只登记了账单、安全、前端与联合验收四个交付包，**底座 / Agent / 模拟银行这条线没有交付包**。后果已经出现：契约 §6.7 早就写好的**报告与文件交付（F21—F24）**属于「契约里已定义、还没有实现」的能力，既不算契约缺口（不进 Issue），也没有对应交付包（不进票），于是掉在账单线与底座之间的缝里（2026-10-13 Erwin 指出并拍板补包）。

本规格界定这条线在 v0.4 的交付范围与验收；业务规则以冻结 PRD 与公共契约为唯一事实源，不在此复制或改写。

## 3. 本里程碑要证明什么

1. **第二个业务模块（账单）能按既有注册点接入平台**：能力注册、意图路由、任务视图、事件与 `module` 标识都对，不复制转账运行体系。
2. **报告与文件交付链路（F21—F24）可用**：报告只读、卡片导出为普通操作、明细导出必须再次验证、下载路径受控。
3. **银行接缝与共用种子支撑账单取数**：取数完整 / 失败 / 数据不足三态分开，不编造数字。
4. **契约变更由底座受理并落地**：各线不复制契约、不越目录改公共定义，公共改动流程留痕。

## 4. 核心验收场景

| 编号 | 场景 | 通过条件 |
|---|---|---|
| P01 | 账单任务在平台上创建、等待、恢复 | 任务视图带 `module=bills`；状态与交互符合契约 §6.5；转账链路不受影响 |
| P02 | 前端按 `module` 选插槽，双场景互不串台 | 转账任务仍为 `module=transfer`；账单任务载荷为账单模块结果 |
| P03 | 报告读取（F21） | 本人范围校验；只返回受控报告卡片内容，不含原始全量明细 |
| P04 | 卡片导出与明细导出（F22 / F23 / F24） | 卡片导出无需再验证；明细导出必须再次完成本次所需验证，成功 / 失败 / 过期 / 越权分别给出结果；下载路径为应用内受控路径 |
| P05 | 账单取数与失败口径 | 接缝三态（完整 / 查询失败 / 数据不足）分开返回、不吞并不编造；「统计完整」的宣称与结论口径由账单线 BF03/BF06 验收 |
| P06 | 契约受理与联调 | 各线缺口经公共改动流程登记，由底座实现或明确拒绝，不留无归属项 |

### 测试覆盖框架

覆盖类别（底座侧）：正常完成（P01—P04）；权限与越权拒绝（P03/P04：本人范围校验、越权拒绝）；验证分支（P04：成功 / 失败 / 过期）；中断与恢复（P01：等待 / 恢复，敏感导出暂停恢复沿同一平台任务）；事件与模块标识（P02：`module` 填写与载荷）；取数失败三态（P05）。

不适用或归属他线的类别：缺信息后补齐与口径纠正是账单模块行为（v04-bills BF05，周恩宇）；动钱确认不适用——本线无资金动作（报告与导出为只读 + 文件交付）；账单结论正确性（数字、分类、异常判断）由账单线验收，底座只验管道与三态透传。

具体用例与证据：底座侧 E2E 落 `backend/` 测试（真实运行时 + 模拟银行 + 安全门既有路径）；跨线联调证据按 P06 进联合验收（v04-bills/02）。
