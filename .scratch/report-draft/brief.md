## 一、PM 的核心判断（必须成为报告主线，用他的意思写，不要改成别的论点）

1. **为什么选 LangChain 生态**：银行业务步骤多、安全检查严。所以框架选 LangChain 生态（Deep Agents 做 Agent 底座 + LangGraph 编排业务流程），因为它便于把一步步的业务编排成流程：有状态、分支、暂停等用户确认、中断后从原位置继续。
2. **核心权衡**：银行一步一步的严格程序 vs Agent 智慧带来的自由度。我们的答案：**让 Agent 发挥自由度，做出更灵活的安排；由程序兜住安全风险。**
   - Agent 自由的地方：听懂口语、追问缺的信息、把一句话拆成多步计划、跨场景组合（生日：留专款+订花+订蛋糕+付款+退回余额；养老金：一笔到账分成留存/储蓄/家人+顺手退订）、用白话解释结果。
   - 程序兜底的地方：模型只能从白名单能力里选、参数由程序校验、动钱必须暂停 → 本人在确认单上确认 → 验证码/刷脸 → 沿原任务继续；银行规则（余额、限额、风控、去重）只在模拟银行；结果只认银行返回；工具返回和外部文字按"不可信数据"处理，不能变成指令。
   - 三条铁律：LLM 只动嘴不动手；动钱必过确认门；银行规则只在模拟银行。
3. **交互：聊天为主，卡片为辅**。
   - 主入口是和 Agent 聊天——为老年人设计，说话最自然。
   - 同时提供常规快捷操作：卡片上可以直接修改、确认、取消，也能查看已有的信息和办理步骤（计划卡、进度、回执、恢复卡）。
   - 把聊天的自由度和固定程序的操作便捷结合起来。例证：聊天说"金额改成600元"同一任务出新确认单（T05）；验证码只能填卡片专用框，发进聊天会被拦（X02）；配送信息走专用表单（G02）；计划卡看步骤（R01b、G05c）；中断后恢复卡"继续办理"（X03）。

### 1.4 按代码核实后的口径修正（15:05 补，以此为准）

上面第 2 条的"Agent 自由的地方"写宽了。代码事实：
- 全系统只有一个模型入口 `agent_platform/model.py` 的 `DeepAgentPlanner.select`（`create_deep_agent`），只给模型三个"提议"工具：`propose_transfer`（从白名单选一个能力并提取转账线索）、`propose_continuation`（对已有任务补充/修改/继续/查询/取消）、`reply_only`（白话回复、超范围说明）。本轮只调一个工具一次。
- 生日/养老金/减支：模型只提议 `cross.start_task`（提示词要求"不因其中涉及退订或转账就缩成单项"）；场景识别是 `cross/entry.py` 的 `infer_scenario`（关键词，歧义就澄清不猜）；预算和日期由 `cross/birthday.py` 从用户原话读出；步骤由 `cross/plan.py` 的确定性代码排（"deterministic code owns every transition"）。追问话术也是程序写的。
- 只有转账是完整 LangGraph `StateGraph + interrupt + Command(resume)`；账单/订阅/联动是确定性状态推进，状态存在同一套 LangGraph 检查点（`storage/checkpoints.py`），同样可暂停、可从原位置继续。
- 生日真实顺序：选花和蛋糕 → 采用方案 → 留专款 500（门）→ 花下单（门）→ 花付款（门）→ 蛋糕下单（门）→ 蛋糕付款（门）→ 自动退回 33（不再确认，退回不在模型工具表里，`security/birthday_release.py`）。5 个门 = 5 轮。

所以报告里的正确说法：
- Agent 的自由在"理解与对话"：听懂口语和改口、从白名单里选对能力、提取转账线索、听懂补充/改口/继续/取消、把整件生活目标交给联动模块而不缩成单项、用白话回复和解释、超范围如实说明。
- 程序的严格在"步骤与执行"：排步骤、追问、校验参数、确认门、验证、银行规则、结果核对、退回余额。
- 不要写"Agent 自己把一句话拆成多步计划"或"Agent 自主组合跨场景步骤"。写成"Agent 听懂目标 → 程序排出可核对的步骤 → 每笔钱过门"。
- 框架表述：Deep Agents 做理解与提议；LangGraph 提供状态、暂停、检查点与恢复（转账用完整图，其余模块把状态存进同一套检查点）。
