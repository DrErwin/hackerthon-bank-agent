03

模板体系：发出去的是模板，收回来的是事实

对齐信息不靠开会反复讲，靠「结构化模板 + 明确的填写去处」

队友水平不一（有非技术成员），与其让他们自由发挥再返工，不如把「要交什么」直接做成表格和清单：每一行都注明「去哪抄」，交回来的东西才能直接拼进系统。

📋PRD 收件清单（7 项）

发一份清单给每个场景负责人：用户目标与范围、正常流程、输入输出与能力、异常与取消、安全与确认、流程图、验收例子与待确认问题。按清单收齐 5 份 PRD：转账（梁爽）、账单（六水）、跨场景（周恩宇）、Mock Bank（我）、安全底座父级（Ringo）。

收齐 → 预审会 → 回填 → 冻结

🧾安全回填表（15 行模板）

安全底座父级 PRD 定「怎么填」，回填表收「填回来的事实」。拆成会前 5 行 / 会后 10 行，每行注明去哪抄，附一份填好的样例。三张业务表叠起来，还能看出单个模块看不到的跨模块结论。

父级定规则回填表给事实

🎙️会议双稿：逐字稿 + 纪要

每场会留两份：逐字稿是语音转写原文（保留口语和错字，不改写，当档案）；纪要是整理版（结论、待拍决策、行动清单）。口说无凭，回头翻的是纪要；纪要有争议，翻逐字稿。

原始记录结论与行动项

⚖️决策清单（勾选框收口）

开放问题集中在索引文档里用 checkbox 管理；Mock Bank 的 16 项决策（D01–D16）编号列出、逐条拍板、拍完回填 PRD 并标记清零。谁拍的、哪天拍的、依据是什么，全程可查。

16/16 决策清零拍完回填正文
「同一份需求只有一个本体：冲突时一律以 PRD 正文为准。」模板、填写教材、过程稿用完归档进 _archive/，不跟事实文档混放。
04

开发流水线：一条需求从想法到合入

AI 技能链跑量大但不需判断的活，人只在关键处拍板
1

迷雾先探路 /wayfinder

路径不清的地方（安全层设计、Agent 编排内部）先走 wayfinder 产出决策而非交付物；业务流程 PRD 已写清楚的部分直接过，不浪费在已经清楚的地方。

2

契约先行：讨论 → 你定 → 冻结 → 实现

契约只有一个 owner，多人一起定会协商成一锅粥。契约不是 markdown 文档，是 backend/app/contracts/ 下的 Pydantic 代码——成员 import 模型去写，字段错、类型不对，编译期直接报错。不读代码也知道他没跑偏。

契约 = 编译产物守住接缝 · 容忍深度
3

定版本：写清做什么、不做什么

每个里程碑在 docs/versions/vX.Y.Z/ 建 requirements.md（目标 / 范围 / 验收 / 明确不做的）+ completion.md（如实记：未开始 / 进行中 / 已完成）。当前 v0.3 = 跑通普通转账纵向链路。

v0.1 PRD 基线 ✔v0.2 架构契约 ✔v0.3 进行中v0.4 业务扩展v0.5 验收打磨v1.0 交付
4

两级拆票 /to-spec → /to-tickets

场景负责人先写 spec.md 和交付包（定业务结果、开始条件、验收标准，不替别人定内部实现）；各目录负责人接受交付包后，为自己的目录拆实施票——一张票只改一个目录。spec 和 ticket 必须在同一上下文产出，implement 之间清上下文。

5

正式激活 + 并行实现 /implement

在「01-项目跟踪」和飞书进度表登记负责人与时间，负责人明确接受才开工（文件躺在 .scratch/ 里不算数）。每人一票一分支一 PR；被依赖阻塞时先做 stub、评测或审查准备，不停工等人的代码。

接口没好？按冻结契约写 stub真 API 出来再切联调
6

收口：验收要有证据 /code-review

AI 做第一遍 Review，人看清单（目录越界？引用契约还是复制？测试与声明一致？）；按依赖顺序合入（契约 → 底座 → 安全 → 业务 → 联动 → 前端），squash merge 一 PR 一条记录。阶段结束先更新 completion.md 记录证据，再激活下一版本。

规则 1
每个人拆自己的票，不等待别人先拆完。负责人接受交付包后即可开工，不用等我写完后端。
规则 2
被阻塞不停工：先做 stub、评测集或审查准备，当天在甘特图标记阻塞原因。
规则 3
临时顶班要写明期限：一个人可以按顺序承担多个目录，但票、分支、PR 仍按单一目录拆，阶段收口后回到长期负责人。
规则 4
任务文件不会通知任何人。正式启动 = 项目跟踪里登记 + 负责人知晓并接受，两者缺一不开工。
06

质量机制：不靠事后审查，靠四层防线

你不可能逐行读完三个人的代码——把「坏代码的破坏半径」在发生之前框死
01

编译不过的契约

契约是 Pydantic 模型，不是文档。类型与运行时校验是最不知疲倦的 reviewer。

02

小接口封死半径

成员拥有接口背后的深度。模块内部丑一点没关系，最坏重写一个函数，坏不进系统。

03

测试当验收

每个 ticket 的「完成」是客观信号：一条测试名、一条命令的输出。先写测试骨架，他们让测试变绿。

04

CI 当第二 reviewer

mypy + ruff + pytest，不过不给合。AI 替我跑 CI、拉 PR 做第一遍 review。

闸 1 · PR 模板清单提交前自答：对照规格做完了吗？测试跑了吗？
→
闸 2 · CI 全绿类型 + 规范 + 测试，机器说了算
→
闸 3 · 合并权一把手main 只有 PM 能合，按依赖顺序收口
「测试红着就是没做完，不能吹。」完成情况要有证据：不把文档、占位接口或单模块测试当作端到端完成。
07

飞书发布：三层白名单，只出不回

两种信息两条路——动态的「现在干什么」常更新，冻结的「长期依据」基本不动
LAYER 1 · 动态层

当前工作台 + 当前版本

《01 项目跟踪》：按工作线 / 按人员看交付、接力信号、协作规则；v0.3 的实施计划、需求、完成情况。

每天/每周更新
LAYER 2 · 总览层

Roadmap + 版本总览

六阶段并行规划、硬依赖与检查点；v0.1～v1.0 每个版本的需求与完成状态汇总。

阶段性更新
LAYER 3 · 冻结层

PRD · 架构 · 契约 · 规则

已冻结且跨阶段复用的五份 PRD、系统架构、主契约与字段附件、协作规则。冻结后基本不动，改动走契约变更流程。

🔒 冻结只读
🚫 不进飞书的

模板、会议逐字稿、研究过程、收口过程记录——这些只留仓库；退出白名单的旧文档移入 Drive 归档，不直接删除。

🔧 几个工程细节

全程用户身份建文档（应用身份建的成员改不了）；发布覆盖正文会移除内嵌甘特图，重跑 embed_stages.py 恢复；新增文档先确认属于哪一层，再进白名单。

$ python tools/feishu_sync.py publish # 推内容：缺失的新建、已存在的原地覆盖
