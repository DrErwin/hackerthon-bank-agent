# 银行助手：前端交互审查与手机优先方案

日期：2026-10-26。当前源码基线 `9a479ea`；产品文件保持原状。本次交付是设计评审与独立原型。

**判断：现在已有不少功能，但组织方式仍像一份不断增长的办理记录。老人需要自己在记录中找资料、找入口、理解系统状态。优先要改的是信息位置、办理顺序和语言。**

用户确认：**手机为主，电脑适配**。

## 1. 看了哪些范围

| 范围 | 核对内容 | 本轮证据 |
|---|---|---|
| 主入口与连续办理 | 首页入口、聊天、当前任务、历史、断线和重进 | 当前源码、隔离页面实际点选 |
| 转账 | 已有收款人、搜索、新收款资料、付款卡、金额、修改、确认、验证码、回执 | 当前源码、隔离页面实际点选 |
| 账单 | 时间/账户范围、分类、单笔、陌生扣款、长明细 | 当前组件、原始业务 PRD |
| 自动扣费 | 正在扣费、待核对线索、停扣、验证、结果 | 当前组件、业务固定文案、PRD |
| 生活安排 | 减支、养老金、生日、整体步骤与逐项办理 | 当前联动总览、票据、PRD；生日专用页面仍有待交付部分 |
| 通用状态 | 等待、失败、核实中、恢复、历史确认、额外验证 | 当前组件状态目录实际浏览 |
| Agent 用词 | 模型提示词、固定回复、前端提示来源 | 源码核对；本轮未运行真实模型对话 |

审查由两个相互独立的视角完成：业务体验（`ux_review`）、界面与能力证据（`ui_evidence`），主代理补页面走查并综合。当前页面使用最新源码的隔离副本、契约演示数据。演示数据不能代替真实接口和模型的完整验收。

`/legacy` 是旧界面对照入口；`/admin`、`/v04/admin` 是管理/演示端；本轮优化对象是银发用户使用的正式主界面，不把管理端操作放进用户办理流程。

## 2. 已有的能力，值得保留

- 账户与收款人查询、点选、搜索、手填本次收款资料、修改金额都已存在。
- 账单/订阅可以原地展开，长明细有抽屉。
- 原任务恢复、专用确认、验证码、等待、待核实与回执已有基础。
- 已有大字号基础、较大的操作区域、键盘焦点样式和减少动态效果。

因此不能再把问题概括为“系统完全没有收款人列表”。真正的问题是**列表出现的时机、能否随手找到，以及是否能直接带回当前办理**。

## 3. 优先问题与优化方式

| 优先 | 当前问题 | 对老人有什么影响 | 本版方案 |
|---|---|---|---|
| 第一批 | 常用入口在第一条聊天消息里，随着对话滚走 | 办到一半想查资料，要往回翻或重新问 | 手机底部常驻首页、办业务、我的资料、办理记录 |
| 第一批 | 收款人和付款卡仅在对应字段的编辑状态出现；引导默认金额→账户→收款人 | 需要先记住资料，再到另一个位置填写 | 先选收款人；填金额时保持收款人摘要、所选付款卡和余额同屏；换卡打开就近选择层 |
| 第一批 | 新收款人入口受当前追问状态限制 | 到最后核对时想换新人，入口可能消失 | 收款人页顶部稳定提供“新增”；每个可修改阶段均能回到它 |
| 第一批 | 许多固定提示重复讲“没做、不会做、只读、原操作” | 看不清现在该点什么，还增加不安 | 每次只说当前情况与下一步；保留与当前决定直接相关的事实 |
| 第二批 | 外层任务状态、内层标题、提示、历史说明反复出现 | 当前重点被挤出屏幕 | 一个页面突出一个决定；历史放办理记录；一个主按钮推进 |
| 第二批 | 联动部分选择仍使用通用文本输入，金额例子混入其他问题 | 日期、地址、金额、选择项看起来一样 | 日期用日历、金额用数字框、账户/商品/扣费用选择卡，配送用专用表单 |
| 第二批 | 回执按数组位置显示前三项 | 重要事实未按不同业务安排 | 每种业务明确必须直接展示的信息；长编号与补充说明放抽屉 |

## 4. 手机上的信息怎么摆

**首页：先看到能办的事，再看到自己的资料。** 四张大卡片：转账、查账单、自动扣费、生活安排。下方展示常用卡余额、常用收款人与未完成事项。

**转账：选人 → 填金额 → 核对 → 验证 → 回执。** 已有资料不重复询问；在金额页看见收款人、付款卡和可用余额。换卡在当前页面打开选择层，金额保持原样。手填收款人使用独立表单，核对后回到这笔办理。

**账单：月份和账户先讲清，分类与单笔可以直接点。** 一般明细原地展开，完整列表用抽屉；关闭后回到当前记录。陌生扣款直接提供核对入口。

**自动扣费：每一项先解释“扣什么、多少钱、哪天、哪张卡”。** 一项一个主动作；退订后结果保留在原卡。仅有相似扣款线索的项目保留“核对”动作，与可执行的银行签约区别清楚。

**生活安排：先看全程，再突出现在的一步。** 养老金先核实本次安排范围和生活费；减支先选用户不用的项目；生日先定日期/预算、选商品、填配送、核对预算及逐项付款。每笔敏感动作仍需本人的明确核对。

**手机主按钮固定在底部，关键资料在它上方。** 帮助就近打开；电脑使用同一内容并展开侧栏。

## 5. 用词改成普通人会说的话

| 现在的写法 | 本版表达 |
|---|---|
| 已恢复原任务，没有创建新任务，也没有重新提交。 | 已找回上次的内容，可以接着办。 |
| 请逐项核对。在聊天里说“确认”不算数，必须点下面的按钮。 | 请核对收款人和金额，确认后继续。 |
| 查询不会再办一次。 | 查看这笔转账的进度。 |
| 正在办理，请不要重复操作。 | 银行正在处理，结果会显示在这里。 |
| 已经停下了，没有提交退订，银行那边没有变化。 | 已取消这次办理。 |
| 资料已更新。请核对当前内容，确认前不会转账。 | 资料改好了，请再核对一下。 |
| 请自己点选，系统不会替您默认选择。 | 请选择一位收款人。 |
| 普通对话回复已记录；没有发起业务操作。 | 明白了，您可以继续问我。 |

写作规则：优先一句话；先说具体对象与状态；按钮直接写动作；详细解释按需展开。**正向提示不代表掩盖失败或退款范围。** 结果未知仍写核实中；停扣确认中用一个清楚的字段说明退款范围；具体风险出现时说明原因和可执行的核实方法。

话术来源有三处：前端固定文案、业务/平台固定回复、模型生成。模型提示词已经要求简短日常用语；单独再加一条“请简洁”不能解决所有问题。

## 6. 原型里哪些是新增建议

| 能力 | 当前事实 | 原型表达 |
|---|---|---|
| 查询、点选常用收款人和账户 | 已有基础 | 改入口位置与办理顺序 |
| 填写本次新收款人 | 已有受控输入，受任务状态限制 | 稳定入口＋核对结果＋回填草稿 |
| 保存常用收款人、备注 | 当前接口没有对应保存字段 | 明确作为拟新增能力；原型只保存在本页内存 |
| 卡片外直接发起“转给TA” | 当前独立列表主要回填已有转账 | 直接进入新的转账草稿 |
| 月份快捷切换 | 当前已有月份输入 | 更方便点选 |
| 生日专用交互 | 初评后主线 #314 已接商品/数量、配送专用输入、受控修改和结构化收尾，视觉与适老化仍待验收 | 展示拟议的完整信息组织；不得据此标记产品已交付 |
| 语音输入、朗读 | 真实能力未接入 | 这版先以点选和打字完成，不放假录音按钮 |

原型余额、银行卡、交易、验证码都是固定示例。业务权限、银行规则、确认有效性、到账与停扣结果，在正式产品中仍由服务端与银行返回决定。原型里的本地规则只服务于界面体验。

## 7. 建议实施顺序

1. **先把转账做顺**：常驻资料入口、稳定的新收款人入口、金额/余额同屏、修改后重新核对、完整回执。
2. **统一所有业务的说话方式**：清理前端、平台、转账/订阅/联动固定回复，并做真实模型对话走查。
3. **把卡片选择铺到其他业务**：账单月份/账户、扣费项目、联动日期/金额/商品/配送，保持整体目标可见。
4. **用手机和老人验证**：找人、找卡、换人、改金额、查扣费、失败恢复；检查软键盘、系统大字、200%缩放、读屏和持续办理。

用户随后授权更新设计系统并接入组件库。已在隔离工作区，以最新主线 `00543b4` 为基线领取 `frontend-design-system/01`，交付设计系统、基础组件和首批页面接入。全业务重新编排仍以本原型作为评审依据；后端固定回复与接口缺口按目录分别推进。

## 8. 初评与证据限制

这是设计启发式初评，不是用户实验得分。

| 维度 | 分数（4分制） | 判断 |
|---|---:|---|
| 状态可见 | 3 | 状态齐全，重复且偏系统化 |
| 日常语言 | 2 | 防御性说明、内部术语偏多 |
| 用户可控 | 3 | 修改/取消已有，入口不总稳定 |
| 一致性 | 2 | 通用输入与专用引导混用 |
| 防错 | 3 | 明确确认/验证已有基础 |
| 看见再选 | 2 | 候选存在但不够就近 |
| 操作效率 | 2 | 找入口和找资料成本高 |
| 简洁 | 2 | 信息层级与重复说明需重排 |
| 错误恢复 | 3 | 能力已有，用词需改善 |
| 帮助 | 2 | 更需要贴近当前步骤的提示 |
| 合计 | **24/40** | 主要改进空间在认知负担 |

当前源码的机械检测命中一处装饰边框；它不是本轮最重要的用户障碍。原型检测退化为正则扫描，输出零条，不构成完整无障碍证明。原型另做浏览器点击与窄屏/桌面布局检查，具体记录见 `verification.md`。

未完成的产品验收：真实Agent/接口全流程、实体手机与软键盘、实际200%缩放、完整读屏、老人使用测试。下一轮应以这些证据判断设计是否真正好用。
