### 1.2 缺口（本票要补的 UI）

1. `module === "cross"` 目前解析到 `genericSlot`，父任务卡**只显示状态标签 + 一句话**，看不到「一共几步、哪步办完了、下一步是什么」。
2. 联动父子关系来自服务端（`GET /api/v1/tasks/{task_id}/children`），现有前端只有账单/订阅的**本地 cardLinks**（存在 localStorage，仅限账单动作），不适用于联动父子。
3. 契约导出的 TS 类型里还没有 `CrossTaskView / CrossStep / BudgetView / ArrangementView`（`frontend/src/api.generated.ts` 未包含）。生成脚本在 `frontend/scripts/generate_contract_schema.py`，**属前端目录，可自行补导出**，不改后端。

### 1.3 盘点补充（只读盘点报告：[research/frontend-inventory.md](research/frontend-inventory.md)）

- 前端目前**没有任何联动占位**：`cross` 只作为枚举字符串存在于生成类型，`birthday/budget/expense/pension` 零命中，`slots.resolve("cross")` 回退 `genericSlot`。
- 现有父子雏形（`CardLink` + `cardAction` + `renderChild` + `buildTimeline`）是**前端本地卡片关系**（存 localStorage），不是服务端父子任务；联动必须走服务端 `/children`，不能复用本地关系冒充。
- `GET /api/v1/tasks/{id}/children` 的 `data` **直接就是 `TaskView[]`**（不是分页对象），实现 `listChildren` 时按数组取。
- 插槽 `BusinessSlot` 只能产 `DisplayField`，**放不下自定义版式**；总览卡必须做成 `TaskBlock` 的 `card` 钩子或 `module === "cross"` 分支。
- `shell/stub/demoBackend.ts` 目前**没有 `cardAction`**，契约演示模式下联动卡动作需要补 stub 才能演示。
- 全站样式**全 px、无 rem**，也没有 200% 缩放专项；200% 缩放需实测（浏览器页面缩放会整体放大，但固定 `position: fixed` 外壳 + 顶栏/输入栏固定高度在大字号下要现场验证，见 §5）。

### 1.4 服务端真实能给的数据（2026-10-25 读码核对，非票据转述）

| 父子任务状态 | `data` 实际内容 | 来源 |
|---|---|---|
| 父任务 running（某一步正在办） | `CrossTaskView`：`steps[]`、`summary`、`plan_revision`、`active_step_id`、`interaction_task_id` | `backend/app/modules/cross/entry.py:158-169` |
| 父任务终态（succeeded/failed/cancelled/partially_succeeded） | `CrossTaskView`（步骤 + 汇总话术） | `entry.py:135-142` |
| 父任务 waiting_input（服务端菜单：采用方案、选退订项、选去向、补金额…） | **多数为 `null`**；只有「选择要退订的签约」这一处附带了 `CrossTaskView` | `entry.py:118-133`、`entry.py:590-591` |
| 子任务（真正的业务动作） | 各业务自己的视图（转账/退订/账单），带自己的 `allowed_actions` | `entry.py:804-834`（`GET /tasks/{id}/children`） |

由此得到两个必须记录的事实（影响本方案与验收，不美化）：

- **G1：菜单状态下父任务没有结构化视图。** 采用方案、选留存/去向、输入金额这些关键时刻，服务端只给一句话 + 选项（`data=null`）。前端要展示「已经办到第几步」只能靠上一次快照缓存；刷新后拿不到 → 与「刷新不丢目标」的验收项冲突。
- **G3：养老金金额依据没有结构化字段。** `ArrangementView` 已实现（`backend/app/modules/cross/pension.py:118-138`），但父任务视图里 `arrangement` 恒为 `None`（`plan.py:169`），入账/留存/可安排/代扣只在提示文字里。

两处都可以用**很小的后端改动**补齐（在菜单返回时把已有的 `plan.build_view(...)` / `pension.view()` 一并塞进 `data`，字段不新增、不改契约），但属 `backend/app/modules/cross/` 目录，**需 PM 裁定后另开一张后端票**，不能在本前端票里跨目录改。

### 3.5 断线 / 刷新 / 重登录后

- 刷新：先按服务端快照恢复父任务；父任务 `recovery_required` 时沿用现有「恢复原任务 / 放弃」卡，**不自动继续**。
- 父任务运行中：前端按 `GET /tasks/{id}/children` 取回真实子任务再渲染，不用本地缓存冒充。
- 旧确认卡：服务端不再给 `confirm/verify` 时按钮置灰并写「这次确认已经失效，请以最新内容重新办理」，点不动。
- 会话失效：沿用现有「演示登录已过期」横幅，旧按钮不可点。

## 4. 交互规则（红线）

1. **采用方案 ≠ 批准办理**：采用是父任务的一次「选择」，不产生写操作；每笔业务仍走原子任务自己的确认/验证。
2. **只对当前有效交互提交**：提交目标 = `interaction_task_id` 指向的子任务；父任务的 `allowed_actions` 里没有 `confirm/verify` 时，父卡不出现确认按钮。
3. **旧确认不可用**：计划版本变化（`plan_revision` 变大）或子任务 `allowed_actions` 不含 `confirm/verify` 时，旧卡只读。
4. **重复点击**：沿用现有 busy + 幂等 `request_id`；父卡不新增重试通道。
5. **插入查询不覆盖原任务**：聊天里插入的只读查询是新任务；原联动任务保留在时间线原位（现有 `buildTimeline` 行为）。
6. **前端不推算**：不自行判断能不能办、预算够不够、银行余额；不把「预计节省」当已实现。
7. **隐私**：配送原文、验证码、完整账号不进入父卡、聊天与普通日志；配送走受控入口引用（票 02）。

## 5. 适老化与无障碍（本票页面必须留证）

## 10. 服务端阻塞（2026-10-25 **代码核对**结论，尚未实机复跑）

### 2026-10-25 实现后复审（AI，非真人）
