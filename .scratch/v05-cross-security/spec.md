## 1. Problem Statement 与 Solution

跨场景任务要同时管多个业务，不能把“同意总方案”当成随意扣款的许可。生日购买还需在取消或安全终止后释放未消费冻结，既不能继续买，也不能因为普通任务被终止就丢下资金不管。

本包先在现有安全执行器中落实生日动作及限定收尾的权限、确认和授权，再对装配完成后的真实路径做专项验证。AI 只提出计划和解释；授权判定、确认版本和资金执行依据由确定性程序与可信记录提供。

依据：[现行 PRD](../../docs/prd/06-跨场景联动-PRD-2026-09-23.md)、[公共契约 §3.5、§4](../../docs/contracts/公共契约-2026-09-23.md)、[安全与审计附件](../../docs/contracts/安全与审计字段-2026-09-24.md)、[安全底座原则](../../docs/principles/02-security-platform.md)和[共享规格](../v05-cross-linkage/spec.md)。旧提案只辅助定位差异，不能覆盖已生效契约。

## 2. User Stories

1. 用户确认某个动作时，只授权眼前的账户、对象、金额和版本，方案采用不替代动作确认。
2. 用户修改金额、商品或账户后，旧确认和旧验证不能批准新动作。
3. 用户拒绝或取消后不会发生新购买；已付款的结果仍真实保留。
4. 用户在冻结时能看清限定释放条款；任务结束后，系统仅释放原冻结未消费余额回原账户。
5. 用户付款结果未知时先核实原操作，不重复扣款，也不提前释放在途资金。
6. 用户登录失效或发生安全终止后，普通购买不能复活；受控身份仍可按原授权核对并完成允许的收尾。
7. 不同用户、任务、账户或演示轮次不能借用他人的确认、冻结和配送引用。
8. 配送资料、验证码和完整账号只在获准入口使用，不进入模型、普通日志或普通任务响应。
9. 规则、授权或必要审计不可核实时停止新写入，并说明待处理事项。
10. 验收者能把页面操作、父子任务、确认、执行判定和银行变化对应起来，区分真实通过、失败、未运行和阻塞。

## 4. Implementation Decisions：已有规则直接采用

| 动作 / 状态 | 固定规则 | 安全侧提供的结果 |
|---|---|---|
| 查询商品、原订单/冻结/操作 | 核对用户、任务、轮次和资源归属；只读不是免权限 | 允许读取或明确拒绝，不取得购买权 |
| 冻结、下单、按订单核销 | 每项经声明、参数绑定确认、适用验证、提交前授权和必要审计；父任务批准不替代子动作 | 可信等待/允许/拒绝与可追溯授权；银行仍判断实际业务结果 |
| 冻结确认及后续绑定 | 首次冻结确认包含限定释放条款；确认作答后保存受控授权，冻结成功再绑定 freeze_id；未知查原编号 | pending_freeze/active/completed/invalid 等记录语义按安全附件；模型不能填写生效状态 |
| 完成、取消或安全终止后的收尾 | 停新购买，核实在途，查询银行未消费余额；余额为零不提交释放 | 限定查询与释放，原授权不变成一般购买许可；不额外等待一次释放确认 |
| 会话失效、终止任务 | 普通 resume 不复活业务；收尾使用受控身份并核验原用户/任务/账户/轮次 | 仅允许原授权范围内收尾，不能把旧会话或历史验证当作通用授权 |
| 未知、日志失败、授权缺失 | 原操作回查；缺必要事实时暂停；释放未知不换号重做 | 无新银行写入或保留待核实，不把失败/未知写为已完成 |
| D1/D2 | 同账户活动安排、版本与父子关联要核对；部分完成事实不被取消覆盖 | 不放宽原业务约束；父状态与预算计算由业务负责，安全不复制它们 |

规则确认方式：D1/D2、逐项确认和限定释放已由契约确定，直接沿用。执行者将“本次如何落实、差异和兼容影响”交 Erwin 作本阶段本人安全审阅；若有必须改变规则或新增公共约定的地方，列出具体方案与影响后确认，不把接包或 AI 检查冒充已批准。

## 5. 实际接缝核对与风险点

源码/文档核对基线：`cd0e3c4`；本次只读检查，没有执行代码或重跑既有测试。

- 公共模型已有 ExecutionSecurityContext.release_authorization_id；安全附件定义了 FreezeReleaseAuthorization 的记录语义。接手时核对授权记录的现有落点和缺口，按本目录已有安全状态机制持久化；缺公共类型或跨目录能力时回提供方单独补齐，不复制另一份公共契约。
- 现有工具注册要求有副作用的动作使用 per_action，执行器拒绝终止任务；限定收尾需要有严格条件的专用分支。不能把释放伪装只读、普遍放行终止任务或增加通用 skip_confirmation 开关。
- 银行网关已有 authorize_birthday(context, operation_id, action) 接缝，未装配默认拒绝生日写入。回调仅有身份/编号/动作，不能靠“出现过同一个编号”就放行；安全侧的授权必须绑定真实已核对参数与资源，平台/网关接入须保持这一绑定。若实际接口不足，向提供方登记最小改动，不能返回恒真回调。
- 真实业务编排属于 cross，运行装配属于平台 09，配送输入属于 API/前端，银行事实和原子提交属于服务/存储。票 01 不依赖尚未实现的生日业务才能做局部验证，也不能代写其实现。
- 本阶段规则审阅与实现均由 Erwin 负责；历史文档中的 Ringo 人员前置按根 AGENTS 的阶段例外处理。实际 Erwin 本人审阅、AI 审查、自动化测试和历史专业签核分别记录。

## 6. Testing Decisions

先围绕现有安全执行器及真实持久状态验证可观察的放行、拒绝、等待和银行副作用次数；参考现有 gate、订阅策略及验证终态测试，复用测试方法，不以重复实现内部函数来证明正确。票 01 的局部安全能力不要求先有页面；票 02 再使用真实页面/模型/HTTP/隔离模拟银行检验接通效果。

| 核验范围 | 场景依据 | 核心判断 |
|---|---|---|
| 正常生日、部分购买后停止 | XL-B01/B04/B06 | 500 冻结、199/268 核销、33 释放；只付花后301释放；真实购买与收尾分开 |
| 冻结/订单/核销/释放未知 | XL-B05/B06 | 原编号查询，已成功不重复写，未知在途不释放 |
| 旧确认、篡改和父子授权 | XL-X02/X03/X07 | 参数/版本/归属变化后无未经批准写入，模型自报父任务不授予权限 |
| 重启、重复提交、会话/轮次 | XL-X04/X05 | 可信记录可恢复，重复操作最多一次，终止只允许限定收尾 |
| 规则、审计及授权不可用 | XL-X06 | 必要事实或日志失败时零新增敏感写入，待核实不报成功 |
| 注入、隐私与可追溯 | XL-X07/X08 | 外部文本不变成权限，秘密不进模型/普通日志，可追溯到真实银行结果 |

具体输入和边界见两张票及[场景设计](../../evals/cross/representative-cases.md)。每个风险检查给出允许与拒绝对照，既验证不越权，也验证正常业务能完成。证据标注真实/替身层，固定风险条件不宣称真实检测能力；保留失败批次。
