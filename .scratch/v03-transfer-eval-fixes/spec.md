## Problem Statement

老人已开始转账，却可能看到过时的验证画面、无法重新取码，或再次被要求验证；服务故障和真正验证失败没有清楚分开。专用表单录入的完整卡号还进入普通流程检查点，不符合秘密保存边界。模型对缺金额、近似金额等输入也可能只聊天追问而不建立可恢复任务，影响后续补充、刷新和恢复。

评测自身有两处口径差异，已由用户确认处理方式：手工户名不匹配被要求直接failed，但正式F36要求纠正资料；部分允许“输入拒绝”的金额场景被统一要求必须创建任务。不能把所有红色结果都当成产品bug，也不能随意改期望制造全绿。

## Solution

修复以现有普通转账链路、确认门与银行事实为基础：完整号码只经受控办理记录传递；验证失败明确结束，技术故障暂停待核实；有效会话基础验证可用于另一笔分别确认的转账；处理中始终保留原操作编号。模型明确识别转账意图后，即使缺项也应创建可恢复任务并追问，不能猜金额。

按已确认的当前契约口径修订评测，再由各目录最小修复。保留首次失败、全量报告和定向报告；新结果单独记录，不改写历史。

## User Stories

1. 作为转账用户，我希望专用号码只用于本次核验和办理，避免完整卡号进入聊天、模型、日志和普通检查点。
2. 作为转账用户，我希望匹配成功后只看脱敏姓名、账号和开户行，确认对象清楚可信。
3. 作为转账用户，我希望户名不匹配时收到明确提示并按既定规则纠正资料，避免错误目标被用于转账。
4. 作为低风险用户，我希望验证码过期后能重新获取并有新的五分钟作答时间。
5. 作为低风险用户，我希望重发保留已累计错误次数，第三次实际错误后结束本任务。
6. 作为中风险用户，我希望任何一项真实失败或超时后明确结束，迟到成功不能复活任务。
7. 作为中风险用户，我希望重发不延长验证码期限，人脸计时仍从首次启动独立开始。
8. 作为用户，我希望技术故障明确显示待核实，不被记成输错，也不被冒充通过。
9. 作为用户，我希望在同一有效会话办理第二笔低风险转账时复用基础验证，但仍分别核对并确认每笔金额和对象。
10. 作为用户，我希望新登录、不同用户、不同轮次或中风险新动作不能借旧记录获得授权。
11. 作为用户，我希望已受理转账在登录失效后显示待核实，重新登录只查询原操作，不重复提交。
12. 作为用户，我希望执行前审计故障会暂停任务，而不是停在旧验证码画面或报告成功。
13. 作为用户，我希望“给妈妈转钱”建立待补金额的任务，刷新或重启后仍能继续原任务。
14. 作为用户，我希望“大概五百”和金额区间要求精确金额，不能自动取整、取边界或取平均值。
15. 作为用户，我希望非正金额和超过分精度的金额被明确拒绝或追问，不能改成默认值或绝对值。
16. 作为用户，我希望合法十六元先正确显示，再在同任务改为六十元，重新确认后才执行。
17. 作为验收负责人，我希望产品失败、评测器问题、模型无可用输出和安全缺证据分别记录，能知道下一步由谁处理。

## Implementation Decisions

- 目录按根AGENTS临时安排执行：底座/API/银行由Erwin；v0.3转账和最小安全门可由Erwin临时执行，长期安全归Ringo、转账归梁爽。涉及隐私、验证、资金、审计的实际修复仍需Ringo安全审查；本轮没有修复PR的真人安全批准或豁免，不继承历史PR的豁免。
- 不改银行余额、限额或风险业务规则，不增自动兜底，不做宽泛重构。只改当前v0.3路径，不引入未来版本和预约转账票。
- 专用资料先提供服务端受控引用能力，再使转账状态仅携带引用和脱敏展示，最后让F36走引用入口。优先复用已有受控参数快照和资料生命周期，不另建通用秘密平台。受控原文不能进入checkpoint值或写入历史，包括首次输入、修改、恢复、中断窗口。
- 受控引用必须绑定当前用户、任务、轮次及适用版本；模型、前端不能借任意引用选择他人资料。银行办理前仍从受控记录取得原参数，由银行再次核验。对外F36和PayeeInput契约维持现行语义；确需新增公共字段时先报告契约缺口并单独拆契约票，不在业务票越界。
- 银行低风险过期重发问题落在模拟银行验证实现：现有重发先处理到期，再一律要求pending，实际把允许重发的基础码过期也拒绝。只修基础未满三错的过期分支；中风险失败/超时、已通过、取消和跨归属继续拒绝。
- 安全门区分银行可信终止事实与依赖不可用。当前准备挑战/检查挑战的异常统一PAUSE，导致真实终止也成为needs_attention。对已确认的终止走不可恢复阻断，已有转账映射可得到failed；技术故障仍PAUSE。不将所有异常改为BLOCK，也不由业务模块自行制定验证规则。
- 同会话基础记录的发现、受控绑定和装入执行上下文由底座负责。当前索引按task_id筛选且解析要求当前task绑定，银行成功记录本身已允许同user/session/round的session记录。复用前核验真实有效会话、当前风险及记录；scope=action仍绑定原动作版本，不把任务归属校验整体删除。
- 验证HTTP技术故障由API发布可信暂停结果；回查途中失效、执行前审计失败以及流程推进中异常未回填结果由底座处理。当前API读取已保存的任务result；底座只有流程正常返回才保存新结果，因此出现旧waiting_approval快照。先核实故障窗口，使用受控任务更新能力使新快照/事件/版本一致，不直接伪造银行结果。
- 模型只提出普通转账意图和确定字段。明确转账而缺金额不等于闲聊；应形成缺项proposal，交确定性流程追问。金额不确定不填具体金额；已完整的十六元不能被无谓转成无任务回复。三个ValueError样本先诊断输出数量/格式/调用链，不预设网络或供应商根因；不通过重试取最好一次掩盖失败。
- 手动户名不匹配及非法金额无任务拒绝按下方已确认D1/D2评测口径执行，不能先修改产品来迎合有冲突的断言。

### 验收规则

- 密码、验证码、完整专用号码不得出现在模型、聊天/SSE、HTTP日志、异常输出、普通checkpoint_blobs/checkpoint_writes；受控办理参数保存按正式契约，不全库一概禁止。
- 基础前三错规则、中风险一次失败/超时终止、迟到不复活、重传不重复计数、重发不续中风险期限必须全部符合。
- 新动作分别确认；session验证只限合法同会话，action验证不跨动作；参数变化使原授权不适用。
- 技术故障时不增加用户错误次数，不产生执行认领/资金调用；故障后恢复须重新核对当前授权。
- 在途未知只读原operation，结果明确前不得报告成功或生成新资金动作；新登录恢复保留task_id/operation_id。
- 非正或非法精度允许明确输入拒绝，无任务不是自动通过：必须另核对用户提示、没有可执行确认、银行零副作用；专用字段输入分支仍须覆盖。
- 缺项正确追问目标100%，标准合法成功任务≥90%；不以21/21掩盖隐私或强制规则失败。评测口径修订后各分母和迁移单独说明，不沿用旧6/9作为新口径结果。
- 模型未返回可用输出保留Blocked及证据不足原因；不能标Passed或凭ValueError指定根因。
- 全量离线、真实GLM各保留151场景/153样本及源码/数据指纹；模型变化需保留所有计划运行的结果，不挑最好一次。当前数分钟实跑不承诺“秒级全绿”，运行预算在来源票后续验收澄清，不为本轮改CI。
