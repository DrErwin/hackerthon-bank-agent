## Problem Statement

Erwin 已接手简易前端，希望现在开始、在本机尽快看到效果，并在联调后实际展示测试。现有前端只有说明文件；后端虽然已有公开 API 和真实转账组合入口，但缺少可启动的模型与受控策略配置，不能仅凭接口测试宣布浏览器闭环可用。

项目已有 [v03-erwin-vertical-backend/12：执行 v0.3 联合验收并收口版本](../v03-erwin-vertical-backend/issues/12-v03-acceptance-closeout.md)。本工作补齐它需要的交付物，不另建重复的联合验收票。

## Solution

交付一个本机运行的简易 React 前端，先用明确标注的契约测试响应展示交互，再通过已有 HTTP API 接智谱普通 API、真实 Harness、安全门和模拟银行。首轮以普通转账为核心，兼顾普通对话、确认、验证、恢复、结果和管理员只读时间线。

前端负责展示与收集动作；后端确定是否允许执行；银行结果决定交易结果。各实施票完成自己的验证并交接证据，最终 AF01—AF14 与版本收口沿用原票12。

## User Stories

1. 作为 Erwin，我希望本机有清楚的启动步骤，以便快速展示和排查联调问题。
2. 作为 Erwin，我希望先看到可操作的页面，以便在真实模型配置完成前验证交互。
3. 作为演示用户，我希望固定演示身份自动进入，以便不增加注册和账号管理流程。
4. 作为演示用户，我希望普通聊天获得回复，以便不被强制创建转账任务。
5. 作为演示用户，我希望用自然语言发起普通转账，以便不用填写完整转账表格。
6. 作为演示用户，我希望缺少信息时只补缺项，以便沿原任务继续办理。
7. 作为演示用户，我希望自己选择可区分的收款人候选，以便模型不能代选同名对象。
8. 作为演示用户，我希望敏感收款资料有独立输入入口，以便完整账号不回显到聊天。
9. 作为演示用户，我希望看到完整且脱敏的当前确认单，以便核对账户、对象、金额、费用和风险信息。
10. 作为演示用户，我希望确认办理、修改、取消有明确按钮，以便聊天中的“确认”不能批准资金动作。
11. 作为演示用户，我希望修改关键内容后看到新确认单，以便旧确认不能继续使用。
12. 作为演示用户，我希望验证码在专用入口提交，以便它不进入聊天、模型或日志。
13. 作为演示用户，我希望知道何时等待模拟人脸核验，以便不把等待误认成转账成功。
14. 作为演示管理员，我希望用独立身份回答模拟人脸，以便普通用户不能给自己生成通过记录。
15. 作为演示用户，我希望清楚看到成功、失败、取消、处理中和待核实，以便知道下一步能做什么。
16. 作为演示用户，我希望刷新、断线或重新登录后找回原任务，以便不重新转一次。
17. 作为演示用户，我希望重复点击和请求超时后查询原结果，以便避免重复扣款。
18. 作为演示管理员，我希望按任务查看脱敏、只读运行时间线，以便展示测试证据。
19. 作为 Erwin，我希望 GLM 密钥和演示管理密钥只留在本机后端配置，以便页面和仓库不携带密钥。
20. 作为后续前端负责人，我希望交接沿用同一公共契约和 API，以便完整前端能够替换这份简易页面。

## Implementation Decisions

- 采用已定的 React、Vite、TypeScript。一个聊天主界面配状态卡片，管理员入口独立；大字、高对比、按钮清楚，不建设视觉设计系统。
- 前端实施在一个票内完成普通转账所需页面与真实 API 接入；测试响应只用于先行交互验证，界面明确区分测试响应和真实接口。真实模式失败时如实报错，不自动切换测试响应。
- 公共字段、金额与状态引用[公共契约](../../docs/contracts/公共契约-2026-09-23.md)、[确认验证字段](../../docs/contracts/确认验证字段-2026-09-24.md)、[安全与审计字段](../../docs/contracts/安全与审计字段-2026-09-24.md)和[已有 API 交接](../../backend/app/api/README.md)。前端类型从后端公共模型/OpenAPI 生成或核对，不另定业务协议。
- 本机前端通过开发代理访问已有 API，Cookie、Origin 与事件流保持一致。启动说明固定一种本机地址；端口与允许来源必须对应。
- 消息受理可没有任务编号；普通回复只进消息历史。任务产生后从事件和快照关联，不把 HTTP 202 当作业务成功。
- 修改、取消、恢复、结果查询按当前快照提供的可用动作和现有接口执行。遇到 API 不支持的动作，记录具体缺口，回到对应目录处理，不在前端补业务流程。
- 请求重传沿用原请求编号；刷新后先查询原任务。验证码不持久保存；提交编号可用于查询原处理结果，但不保存验证码以自动重发。已提交或结果未知的资金操作仅查原结果。
- SSE 与历史查询按现有事件编号和任务版本补齐；旧会话、旧确认、旧验证不能恢复可点击按钮。重新登录后显式恢复原任务，按服务端要求重新确认和验证。
- 普通用户与管理员使用独立会话容器；管理密钥不编入普通页面或浏览器持久存储。管理员只处理当前模拟人脸和只读时间线，不扩展重置、时间快进等管理功能。
- 真实模型使用智谱普通 API；本机默认模型为可配置的 `glm-4.7`，默认服务地址为普通 API 地址。由标准模型连接器接入已有规划入口，保留配置一致性检查。实际 API 来源是智谱，兼容客户端的名称不能被描述成调用了 OpenAI 服务。
- GLM 模型仅理解、提出转账候选或普通回复，不执行银行动作。密钥、模型、地址和配置版本由后端读取。缺配置、依赖不可用或模型结果无效时停止并报错，不伪造成功或静默回退测试模型。
- 本机检查发现模型连接依赖未安装，因此依赖声明单独形成工程配置票；不为减少票数在平台票中修改工程配置。
- 复用现有转账组合入口、存储、审计、记忆、安全门和银行服务。应用与银行存储使用固定本机持久路径，重启不重新播种或清空原记录，秘密与演示轮次保持一致。
- 受控权限和风险回调属于安全工作线。当前仅有测试中全部放行与固定风险回调，需补真正的本机受控配置。只允许固定演示主体的已登记能力和所需权限，未知身份、动作、轮次、权限及无法核实的事实不默认放行。
- 风险依据引用[转账 PRD §9.2](../../docs/prd/01-智能转账-PRD-2026-09-23.md)和[安全底座 PRD](../../docs/prd/安全底座父级-PRD-2026-09-23.md)。用于展示低、中、高风险的事实必须来自受控演示数据或服务端核实结果，标明规则与数据版本；不能由模型或普通前端填最终风险等级。不自行设未确认的金额阈值，不复制银行风控、余额或限额。
- 如现有公开读入口无法提供某项风险事实，该项保持不可用并明确阻塞；由安全侧列明缺口，不通过猜测、私有读取或固定低风险放行完成票据。演示事实覆盖不能被描述成全量反诈检测。
- 中风险采用既有验证码与模拟人脸双因子；低风险会话复用、高风险终止、过期与错误次数均由已有规则处理，前端不另写一套。
- 单票、分支和 PR 对应一个目录。过程记录可关联本人包和项目跟踪；实现时保护当前未提交改动，使用合适 worktree，不把已有文档改动混入实施提交。

## Testing Decisions

沿用户已确认的验证入口，从浏览器通过公开 HTTP API 办理，再核对模拟银行结果与脱敏运行证据。各票验证可观察行为，优先复用已有 API、平台、安全门的测试入口。

- 前端：普通回复不创建资金动作，候选选择、独立确认/验证、修改/取消、错误显示、事件恢复和重新登录恢复。验证码不进入聊天、客户端日志或持久存储。
- 策略：固定演示主体允许所需动作；其他主体、未登记动作、缺失权限和无权管理人脸被拒绝。低、中、高风险使用明确来源的事实验证已有安全门行为；未确认不能提交。
- 组合：真实 API 连真实 Harness、安全门和模拟银行；测试模型可用于重复性回归，真实 GLM 的普通回复与显式转账另列真实调用证据，两者分别记录。
- 恢复与重复：确认前刷新、后端重启、重复确认、提交中断和结果未知均沿原任务/操作；银行记录只出现一次资金提交。不能以同进程重试代替重启验证。
- 管理：独立身份查看按任务脱敏时间线，普通用户无管理权限；查看不调用模型或资金工具。
- 前端票交接操作步骤、启动方式、覆盖结果和已知缺口；API 原票10引用本轮证据完成剩余验收。AF01—AF14、专业评测和版本决定只在原票12汇总，不新增同类验收票。

## Out of Scope

- 账单、跨场景、预约转账、AA 收款及三场景完整前端。
- 公网部署、正式账号体系、真实银行、真实短信或真实人脸。
- 完整设计系统、视觉动效打磨及可扩展管理平台。
- 新的模型框架、通用策略平台、多模型自动回退或自动模型路由。
- 银行规则复制、未确认风险阈值及全量反诈覆盖承诺。
- 替代 Ringo 专业审查、绕过长期合并门槛或提前收口 v0.3。
